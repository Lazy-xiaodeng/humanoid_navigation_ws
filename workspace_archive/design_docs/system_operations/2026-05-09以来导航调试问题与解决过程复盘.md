## 2. 问题一：坐标系不统一导致定位、地图和导航链路错位

### 现象

早期导航中，机器人模型、地图、局部点云和定位结果存在错位或漂移。全局定位输出、HDL/NDT 输出、Nav2 使用的 `map/odom/base_footprint` 链路没有完全统一，导致 RViz 显示和实际导航判断不一致。

### 尝试过程

1. 保存当前定位 frame 状态，作为后续修改基线。
   - 代表提交：`82b4c7c Save current localization frame state`
   - 涉及文件：`hdl_global_localization`、`hdl_localization`、`robot_realpose_publisher.py`、地图文件和 RViz 配置。

2. 统一导航 frame 到 `map` 和 `odom`。
   - 代表提交：`2f800d5 Unify navigation frames to map and odom`
   - 调整全局定位、运动监控、真实位姿发布、Nav2 参数和 RViz。

3. 发现定位 PCD 地图高度和导航点云不匹配，新增 grounded localization map。
   - 代表提交：`364a53d Add grounded localization map`
   - 新增 `hall_localization_grounded.pcd` 和地图转换脚本。

4. 对齐 localization scan height 和 costmap cloud frame。
   - 代表提交：`4e02c38 Align localization scan height and costmap cloud frame`
   - 同时改 HDL localization launch 和点云滤波节点。

### 中间问题

- 只改 frame 名称不足以解决问题，因为点云本身高度范围、地图高度基准和局部代价地图输入也会造成错位。
- grounded map 能缓解定位地图高度差，但局部 costmap 的 voxel 高度范围仍会影响障碍显示和清障。

### 最终处理

- 建立 `map -> odom -> camera_init/body -> base_footprint` 的统一链路。
- 使用 grounded PCD 给定位链路提供更一致的地图。
- 让点云滤波、定位、costmap 和 RViz 使用一致的 frame 与高度范围。

### 验证方法

- RViz 检查机器人模型、地图、点云是否重合。
- `ros2 run tf2_ros tf2_echo map odom`
- `ros2 topic echo /robot_realpose`
- 导航过程中检查 `/map`、`/odom`、`/tf` 是否持续更新。

### 中间问题

- 单纯扩大高度范围会改善漏检，但也会增加地面或机器人自身进入障碍层的风险。

## 4. 问题三：全局定位候选歧义，错误候选会把机器人拉到相似区域

### 现象

在走廊、展厅、重复墙面等对称环境中，全局定位候选可能 fitness 较好但位置错误。早期如果直接接受候选，会导致机器人位姿跳到相似区域，后续导航围绕错误位置继续运行。

### 尝试过程

1. 拒绝歧义全局定位候选。
   - `aadd5cb Reject ambiguous global localization candidates`

2. 强化 global localization acceptance。
   - `a787f80 Harden global localization acceptance`

3. 后续在 recovery 方案中继续加入 prior gate、soft acceptance、hard gate 等策略。
   - `ebd551f`
   - `beaa05e`
   - `f302565`

### 中间问题

- 环境太对称时，单靠 fitness margin 不足以区分正确候选。
- 如果把错误候选写入 trusted pose 或 frozen prior，会污染后续 recovery，使系统反复在错误区域搜索。

### 最终处理

- 候选必须同时满足位置先验、fitness、距离、时间戳和连续性检查。
- recovery 请求优先带导航上下文 prior，而不是无约束全局搜索。
- 软验收拒绝错误候选后，不允许错误 TF/frozen pose 继续污染后续 prior。

### 验证方法

- 查看 `/localization/recovery_requests`、`/localization/recovery_status`。
- 对照 `/robot_realpose` 和恢复候选位置。
- 统计错误候选被拒绝后，下一次 recovery 是否仍围绕正确点位附近。

## 5. 问题四：启动重定位与 recovery 请求互相打断，形成恢复死循环

### 现象

启动阶段 HDL/SC 还在 bootstrap，全局定位尚未完成时，fusion 或导航状态管理器因超时发起外部 recovery。外部 recovery 重置 bootstrap 状态，导致原本正在进行的启动重定位被打断；系统反复发布 `/initialpose`，机器人位姿被错误覆盖。

### 尝试过程

1. 先做 relocalization retry split checkpoint。
   - `630698a checkpoint before relocalization retry split`

2. 增加 startup origin-prior relocalization。
   - `dd41473 feat: add startup origin-prior relocalization`

3. 发现 startup bootstrap 会被外部 recovery 打断后，在 fusion/recovery 逻辑中区分“从未收到 initialpose”和“收到但持续退化”。
   - 见 `变更日志.md` 中 2026-05-27 20:30 记录。

### 中间问题

- 仅增加 startup prior 不够，因为外部 recovery 仍可能在 bootstrap 未完成时抢占。
- 反复 `/initialpose` 会让 NDT 短暂恢复一帧，然后又进入 reject/recovery，形成循环。

### 最终处理

- 启动阶段对无 prior 的外部 recovery 请求增加保护，不打断正在进行的 startup bootstrap。
- recovery 增加指数退避和最大失败次数。
- initialpose 验证通过前，不直接让自动恢复路径进入 standby 或 suppress。

### 验证方法

- 启动日志中检查 HDL bootstrap 是否自然完成。
- `/initialpose` 是否只在合理时机发布。
- NDT 收到 initialpose 后是否能连续 accepted，而不是一帧后再次 rejected。

## 6. 问题五：NDT 在走廊/转角退化区域产生低 fitness 大平移错误修正

### 现象

在 test3、test4 和后续测试中，NDT 在几何退化区域给出 fitness 很低的匹配，但 correction translation 达到 0.5m 到 1.7m，甚至更大。低 fitness 说明“局部匹配看起来好”，但位姿实际跳到错误位置。

test4 证据：

- 点位 6 已到达，点位 7 过程中失败。
- NDT `accepted/ok` 多，但后续 `rejected/pose_jump` 609 次。
- `rejected/pose_jump` fitness 低至 0.0021 到 0.0409，但最大修正量 1.707m。
- 后期错误 `/initialpose` 后 fitness 升至约 145，定位完全失效。

### 尝试过程

1. 首先收紧 NDT pose jump 阈值。
   - `ec270aa fix: tighten NDT pose_jump thresholds based on test3 drift analysis`
   - 将平移/yaw 门限收紧，提前触发 DEGRADED。

2. 暴露 NDT 鲁棒性参数。
   - `ndt_outlier_ratio`
   - `ndt_max_corr_dist`
   - `ndt_rotation_prior_enabled`
   - `mean_corr_dist`

3. 增加地图质量检查工具。
   - `check_map_quality.py`
   - 用 PCD 地图分析退化热点，辅助判断是不是地图几何不够约束。

### 中间问题

- 单纯收紧门限会拦住错误跳变，但也可能误杀恢复阶段的合理纠偏。
- 单纯放宽门限能减少误杀，但会让错误修正进入 TF，造成真实导航漂移。
- NDT fitness 不能单独作为接受条件，因为错误位置也可能 fitness 很好。

### 最终处理

- 引入多指标判断：fitness、correction translation/yaw、mean_corr_dist、连续帧一致性、导航状态。
- 恢复阶段与正常导航阶段使用不同接受策略。
- 对高风险区域用地图质量工具验证，必要时重新建图或改善局部几何。

### 验证方法

- `ros2 run humanoid_navigation2 check_map_quality <pcd>`
- 监控 `/localization/ndt_status` 中 fitness、reason、correction、mean_corr_dist。
- bag 回放统计 accepted/rejected/pose_jump 数量。

## 7. 问题六：NDT 与 Fusion 双发布 map->odom，导致 TF 竞争和 prior 污染

### 现象

Fusion 方案初衷是 NDT 异常时冻结 `map->odom`，让 odom 短时兜底。但实际调试中，NDT 在 DEGRADED/LOST 或拒帧时仍可能重发旧 TF，Fusion 也在发布冻结 TF，两个发布者竞争。下游 TF 查询会取最新时间戳，导致位姿在旧值、冻结值和错误值之间跳动。

### 尝试过程

1. 设计 NDT+odom fusion 双路径架构。
   - `b5a76e9 feat: add localization_odom_fusion node for NDT+odometry fusion`
   - `9cad3e5 feat: add two-path architecture - fusion mode with odom fallback`

2. 增加 LOST timeout、recovery_requests、到点重置等修补。
   - `0a0fa4f`
   - `6d961fa`
   - `f672615`
   - `d4e7ab5`
   - `852be60`
   - `edeb2b3`

3. test3 后发现 TF 抢占本质问题，先关闭 NDT 拒帧重发 last_good TF。
   - `republish_last_good_tf_on_failure: true -> false`
   - `max_last_good_tf_age_sec: 3.0 -> 0.5`

4. Phase 1 设计中尝试让 Fusion 在 DEGRADED 接管 TF，NDT 非 HEALTHY 抑制 TF。
   - `dc284ef feat: Phase 1 — TF suppression + DEGRADED stop + LOST TF keep + nav entry guards`

### 中间问题

- 如果 NDT 完全不重发 TF，Nav2 可能快速 TF 断档。
- 如果 NDT 重发旧 TF，则又会和 Fusion 冻结 TF 抢占。
- Fusion 自己也查询 `map->odom`，在自己发布冻结 TF 后，可能读到自己的 TF，而非 NDT 原始输出。
- Fusion 节点达到近 2000 行，状态机复杂，和导航状态管理器互相耦合。

### 最终处理

短期：

- 修复 prior 污染：DEGRADED/LOST 期间不再从 TF 树读可能被污染的 `map->body`，而用内存中的 frozen map/odom 与 odom/body 手工合成 prior。
- 提高零速压制频率，减少 Nav2 controller 与 localization stop 的 cmd_vel 竞态。
- 用 `navigation_context_segment` prior 刷新正在 pending 的 recovery。

长期：

- 去掉 Fusion 节点，让 NDT 自监控，`navigation_state_manager` 直接监听 `/localization/ndt_status`。
- 保留 NDT 独占发布 TF，减少双发布者竞争。
- 将异常暂停、恢复、导航缓存统一收到 navigation_state_manager。

代表提交：

- `f302565 fix: P0/P1 localization recovery — nav-aware gate, prior protection, cmd_vel race`
- `a584a7b fix: prevent HEALTHY↔DEGRADED oscillation via per-lifecycle grace period`
- `69899e2 docs: 定位架构简化方案 — 去 fusion 节点`
- `a4ffca5 refactor: 去掉 fusion 节点 — NDT自监控 + nav_state直接监听ndt_status`

### 验证方法

- 检查 `map->odom` 是否只有预期发布路径。
- 检查 `/navigation/status` 是否在 NDT 异常时进入暂停/恢复流程。
- 查看 `navigation_command_result` 是否统一推送 APP，而不是多个节点各自停车。

## 8. 问题七：recovery prior 过期或被错误 TF 污染，导致越恢复越偏

### 现象

在点位 6 附近触发暂停时，机器人实际已经接近点位 6。系统一开始的 prior 也在点位 6 附近，但 HDL 搜索前 prior 过期，被降级为 full global；随后选中了错误候选，错误结果污染 frozen prior，后续 recovery 又围绕点位 4/5 附近继续搜索。

关键证据来自 `导航定位漂移分析.md`：

- 点位 6 附近 prior `(15.15, 18.23)` 距点位 6 约 0.29m。
- HDL 判断 `external recovery prior` age 3.12285s > 3s，直接不用 prior。
- 后续 prior 跳到 `(10.58, 18.27)`，更接近点位 4/5，而不是点位 6。

### 尝试过程

1. 给 recovery request 加 prior。
2. 发现 prior TTL 3 秒太短，完整 HDL 候选计算可能超过该时间。
3. 发现有 recovery pending 时，新的 `navigation_context_segment` prior 被当作 duplicate 丢弃。
4. 发现 DEGRADED/LOST 期间从 TF 查询 prior 会读到被 NDT/Fusion 竞争污染的值。

### 最终处理

- `external_recovery_prior_max_age_sec` 从 3s 延长到 8s。
- `navigation_context_segment` prior 可以刷新 pending recovery。
- DEGRADED/LOST 期间 prior 用 frozen map/odom + 当前 odom/body 合成，不直接查被污染的 map/body TF 链。
- 错误候选被软验收拒绝后，不允许继续污染后续 prior。

### 验证方法

- recovery request 记录 prior source、age、radius。
- 检查 HDL 是否使用 prior 搜索，而不是无 prior 全局搜索。
- 对比 recovery 前机器人真实点位和候选位置。

## 9. 问题八：Nav2/BT 使用旧时间戳，导致 TF extrapolation into the past

### 现象

`nav_drift_test4` 中，点位 7 导航过程中，Nav2/BT 持续使用旧时间戳查询 TF：

```text
Requested time 1779874623.985943
earliest data is at time 1779874647.983390
```

- 长时间行为里不能一直使用 goal 开始时的 stamp。
- 查询当前机器人位姿时应使用当前时间或刷新 `PoseStamped.header.stamp`。
- Nav2 failure 后清理 stale goal 和 costmap filter 消息，避免旧 stamp 污染后续恢复。

### 验证方法

- 对比 requested time 是否持续固定。
- 检查 `/navigate_to_pose/_action/status`、`/behavior_tree_log` 和 `/tf`。

## 10. 问题九：NDT 98% 帧被 pose_jump gate 拒绝，导航反复停车恢复

### 现象

2026-05-27 14:27 的 23 分钟导航测试中，NDT 几乎不工作：

```text
NDT 总帧数: 1501
Accepted: 27 (1.8%)
Rejected: 1473 (98.1%)
Max 连续 reject: 269 帧
23 分钟内 34 次 recovery
```

fitness 本身很好，p50 约 0.0013，但结果被 pose_jump gate 系统性丢弃。

### 根因

NDT 活跃时 5-10Hz，每帧位移 0.05-0.1m，门限本身够用。真正问题是 DEGRADED/停车/recovery 形成长间隙，`init_guess` 冻结在最后 accepted 的位置。恢复后真实位置与旧 init_guess 相差过大，下一帧 correction 超门限，再次 reject，进入“恢复一帧又冻死”的循环。

### 尝试过程

1. 放宽 pose jump 门限。
   - 短期能减少误杀，但间隙足够长仍会超过门限。

2. 启用 reacquire。
   - 如果恢复前累计偏移 >0.8m，reacquire 入口也被挡住，无法自愈。

3. 设计 Fast-LIO delta guess。
   - 用 `camera_init->body` TF 的高频位姿差推进 NDT init_guess。
   - 目标是在 NDT 长间隙后仍让 init_guess 接近真实位置。

4. 首版 Plan B 出现语义错误。
   - 旧做法：直接 `map->odom += body_delta`。
   - 离线 bag A/B 发现这种方式会把机器人自身运动混入全局校正项，破坏 map->odom。

5. 重构 Plan B。
   - 新公式：

```text
T_map_odom_guess =
  T_map_odom_prev * T_odom_body_prev * T_delta_ros * inverse(T_odom_body_curr)
```

这样先预测 map->body，再用当前 odom->body 反推 map->odom，机器人自身运动不会污染 map->odom。

### 最终处理

- Fast-LIO delta guess 引入参数开关、时间戳检查、delta 平移/yaw 限制、dead-reckon 超时和 debug 字段。
- 代码审查修复 initialpose/map 后计时重置、TF clock mismatch、超限 debug 空白等问题。
- 默认先关闭或分阶段开启，避免未经验证直接影响实机。

代表提交：

- `1ba5a6f feat: Plan B — Fast-LIO delta guess 防止 NDT init_guess 冻结`
- `6a0c73f fix: Plan B code review — 5 项修复`
- `c411be6 fix: Plan B 重构 — map_body_to_map_odom 模式替换错误的身体运动叠加`

### 验证方法

- test4 前 200s 离线回放：旧错误公式 accept rate 50.8%，重构公式 accept rate 93.0%，fitness p50=0.0009。
- 数值验证平移/yaw 组合场景 map->odom 误差 0。
- 后续仍需要实机 A/B：只记录不推进、推进但不改门限、全功能三阶段验证。

## 11. 问题十：原地旋转和点位切换时，低 fitness 错匹配触发大平移跳变

### 现象

点位 5 或点位切换后的最终转向阶段，机器人主要原地旋转。NDT fitness 很低，例如 0.004，但相对最后可信位姿产生 1.8m 到 2.2m 平移跳变。这不是匹配质量差，而是重复走廊/墙面环境下，错误位置也能匹配得很好。

### 尝试过程

1. 先靠普通 pose_jump gate 拦截。
   - 能拦截大跳变，但会立即触发 recovery，导致到点/转向阶段反复暂停。

2. 设计旋转保护。
   - `SpinToPose`、`Spin`、`BackUp` 或 `/cmd_vel.angular.z` 超阈值时进入 guard。
   - 旋转期间大平移 correction 不作为真实定位更新，也不立即触发 recovery。
   - 旋转结束后进入 settle，要求连续健康帧。

3. 设计多帧 NDT。
   - 将最近 0.5-1.0s 的多帧点云按 Fast-LIO/odom 相对运动补偿后合成 source cloud。
   - 用更完整的局部结构降低单帧视角歧义。

### 中间问题

- 多帧补偿必须严格处理 Fast-LIO 非标准坐标系和 ROS 标准坐标系，不可混用。
- 多帧窗口过长会拖影，过短不能增加足够几何约束。
- 旋转保护不能无限冻结，否则真实丢定位时无法 recovery。

### 最终处理

- 增加旋转保护和多帧 NDT 参数，默认可按场景控制。
- rotation_guard 期间记录 `rotation_guard_*` 诊断原因，不直接作为普通 pose_jump recovery。
- 旋转结束后 0.5-2s 内要求连续健康帧再继续下一目标。

代表提交：

- `3e14538 增加旋转保护+多帧NDT`

### 验证方法

- 点位最终转向期间不再触发 `navigation_auto_paused`。
- NDT 仍运行，但大跳变记录为 rotation_guard 候选。
- 旋转结束后 1-2s 内连续 healthy，再发下一个导航目标。

## 14. 关键调试方法总结

### 14.1 按问题拆链路

每次定位/导航失败不直接归因于“导航失败”，而是拆成：

```text
传感器输入 -> Fast-LIO / odom -> 全局定位候选 -> map->odom bridge -> TF -> Nav2 -> 状态管理器 -> APP
```

这样能区分：

- 雷达/IMU 是否还在发。
- odom 是否还在走。
- `map->odom` 是不是停止或跳变。
- Nav2 是规划失败、控制失败还是 TF 查询失败。
- APP 收到的是导航失败、定位暂停还是软件停止。

### 14.2 用 bag 回放复现，而不是只看实机现象

常用输入：

- `/tf`、`/tf_static`
- `/fast_lio/cloud_registered`
- `/airy_points`、`/airy_imu`
- `/odom`、`/robot_realpose`
- `/localization/ndt_status`
- `/navigation/status`
- `/navigation/acknowledgments`
- `/cmd_vel`
- `/behavior_tree_log`

常用输出：

- accepted/rejected/pending 统计。
- map->odom 单步跳变。
- recovery request 和 recovery result 时间线。
- Nav2 action 状态和 BT 日志。

### 14.3 每个修复都保留 checkpoint

从提交历史看，多次在大改前保留 checkpoint：

- `31c3045`：TF chain fix 前。
- `fe93e61`：倒走导航前。
- `6652d8c`：startup prior relocalization 前。
- `80d2a96`：fusion two-path 前。
- `bcb2bd2`：P0/P1 recovery fix 前。
- `f73993e`：Fusion 版本归档，准备架构简化。
- `1fcafee`：prior-map 集成 checkpoint。

这使得后续发现方案方向错误时可以明确回退点和对比基线。

### 14.4 对每个方案做反证

典型例子：

- 放宽 pose_jump：能减少误杀，但可能放进错误大跳变。
- 收紧 pose_jump：能拦截错误跳变，但会让恢复更难。
- Fusion 冻结 TF：能维持 TF 树，但双发布者会产生 TF 竞争。
- Fast-LIO delta guess 首版：看似能推进 init_guess，但直接叠加 body_delta 会污染 map->odom。
- prior-map bridge 直接查 TF：逻辑正确但 0.1s 时间差会导致 missing_tf，需要 odom cache/pending。

## 15. 当前经验结论

1. `map->odom` 发布权必须清晰，不能让多个节点在同一状态下竞争。
2. NDT fitness 不能单独判断定位正确，低 fitness 也可能是错误位置。
3. recovery prior 必须带 source、age、radius，并且不能被错误 TF 污染。
4. `/initialpose` 必须验证，不能一注入就抑制自动 recovery。
5. Nav2 失败要检查 TF requested time，固定旧 stamp 是典型故障信号。
6. 旋转和最终朝向调整是定位高风险窗口，应有 guard 和 settle。
7. prior-map/Open3D/RoboSense 输出应作为候选，由统一 bridge 管理 `map->odom`。
8. APP 导航状态应统一从 navigation_state_manager/data_integration 输出，避免多个节点各自上报不同语义。

## 16. 后续建议

1. 继续保留 bag 录制和离线回放流程，尤其是 `/prior_localization/*` 完整话题，避免后续只能间接分析候选。
2. 实机长跑时同步记录 CPU/RSS，确认多帧、Open3D 或 RoboSense 路径不会引入资源瓶颈。
3. 对客户现场使用流程，继续保持 `./start_navigation.sh` 单入口和 APP 多点导航主流程，减少操作变量。
4. 对预留接口如重试失败点、跳过目标点、设置初始位姿，启用前必须完成独立联调和验收。
5. 新地图交付前运行地图质量检查，提前识别长廊、重复墙面、开阔厅等 NDT/scan matching 退化区域。
