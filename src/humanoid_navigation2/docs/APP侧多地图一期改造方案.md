# App 侧多地图一期改造方案

## 1. 文档目的

本文档只关注 app 侧需要做的改动，和 ROS 侧文档 [ROS侧多地图一期改造方案.md](/home/ubuntu/humanoid_ws/src/humanoid_navigation2/docs/ROS侧多地图一期改造方案.md:1) 配套使用。

目标是让 app 在一期中支持：

1. 多地图选择。
2. 点位和地图绑定。
3. 导航任务级别的 `task_session_id` 管理。
4. 导航前切图的状态展示。
5. 任务内地图锁定后的错误处理。

## 2. 一期业务前提

app 侧需要和产品、运营、现场使用方统一以下前提：

1. 用户先选地图，再在该地图上设置点位。
2. 一轮讲解/巡航任务开始前，如果目标地图不是当前运行地图，ROS 会先切图。
3. 切图前，机器人需要被放到目标地图建图原点附近。
4. 切图后，ROS 会自动按该图预设初始位姿重新初始化定位。
5. 一轮任务开始后，地图会被锁定，任务中不能跨地图切换。

## 3. app 一期要实现的功能

### 3.1 地图列表获取

app 启动后或进入导航页面后，需要主动向 ROS 请求地图列表。

用途：

1. 填充“底图选择器”。
2. 显示当前运行地图。
3. 作为设置点位、开始任务前的地图上下文。

### 3.2 地图选择

app 需要提供显式的地图选择入口，例如：

1. 导航页顶部下拉选择器。
2. 点位管理页顶部下拉选择器。
3. 地图预览页切换按钮。

用户选择某张图后：

1. 页面当前地图上下文切到该图。
2. 只显示该图的点位。
3. 新增或修改点位时，自动绑定这张图的 `map_id`。

### 3.3 点位设置与保存

app 在地图上点选点位并保存时，必须把当前地图 `map_id` 一起带给 ROS。

### 3.4 任务级别的开始执行

app 用户点击“开始执行”时，不再只是简单发一个点位，而是视为“开启一轮任务”：

1. app 生成一个新的 `task_session_id`
2. 从这一轮第一个点开始发送导航命令
3. 后续每个点继续复用同一个 `task_session_id`
4. 协议层继续沿用 `start_multi_point_navigation`
5. 但每次请求只在 `waypoint_ids` 中放当前要执行的 1 个点

### 3.5 任务级别的终止

app 现有“终止任务”功能保留，并且要作为任务解锁的核心操作之一。

终止任务后：

1. 本轮 `task_session_id` 结束
2. 下一轮再点“开始执行”时，生成新的 `task_session_id`

### 3.6 切图和定位初始化状态展示

app 不能只显示“正在导航”，还需要区分：

1. 正在切图
2. 正在重置定位
3. 正在等待定位稳定
4. 已可开始导航

## 4. app 页面与交互改造

### 4.1 导航主页面

建议新增以下展示区：

1. 当前选中地图
2. 当前机器人运行地图
3. 当前任务状态
4. 当前任务 id
5. 当前任务锁定地图

推荐展示文案示例：

- `已选择地图：hall1`
- `当前机器人地图：hall`
- `任务状态：等待开始`
- `当前任务地图：hall`

### 4.2 点位管理页面

建议增加：

1. 地图筛选器
2. 当前地图标签
3. 点位所属地图显示

点位列表中建议每个点位有明显地图归属字段，例如：

- `前台 [hall]`
- `展位3 [hall1]`

### 4.3 开始执行按钮逻辑

当前点击“开始执行”时，app 应先做本地前置判断：

1. 是否已选地图
2. 当前任务是否已结束
3. 本轮要执行的点位是否都属于同一张图

若前置判断通过：

1. 生成 `task_session_id`
2. 发送第一点导航命令

### 4.4 暂停按钮逻辑

暂停不等于结束任务。

暂停后：

1. 不生成新的 `task_session_id`
2. 不解锁当前任务地图
3. 如果后续是继续当前任务，继续沿用原 `task_session_id`

### 4.5 终止任务按钮逻辑

终止任务是显式结束一轮任务的操作。

终止后：

1. app 把当前任务标记为结束
2. 清掉本轮缓存的 `task_session_id`
3. 下一次再点“开始执行”时生成新的 `task_session_id`

## 5. app 本地状态设计

建议 app 本地维护一份任务状态对象：

```json
{
  "selected_map_id": "hall1",
  "robot_current_map_id": "hall",
  "task_session_id": "tour_20250610_001",
  "task_status": "idle",
  "session_map_id": "",
  "current_waypoint_id": "",
  "remaining_waypoint_ids": []
}
```

字段说明：

1. `selected_map_id`
   用户当前在 UI 里选中的地图。

2. `robot_current_map_id`
   ROS 当前运行地图，由 ROS 状态推送更新。

3. `task_session_id`
   当前这一轮任务 id。

4. `task_status`
   建议值：
   - `idle`
   - `starting`
   - `switching_map`
   - `resetting_localization`
   - `waiting_localization`
   - `navigating`
   - `paused`
   - `completed`
   - `failed`
   - `terminated`

5. `session_map_id`
   本轮任务锁定地图。

## 6. task_session_id 规则

### 6.1 什么时候生成

app 在用户点击“开始执行”时生成一轮新的 `task_session_id`。

不要在每个点位都生成新的任务 id。

### 6.2 什么时候复用

只要还是同一轮任务，后续每个点位都复用同一个 `task_session_id`。

典型流程：

1. 用户点开始执行
2. app 生成 `tour_001`
3. 发点位 1，带 `tour_001`
4. ROS 返回到达成功
5. app 播报
6. app 发点位 2，继续带 `tour_001`

### 6.3 什么时候换新 id

出现以下任一情况后，下一轮任务必须生成新的 `task_session_id`：

1. 用户点终止任务
2. 当前任务失败退出
3. 当前任务所有点位完成
4. app 收到 ROS 确认当前任务已结束
5. app 重启后重新开始任务

即使下一轮还是同一张地图、还是从点位 1 开始，也必须换新 id。

### 6.4 建议格式

格式不用太复杂，推荐：

- `tour_<yyyyMMdd>_<序号>`
- `tour_<时间戳>`
- `uuid`

示例：

- `tour_20250610_001`
- `tour_1718012345`

## 7. 点位数据规则

### 7.1 新增字段

app 在本地点位对象中新增：

```json
{
  "id": "point_a",
  "name": "前台",
  "map_id": "hall1",
  "position": [1.23, 4.56, 0.0],
  "orientation": [0.0, 0.0, 0.707, 0.707]
}
```

### 7.2 点位编辑规则

1. 用户在 `hall1` 页面上新建点位，则自动保存 `map_id=hall1`
2. 修改点位时，不建议允许“直接切换点位所属地图”
3. 如果确实要改地图，建议走“复制到另一张图/重新建点”的产品逻辑，而不是简单改字段

原因：

1. 同名点位跨图迁移容易造成混淆
2. 也容易导致任务执行中地图不一致

## 8. 开始执行前的 app 本地前置校验

在发给 ROS 之前，app 自己先做一层本地校验，减少无效请求。

### 8.1 当前点请求前检查

1. 当前是否选中了地图
2. 目标点位是否存在
3. 点位 `map_id` 是否等于当前选中地图

### 8.2 多点任务前检查

如果本轮任务是多个点位：

1. 点位列表不能为空
2. 所有点位必须属于同一张地图
3. 这一张地图必须和当前 UI 选中地图一致

如果不一致，app 可以本地直接拦截，提示：

- `本轮任务包含多张地图的点位，无法开始执行`

虽然 ROS 侧也会校验，但 app 先拦截体验更好。

## 9. app 与 ROS 的接口建议

### 9.1 获取地图列表

请求：

```json
{
  "command_type": "map_management",
  "command_data": {
    "command_type": "get_map_list"
  }
}
```

返回：

```json
{
  "maps": [
    {"map_id": "hall", "display_name": "Hall"},
    {"map_id": "hall1", "display_name": "Hall 1"}
  ],
  "current_map_id": "hall"
}
```

### 9.2 设置点位

请求：

```json
{
  "command_type": "waypoint_management",
  "command_data": {
    "command_type": "set_waypoint",
    "waypoint_data": {
      "id": "point_a",
      "name": "前台",
      "type": "navigation_target",
      "map_id": "hall1",
      "position": [1.23, 4.56, 0.0],
      "orientation": [0.0, 0.0, 0.707, 0.707]
    }
  }
}
```

### 9.3 发起逐点导航请求

虽然协议层用的是多点导航命令，但一期约定每次只传当前要执行的一个点。

请求：

```json
{
  "command_type": "navigation_control",
  "command_data": {
    "command_type": "start_multi_point_navigation",
    "task_session_id": "tour_20250610_001",
    "waypoint_ids": ["point_a"],
    "map_id": "hall1"
  }
}
```

一期额外约束：

1. `waypoint_ids` 必须存在
2. `waypoint_ids` 长度必须为 `1`
3. 如果一次传多个点，ROS 侧应拒绝，避免和当前“app 驱动逐点执行”的语义冲突

### 9.4 终止任务

建议 app 继续使用现有终止任务命令，但要明确它的语义是：

1. 终止当前导航
2. 结束当前任务会话
3. 解锁当前任务地图

## 10. ROS 状态推送后 app 的处理逻辑

### 10.1 收到 map_status

app 需要更新：

1. 当前机器人地图
2. 是否在切图
3. 是否显示“请等待切图完成”

### 10.2 收到 localization_status

app 需要更新：

1. 是否正在等待定位稳定
2. 是否显示“请保持机器人在目标地图原点附近”

### 10.3 收到 navigation_started

app 需要：

1. 把任务状态切到 `navigating`
2. 记录当前点位为正在执行

### 10.4 收到 waypoint arrival / navigation completed

app 需要：

1. 把当前点位标记为完成
2. 决定是否播报
3. 播报完成后发送下一点

### 10.5 收到任务失败

app 需要：

1. 停止继续下发下一点
2. 把任务状态标记为 `failed`
3. 根据错误码展示明确提示

## 11. 地图锁定后的 app 逻辑

一期里，地图锁定是很关键的约束。

### 11.1 锁定时机

从本轮任务首个成功进入执行的点开始，`session_map_id` 锁定。

### 11.2 app 应该怎么配合

任务进行中：

1. app 不应允许用户偷偷切换本轮任务的地图上下文
2. 即使 UI 允许切换查看别的地图，也不能影响当前任务
3. 当前任务下发的后续点位，必须继续来自 `session_map_id`

### 11.3 如果后续点位 map 变了

如果 app 还是发出了不同地图的点位：

1. ROS 会拒绝执行
2. app 收到错误后，应立即停止本轮任务的继续下发
3. UI 提示用户：
   - `当前任务地图已锁定为 hall，后续点位属于 hall1，无法继续导航`

## 12. 和现有“当前正在执行其他导航任务”逻辑的关系

你们现在已有一个现象：

- app 点暂停后又点开始执行
- 系统报错：`当前正在执行其他导航任务`

一期 app 改造后，应把这条现有逻辑理解为“当前活动任务未结束”。

### 12.1 暂停后的规则

暂停不等于结束任务。

所以暂停后：

1. 不生成新的 `task_session_id`
2. 若是继续当前任务，则继续沿用旧 id
3. 若用户想开始新一轮任务，必须先终止当前任务

### 12.2 新任务 id 冲突

如果当前任务还没结束，app 又生成了新的 `task_session_id` 去发开始请求，那么 ROS 可能返回：

- `task_session_mismatch`
- 或兼容老文案：`当前正在执行其他导航任务`

app 收到后应理解为：

- 当前不是“开始新任务”的时机
- 要么继续旧任务
- 要么先终止旧任务

## 13. app 的错误提示建议

建议至少支持以下错误提示：

### 13.1 地图不一致

错误码：

- `session_map_mismatch`

建议文案：

- `当前任务已锁定地图 hall，目标点属于 hall1，无法继续导航`

### 13.2 当前任务未结束

错误码：

- `task_session_mismatch`

建议文案：

- `当前任务未结束，不能启动新任务`

兼容旧文案：

- `当前正在执行其他导航任务`

### 13.3 切图失败

错误码：

- `map_switch_timeout`
- `map_switch_partial_failure`

建议文案：

- `地图切换失败，请检查目标地图文件或稍后重试`

### 13.4 定位初始化失败

错误码：

- `localization_not_ready_after_map_switch`
- `initial_pose_injection_failed`

建议文案：

- `已切换到目标地图，但定位初始化失败，请确认机器人位于目标地图原点附近`

## 14. app 推荐状态流转

建议 app 按下面状态流转理解整个流程：

1. `idle`
2. 用户选择地图
3. 设置点位 / 选择点位
4. 点击开始执行
5. 生成 `task_session_id`
6. `starting`
7. 若地图不一致：
   - `switching_map`
   - `resetting_localization`
   - `waiting_localization`
8. `navigating`
9. 到点成功
10. `broadcasting`（app 自己的播报态，可选）
11. 发送下一点
12. 循环直到：
   - `completed`
   - `failed`
   - `terminated`

## 15. app 测试清单

### 15.1 功能测试

1. 能正确拉到地图列表
2. 切换地图后只显示该图点位
3. 设置点位时能正确保存 `map_id`
4. 开始执行时能生成 `task_session_id`
5. 后续点位会复用同一个 `task_session_id`
6. 同一张地图多点任务可以连续执行

### 15.2 异常测试

1. 任务进行中后续点位换图，被正确拒绝
2. 暂停后错误地生成新任务 id，被正确拒绝
3. 切图失败时 UI 有明确提示
4. 定位初始化失败时 UI 有明确提示
5. 若一次在 `waypoint_ids` 中传多个点，被正确拦截或被 ROS 拒绝

### 15.3 回归测试

1. 老的逐点导航流程不崩
2. 老的终止任务流程仍可用
3. 老的暂停/继续流程仍可用
4. 继续沿用多点导航命令但每次只发一个点时，流程正常

## 16. app 改造工时建议

这里只估 app 侧，不含 ROS。

### 16.1 UI 与交互

- 地图选择器、地图状态展示、任务状态展示：1 到 2 天

### 16.2 点位模型与本地状态

- 点位 `map_id`、任务状态对象、任务 id 管理：1 天

### 16.3 协议改造

- 地图列表、导航请求增加 `task_session_id` / `map_id`：0.5 到 1 天

### 16.4 错误处理与状态流转

- 切图、定位、任务冲突等错误展示：1 天

### 16.5 联调测试

- 和 ROS 联调：1 到 2 天

### 16.6 总工时

- 4.5 到 7 个工作日

## 17. 结论

app 一期的核心不是“画更多页面”，而是把以下三件事做好：

1. 地图作为一等业务对象管理起来。
2. 点位和任务都带上地图语义。
3. 用 `task_session_id` 把“这一轮任务”清晰地串起来。

如果 app 侧把：

- `selected_map_id`
- `map_id`
- `task_session_id`
- `task_status`

这四个概念理顺，那么和 ROS 的联调就会清楚很多，也能把现有“当前正在执行其他导航任务”的模糊报错，升级成更好理解的任务会话逻辑。
