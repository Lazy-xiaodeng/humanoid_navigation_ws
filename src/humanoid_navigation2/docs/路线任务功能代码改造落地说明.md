## 2. 最终要实现的功能

这次最终确认的需求，不是旧版那种“继续走 A-B-C-D，只把中间点降级成途经点”。

当前要实现的是：

1. APP 一次性下发整轮路线任务
2. 点位需要支持 `task` 和 `transit` 两类
3. 正常执行时：
   - 任务点之间如果夹着辅助点，ROS 自动吸收这些辅助点
4. 跳步时：
   - 直接跳到目标任务点
   - 中间任务点不执行
   - 当前点与目标点之间按顺序存在的 `transit` 辅助点自动吸收
5. 任务点到达后：
   - ROS 通知 APP 可以播报
   - APP 播报完成后通知 ROS 继续
6. 跳步目标完成后：
   - 从该目标任务点继续沿主任务序列向后执行

关键例子：

1. `7(task) -> 11(transit) -> 12(transit) -> 15(task)`
2. 当前执行到 `7`，APP 跳到 `15`
3. 实际执行应为 `7 -> 11 -> 12 -> 15`
4. 不是 `7 -> 8 -> 9 -> ... -> 15`

1. APP websocket 消息进入 [websocket_server.py](/home/ubuntu/humanoid_ws/src/humanoid_websocket/humanoid_websocket/websocket_server.py:674)
2. `websocket_server` 把导航命令转发到 `/app/navigation_command`

5. [navigation_state_manager.py](/home/ubuntu/humanoid_ws/src/humanoid_navigation/humanoid_navigation/navigation_state_manager.py:555) 订阅 `/navigation/requests`
6. `navigation_state_manager` 执行导航，并把状态发到 `/navigation/status`
7. [data_integration_node_recoverable.py](/home/ubuntu/humanoid_ws/src/humanoid_websocket/humanoid_websocket/data_integration_node_recoverable.py:489) 接收 `/navigation/status`
8. `data_integration` 负责立即推送关键导航事件给 websocket 客户端

### 3.3 当前状态管理器能力

当前 [navigation_state_manager.py](/home/ubuntu/humanoid_ws/src/humanoid_navigation/humanoid_navigation/navigation_state_manager.py:1214) 已支持：

1. `start_single_navigation`
2. `start_multi_point_navigation`
3. `start_exhibition_navigation`
4. `stop_navigation`
5. `pause_navigation`
6. `resume_navigation`

但还没有你这次需求里的：

1. `start_route_task`
2. `jump_to_waypoint`
3. `broadcast_finished`
4. `task / transit` 路线任务状态机
5. `NavigateThroughPoses` 执行段能力

## 6. 建议采用的最小侵入实现策略

### 6.1 不建议一上来改 `Waypoint.msg`

虽然仓库里有 [Waypoint.msg](/home/ubuntu/humanoid_ws/src/humanoid_navigation/msg/Waypoint.msg:1)，但当前主链路里大量点位数据其实是 JSON + `properties` 在流动。

所以更稳妥的第一版做法是：

1. 保持 ROS message 定义先不动
2. 在 `waypoint_data.properties` 中增加：
   - `waypoint_role`
   - `need_broadcast`
   - `broadcast_id`
   - `broadcast_blocking`
   - `stop_and_align`
3. websocket 下发的 `route_waypoints` 里直接带这些字段
4. `dynamic_waypoints_manager` 保存和转发时透传这些字段

这样可以减少改 msg、重编译、兼容老逻辑的风险。

### 6.2 路线任务状态机建议放在状态管理器里

不要把“跳步路径重建”和“辅助点吸收”放在 websocket 层或点位管理层做。

建议统一放在导航状态管理器里，因为这里最适合维护：

1. `master_route_task_ids`
2. `current_anchor_task_id`
3. `current_target_task_id`
4. `active_segment`
5. `awaiting_broadcast`
6. `jump_in_progress`

### 6.3 第一版尽量复用现有多点导航结构

当前已经有：

1. `waypoint_ids`
2. `current_waypoint_index`
3. `start_navigation_sequence()`
4. 逐点完成推进逻辑

建议不是整套推翻，而是：

1. 在其旁边新增一套 `route_task` 结构
2. 先把“整轮任务”和“普通多点导航”分开
3. 普通旧命令先保持兼容

这样回退和灰度都更安全。

## 7. 推荐代码修改顺序

建议另一台机器上的 Codex 按这个顺序施工。

### 第一步：打通协议透传

先改：

1. [websocket_server.py](/home/ubuntu/humanoid_ws/src/humanoid_websocket/humanoid_websocket/websocket_server.py:685)
2. [dynamic_waypoints_manager.py](/home/ubuntu/humanoid_ws/src/humanoid_navigation/humanoid_navigation/dynamic_waypoints_manager.py:259)

目标：

1. APP 发 `start_route_task`
2. ROS 状态管理器能完整收到 `route_waypoints`
3. APP 发 `jump_to_waypoint`
4. ROS 状态管理器能完整收到 `target_waypoint_id`
5. APP 发 `broadcast_finished`
6. ROS 状态管理器能完整收到 `broadcast_id` 和 `waypoint_id`

如果这一步没通，后面不要继续写状态机。

### 第二步：让状态管理器先能“理解新命令”

先在状态管理器里新增命令分发：

1. `handle_start_route_task()`
2. `handle_jump_to_waypoint()`
3. `handle_broadcast_finished()`

这一步先不用追求丝滑，只要能：

1. 保存 `route_task` 对象
2. 正确识别 `task / transit`
3. 正确构建 `master_route_task_ids`
4. 正确构建 `active_segment`

### 第三步：先做普通路线任务闭环

先不做跳步，先做：

1. 整轮路线任务启动
2. 正常相邻任务点之间自动吸收辅助点
3. 到任务点推 `broadcast_requested`
4. 收 `broadcast_finished` 再继续

先把这个闭环跑通，后面再加跳步。

### 第四步：再做跳步逻辑

跳步逻辑要实现：

1. 跳步目标必须是 `task`
2. 中间 `task` 点不执行
3. 中间 `transit` 点自动吸收
4. 跳步目标完成后从该任务点后一个任务点继续

### 第五步：最后再做丝滑 through

当前 [navigation_state_manager.py](/home/ubuntu/humanoid_ws/src/humanoid_navigation/humanoid_navigation/navigation_state_manager.py:1) 只引了 `NavigateToPose`，还没有 `NavigateThroughPoses`。

所以建议：

1. 先用现有逐点方式验证语义
2. 语义正确后，再接入 `NavigateThroughPoses`
3. `transit` 辅助点改成 through poses
4. 最终目标任务点仍保留正式停靠

这样更容易排问题。

## 8. 另一台机器上的 Codex 容易踩的坑

### 8.1 只改了 `navigation_state_manager.py`，但现场跑的是另一个入口

必须先确认 launch 实际跑的是：

1. `navigation_state_manager`
2. 还是 `navigation_state_manager_recoverable`

如果改错文件，功能看起来“写完了”，实际运行却完全没效果。

### 8.2 `websocket_server` 没透传新字段

这是非常高概率的问题。

当前 `navigation_control` 路由时只扁平化保留了少量旧字段，如果不补齐，状态管理器永远拿不到：

1. `route_waypoints`
2. `task_session_id`
3. `target_waypoint_id`
4. `broadcast_id`

### 8.3 新事件没有进实时推送白名单

就算状态管理器已经发了：

1. `broadcast_requested`
2. `jump_updated`
3. `task_waypoint_completed`

如果 [should_push_navigation_status_immediately](/home/ubuntu/humanoid_ws/src/humanoid_websocket/humanoid_websocket/data_integration_node_recoverable.py:823) 不加这些 event，APP 侧也可能只看到慢速状态汇总，表现出来就是“ROS 明明到了，但 APP 不及时播报”。

### 8.4 把辅助点当成任务点推进了主索引

`transit` 只是 through point，不应该推进主任务序列。

推进主任务序列的只能是 `task` 点。

### 8.5 为了加字段去大改老点位类型枚举

当前 [dynamic_waypoints_manager.py](/home/ubuntu/humanoid_ws/src/humanoid_navigation/humanoid_navigation/dynamic_waypoints_manager.py:18) 已经有旧的 `WaypointType` 枚举：

1. `navigation_target`
2. `exhibition_point`
3. `obstacle_point`
4. `charging_point`
5. `rest_point`
6. `landmark_point`

这套旧枚举和这次的 `task / transit` 不是一回事。

建议：

1. 不要直接拿旧 `type` 代替 `task / transit`
2. 新语义优先放到 `properties.waypoint_role`

这样兼容性更好。

## 10. 推荐验收顺序

建议另一台机器上的 Codex 做完后，至少跑这几组：

1. 正常路线：
   - `10(task) -> 11(transit) -> 12(transit) -> 13(task)`
   - 确认 `11/12` 不播报、不等待
2. 正向跳步：
   - 当前 `7`，跳到 `15`
   - 确认执行 `7 -> 11 -> 12 -> 15`
3. 反向跳步：
   - 当前 `15`，跳到 `7`
   - 确认 `7` 完成后继续 `8`
4. 播报闭环：
   - 到任务点后只有在收到 `broadcast_finished` 才继续
5. 播报中跳步：
   - 确认本地播报被打断，状态机不乱
