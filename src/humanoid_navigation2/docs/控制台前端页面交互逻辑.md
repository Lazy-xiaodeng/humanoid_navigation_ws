# 控制台前端页面交互逻辑

## 1. 文档目的

本文档用于基于当前原型页面、ROS 侧真实源码能力、APP 侧开发文档和多地图/路线任务协议，收口一份可直接指导前端、后端、ROS 联调的页面交互逻辑说明。

本文档重点回答：

1. 每个页面和板块的进入条件是什么。
2. 前端点击一个按钮后，前端、后端、ROS 各自应该做什么。
3. 哪些状态以按钮点击为准，哪些状态必须以 ROS 回推为准。
4. 哪些页面允许放行，哪些页面必须校验机器人 / 地图 / ROS 状态后才允许进入。

适用原型目录：

1. `01_登录连接入口页.png`
2. `02_机器人选择页.png`
3. `03_地图配置页.png`
4. `04_点位设置页.png`
5. `05_路线配置页.png`
6. `06_导航控制页.png`
7. `07_诊断日志页.png`
8. `08_系统设置页.png`

## 2. 三层职责

### 2.1 前端职责

前端负责：

1. 页面展示
2. 用户输入
3. 按钮启用/禁用
4. 流程引导
5. 状态可视化
6. 弹窗和错误提示

前端不直接判断机器人是否真的完成了切图、暂停、恢复、导航完成，这些必须等后端转发的 ROS 真实状态。

### 2.2 后端职责

后端负责：

1. 用户身份和设备会话管理
2. 机器人列表和地图列表管理
3. APP 草稿数据保存
4. 前端请求合法性校验
5. 与 ROS WebSocket 协议转换
6. 把 ROS 多条底层消息整理成前端更容易使用的业务状态
7. 失败原因统一转换成前端文案

### 2.3 ROS 职责

ROS 负责：

1. 机器人在线状态
2. 底层系统状态
3. 地图切换
4. 点位存储与 revision 管理
5. 路线任务执行
6. 跳点
7. 播报等待
8. 障碍物暂停/恢复
9. 定位状态和地图 ready 状态

## 3. 全局规则

### 3.1 页面主状态以 ROS 事实状态为准

以下场景不能只靠前端点击结果判断：

1. 机器人是否已连接 ROS
2. 当前地图是否 ready
3. 切图是否完成
4. 路线任务是否开始成功
5. 导航是否暂停成功
6. 导航是否恢复成功
7. 播报是否已进入等待态
8. 障碍是否已清除并恢复

结论：

1. 前端按钮点击后可以进入 `loading / submitting / waiting` 态。
2. 页面最终主状态必须等后端转发 ROS 事件确认。

### 3.2 前端允许“先点按钮”，但不允许“跳过前置条件”

必须卡住的前置条件：

1. 未登录不能进入业务页
2. 未选择机器人不能进入地图配置
3. 机器人未通过后端成功连接到 ROS，不能进入地图配置
4. 地图未 ready，不能进入导航开始阶段
5. 点位草稿未成功同步到 ROS，不能进入正式导航控制
6. 路线未配置完成，不能开始路线任务

### 3.3 命令 ACK 和真实业务状态要分开

前端需要区分两类返回：

1. 命令已受理
2. 业务已完成

例如切图：

1. 后端先回“切图请求已受理”
2. 前端进入“切图中”
3. 只有 ROS 推 `map_ready` 后，前端才允许进入下一板块或允许开始导航

## 5. 页面主流程

推荐主流程如下：

1. 登录连接入口页
2. 机器人选择页
3. 地图配置页
4. 点位设置页
5. 路线配置页
6. 导航控制页
7. 诊断日志页
8. 系统设置页

建议默认主线不是“登录完直接进导航”，而是“登录 -> 选机器人 -> 校验 ROS 连接 -> 选地图 / 必要时切图 -> 配点位 -> 配路线 -> 导航控制”。

## 6. 分页面交互逻辑

### 6.1 登录连接入口页

#### 页面目标

让用户进入控制台，但不在这里直接决定 ROS 是否在线。

#### 前端逻辑

1. 用户点击 `进入控制台`
2. 前端先校验本地登录态 / token
3. 若未登录，跳登录弹窗或登录页
4. 若已登录，进入 `机器人选择页`

#### 后端逻辑

1. 校验 token
2. 返回当前用户可见的机器人列表
3. 返回每台机器人的基础状态：
   - 是否在线
   - 最近心跳
   - 后端是否能连到机器人控制网关
   - 后端是否已通过 websocket 连上 ROS

#### ROS 逻辑

无直接动作。

### 6.2 机器人选择页

#### 页面目标

让用户选择“当前要控制哪台机器人”。

#### 核心规则

用户点击“进入导航前配置”时，是否允许进入下一页，必须以：

`后端是否已通过 ws 成功连接到 ROS`

为准，不是仅仅看用户是否选中了机器人。

#### 前端逻辑

1. 页面加载时展示机器人列表
2. 每个机器人卡片展示：
   - 机器人名称
   - 在线状态
   - 电量
   - ROS 连接状态
   - 当前地图
3. 用户选中某台机器人后，前端将 `selected_robot_id` 写入全局状态
4. 用户点击 `进入导航前配置`
5. 前端调用后端接口 `enter_pre_navigation_check`
6. 前端进入按钮 loading 态，等待后端结果

#### 后端逻辑

1. 收到 `enter_pre_navigation_check(robot_id)`
2. 校验该机器人是否存在
3. 校验当前用户是否有控制权限
4. 校验后端与 ROS 的 websocket 会话是否已建立
5. 如果 ROS 未连接：
   - 返回失败
   - 返回错误码，例如 `ros_not_connected`
   - 返回错误文案，例如“机器人控制链路尚未连接 ROS，请稍后重试”
6. 如果 ROS 已连接：
   - 返回成功
   - 返回当前机器人快照：
     - `robot_accid`
     - `robot_sn`
     - `current_map_id`
     - `map_state`
     - `localization_state`

#### ROS 逻辑

ROS 不需要为这个页面新增命令。  
后端只需要基于当前已建立的 websocket 会话、心跳和快照判断 ROS 是否在线。

#### 页面放行规则

1. `backend_ros_connected=false`：禁止进入地图配置页
2. `backend_ros_connected=true`：允许进入地图配置页

### 6.3 地图配置页

#### 页面目标

确认当前任务使用哪张地图，并在必要时触发切图。

#### 核心规则

`选择当前地图` 这个动作，本质上就是多地图方案中的 `switch_map` 前置流程，但不能直接裸切，必须加业务确认。

#### 推荐按钮

1. `刷新地图列表`
2. `选择当前地图`
3. `进入点位配置`

#### 前端逻辑

1. 页面加载时请求：
   - 地图列表
   - 当前机器人地图快照
2. 展示：
   - UI 选中的地图 `selected_map_id`
   - ROS 当前地图 `ros_current_map_id`
   - 地图状态 `map_state`
   - 定位状态 `localization_state`
3. 用户点击 `选择当前地图`
4. 前端弹出二次确认框，文案建议：
   - “请确认机器人当前实际所在位置位于目标地图原点附近”
   - “若当前地图选择错误，后续定位和导航可能失败”
5. 用户点击确认后，前端向后端发送 `confirm_selected_map`

#### 后端逻辑

收到 `confirm_selected_map(robot_id, selected_map_id)` 后：

1. 先查询当前 ROS 地图状态
2. 比较 `selected_map_id` 与 `ros_current_map_id`

分两种情况：

##### 情况 A：前端选择地图 = ROS 当前地图

后端行为：

1. 不发送 `switch_map`
2. 直接返回“地图校验通过”
3. 把当前地图状态、定位状态、地图 ready 状态回给前端

前端行为：

1. 关闭弹窗
2. 结束 loading
3. 直接放行进入下一板块

##### 情况 B：前端选择地图 != ROS 当前地图

后端行为：

1. 校验当前是否允许切图
   - 当前无路线任务运行
   - 当前无手动暂停待恢复
   - 当前无播报等待
   - 当前无进行中的切图
2. 如果不允许切图，返回错误
3. 如果允许切图，向 ROS 发送 `switch_map`
4. 立即返回“切图流程已启动”
5. 后续继续监听 ROS 的：
   - `map_response`
   - `map_status`

前端行为：

1. 确认按钮置灰
2. 显示“正在切换地图”
3. 显示进度条 / 转圈动画
4. 页面进入 `map_switch_in_progress=true`
5. 禁止用户跳过当前步骤

ROS 行为：

1. 接收 `switch_map`
2. 如目标地图与当前地图不同，执行切图流程
3. 保持 websocket / map_context_manager / dynamic_waypoints_manager 常驻
4. 重启导航定位层
5. 注入目标地图初始位姿
6. 等待定位 ready
7. 回推：
   - `map_response` 切图开始
   - `map_status` switching
   - `map_status` localization_resetting / waiting_localization
   - `map_response` 切图完成或失败
   - `map_status` ready 或 failed

#### 切图完成后的前端放行规则

前端只有在满足以下条件时才自动进入下一板块：

1. `map_state = ready`
2. `localization_state = stable`
3. `ros_current_map_id = selected_map_id`

否则：

1. 若 `map_state = failed`，停留当前页并显示错误
2. 若仍在 `switching / waiting_localization`，继续等待

### 6.4 点位设置页

#### 页面目标

维护当前地图下的点位草稿，并在“保存并继续”时同步到 ROS。

#### 核心规则

点位页不是每次编辑都立即打 ROS 命令，而是：

1. 前端编辑
2. 后端保存草稿
3. 用户点击保存时统一同步到 ROS

#### 前端逻辑

1. 页面只加载 `selected_map_id` 下的点位
2. 点位支持：
   - 新增
   - 修改
   - 删除
   - 清空
3. 编辑后前端标记 `draft_dirty=true`
4. 用户点击 `保存点位并进入路线配置` 或 `保存点位并进入导航`
5. 前端进入 loading 态

#### 后端逻辑

1. 对草稿做 diff
2. 根据 diff 生成 ROS 命令：
   - `set_waypoint`
   - `update_waypoint`
   - `delete_waypoint`
   - `clear_waypoints`
3. 顺序发送到 ROS
4. 等待全部成功
5. 收到最新 `waypoints_revision`
6. 更新后端当前地图点位版本
7. 返回同步成功

如果失败：

1. 返回具体失败点位和错误码
2. 不跳页
3. 保留草稿

#### ROS 逻辑

1. `dynamic_waypoints_manager` 按 `map_id` 保存点位到对应文件
2. 回推：
   - `waypoint_response`
   - `waypoints_data`
3. 在 `waypoints_data` 中回传最新 `waypoints_revision`

#### 页面放行规则

1. 只有“草稿同步 ROS 成功”后，才允许进入路线配置页或导航控制页
2. 如果只是本地草稿保存成功，但 ROS 同步失败，不允许放行

### 6.5 路线配置页

#### 页面目标

在当前地图的点位基础上组织路线顺序。

#### 前端逻辑

1. 只展示当前地图的点位
2. 用户按顺序选择点位形成路线
3. 支持调整顺序
4. 支持保存为路线模板
5. 路线中展示点位属性：
   - `task / transit`
   - `forward / backward`
   - `need_broadcast`

#### 后端逻辑

1. 保存路线对象
2. 校验：
   - 全部点位属于同一个 `map_id`
   - 至少有一个 task 点
   - transit 点不允许作为跳步目标
3. 若用于启动任务，生成：
   - `route_id`
   - `task_session_id`
   - `ordered_waypoint_ids`
   - `waypoints_revision`

#### ROS 逻辑

此页通常不直接发 ROS 命令。  
只有点击开始导航时，后端才把路线组织成 `start_route_task`。

### 6.6 导航控制页

#### 页面目标

执行当前路线任务，并消费 ROS 实时状态。

#### 页面主要板块

1. 顶部机器人状态栏
2. 地图与机器人位姿区
3. 路线进度区
4. 当前目标 / 下一个目标 / 跳点目标
5. 按钮区：开始、暂停、继续、终止、跳点
6. 播报状态区
7. 系统健康 / 异常状态区
8. 事件日志区

#### 开始导航

前端：

1. 点击 `开始`
2. 校验：
   - `map_state = ready`
   - `selected_map_id = ros_current_map_id`
   - 当前路线不为空
   - 点位 revision 已同步
3. 发送开始请求给后端
4. 按钮进入 loading

后端：

1. 组装 `start_route_task`
2. 推荐默认使用：
   - `route_waypoint_ids`
   - `waypoints_revision`
3. 发送给 ROS
4. 等待：
   - `command_ack`
   - `navigation_command_result`
   - `navigation_status`

ROS：

1. 校验当前地图与任务地图一致
2. 启动路线任务
3. 推送真实状态

前端切换规则：

1. 收到 ACK：仅结束按钮 loading，不切主状态
2. 收到 `navigation_command_result success`：进入 `starting`
3. 收到 `navigation_state_changed / navigation_status` 表明真实运行中：进入 `running`

#### 暂停导航

前端：

1. 点击 `暂停`
2. 按钮 loading

后端：

1. 发 `pause_route_task`
2. 返回 ACK
3. 等待 ROS `navigation_paused`

ROS：

1. 进入暂停
2. 推 `navigation_paused`

前端：

1. 仅在收到 `navigation_paused` 后进入暂停态
2. 根据 `pause_source` 展示不同原因

#### 继续导航

前端：

1. 点击 `继续`
2. 可用于：
   - 手动暂停恢复
   - 障碍人工清障后恢复
   - 人工脱困后恢复

后端：

1. 发 `resume_route_task`
2. 返回 ACK
3. 等待 ROS `navigation_resumed`

前端：

1. 只有收到 `navigation_resumed` 才切回运行态

#### 终止导航

前端：

1. 点击 `终止`
2. 二次确认
3. 发送 `stop_route_task`

后端：

1. 转发到 ROS
2. 等待 `navigation_stopped`

前端：

1. 收到 `navigation_stopped` 后清理当前任务上下文
2. 回到已选地图的待命态

#### 跳点

前端：

1. 点击 `跳点`
2. 弹出候选列表
3. 只能选择 `task` 点，不能选择 `transit`
4. 发送 `jump_to_waypoint`

后端：

1. 校验当前任务存在
2. 校验目标点属于当前路线
3. 转发给 ROS

ROS：

1. 重新计算当前执行段
2. 吸收中间 transit 点
3. 推送 `jump_updated`

前端：

1. 收到 `jump_updated` 后刷新当前目标、下一个目标、路线进度
2. 如果跳点打断了等待播报，也要同步清除旧播报等待 UI

#### 播报等待

前端：

1. 收到 `broadcast_requested`
2. 进入“等待播报完成”状态
3. 由后端真正调起语音播报，不由前端直接控制音频引擎
4. 后端把“已收到播报请求 / 正在播报 / 播报完成待恢复”这些实时状态推给前端
5. 播报结束后由后端发 `broadcast_finished`

注意：

1. 这个状态下不要走 `resume_route_task`
2. 播报等待和暂停恢复不是同一个按钮语义
3. 前端“继续按钮”不能代替 `broadcast_finished`

#### 播报链路三方分工

ROS：

1. 到达需要播报的任务点后推送 `broadcast_requested`
2. 收到 `broadcast_finished` 前保持等待
3. 收到 `broadcast_finished` 后继续导航

后端：

1. 收到 ROS 推送的 `broadcast_requested`
2. 真正触发语音播报
3. 维护播报状态机
4. 播报完成后向 ROS 发送 `broadcast_finished`
5. 把播报相关实时状态推给前端

前端：

1. 只负责展示播报状态，不直接决定机器人何时继续导航
2. 根据后端状态刷新 UI 和日志
3. 在“播报中”或“等待播报完成”期间禁用与播报语义冲突的按钮

#### 后端播报主流程

1. ROS 推 `broadcast_requested`
2. 后端收到后进入 `broadcast_waiting`
3. 后端启动音频播放，状态切到 `broadcasting`
4. 后端向前端推送“正在播报”
5. 音频播放结束后，后端进入 `broadcast_finishing`
6. 后端向 ROS 发送 `broadcast_finished`
7. ROS 收到后恢复导航
8. 后端收到 ROS 恢复导航状态后，向前端推送“播报完成，导航已恢复”

#### 前端播报状态区建议

当前导航控制页已经有播报状态区，建议按下面状态细分显示：

1. `idle`
   说明当前没有播报任务
2. `broadcast_waiting`
   已收到 `broadcast_requested`，后端准备开始播报
3. `broadcasting`
   后端已经开始播报
4. `broadcast_finishing`
   本地播报已结束，后端正在发送 `broadcast_finished`
5. `broadcast_done`
   ROS 已确认并继续导航
6. `broadcast_failed`
   播报失败、超时或恢复失败

#### 前端播报状态展示建议

建议播报状态区至少展示：

1. 当前播报状态
2. 当前播报点位名称 / `waypoint_id`
3. 当前 `broadcast_id`
4. 当前播报文本摘要
5. 播报开始时间
6. 播报耗时
7. 播报完成后是否已恢复导航

#### 推荐前端文案

1. 收到播报请求：`已到达任务点，等待播报`
2. 开始播报：`正在播报当前讲解内容`
3. 播报完成待恢复：`播报完成，正在通知机器人继续导航`
4. 导航恢复：`机器人已继续前往下一目标点`
5. 播报失败：`播报失败，请重试或人工处理`

#### 推荐后端播报事件模型

为了让前端状态和日志统一，建议后端对前端推送统一的播报业务事件：

1. `broadcast_requested`
2. `broadcast_started`
3. `broadcast_completed_local`
4. `broadcast_finished_sent`
5. `broadcast_navigation_resumed`
6. `broadcast_failed`

#### 播报与导航状态的关系

1. 播报等待不是“手动暂停”
2. 播报等待不是“障碍暂停”
3. 播报完成后恢复导航不能走 `resume_route_task`
4. 前端主状态栏和播报状态区应同时显示，避免用户误以为机器人卡死
5. 如果用户在播报等待时尝试点击“继续”，前端应拦截并提示“当前为播报等待，请等待播报完成”

#### 障碍暂停与人工脱困

前端：

1. 收到 `navigation_paused` 且 `pause_source=obstacle_wait`
2. 切到障碍等待态
3. 若收到自动 `navigation_resumed`，自动恢复运行态
4. 若需要人工处理，则显示“清障后继续”

### 6.7 诊断日志页

#### 页面目标

用于查看关键事件、异常和调试信息。

#### 前端逻辑

1. 展示：
   - 导航状态变更
   - 地图切换日志
   - 播报事件
   - 障碍暂停/恢复
   - 系统异常
   - rosbag 录制事件
2. 支持过滤
3. 支持按时间倒序

#### 后端逻辑

1. 汇总 ROS 推送事件
2. 形成统一日志流
3. 支持前端查询历史和订阅实时新增

#### ROS 逻辑

通过已有状态推送和系统异常消息提供事件源。

### 6.8 系统设置页

#### 页面目标

放低频管理项，不和导航主流程混在一起。

建议内容：

1. 机器人基础信息
2. 当前 accid/sn
3. 当前地图注册信息
4. WebSocket 连接状态
5. 日志导出
6. rosbag 录制开关
7. 系统版本

#### 机器人身份信息展示规则

此页建议直接展示：

1. `robot_accid`
2. `robot_sn`
3. ROS 连接状态

这样现场人员能一眼确认当前到底控制的是哪台机器人。

## 7. 顶部导航是否允许随时跳页

### 7.1 建议允许跳页，但不是所有跳页都无条件放行

建议：

1. 登录后顶部导航可见
2. 但页面切换前仍需做业务校验

例如：

1. 未选机器人时点击地图页：拦截并提示先选机器人
2. ROS 未连接时点击地图页：拦截并提示机器人链路未就绪
3. 地图未 ready 时点击导航页：允许查看，但禁止开始任务
4. 点位草稿未同步时点击导航页：提示先同步点位

### 7.2 建议的页面跳转放行规则

1. `机器人选择页`：登录后可进
2. `地图配置页`：必须已选机器人且 ROS 已连接
3. `点位设置页`：必须已选地图，并完成地图确认 / 切图 ready
4. `路线配置页`：必须有当前地图上下文
5. `导航控制页`：允许进入，但若路线未就绪则禁用开始按钮
6. `诊断日志页`：登录后可进
7. `系统设置页`：登录后可进

## 8. 推荐的后端聚合接口

为了让前端别直接拼太多底层消息，建议后端至少提供以下聚合能力：

1. `get_robot_entry_snapshot`
   - 机器人选择页用
   - 返回机器人在线、ROS 连接、当前地图、accid/sn

2. `confirm_selected_map`
   - 地图配置页用
   - 内部负责判断是否同图直接放行，还是走 switch_map

3. `save_waypoint_draft`
   - 点位页草稿保存

4. `sync_waypoints_to_ros`
   - 点位页正式保存

5. `save_route_draft`
   - 路线配置页草稿保存

6. `start_route_task`
   - 导航开始

7. `pause_route_task`
8. `resume_route_task`
9. `stop_route_task`
10. `jump_to_waypoint`
11. `broadcast_finished`

## 9. 地图配置页的推荐时序

这里用你刚刚确认过的业务逻辑收口一遍。

### 9.1 当前地图相同

1. 前端点击 `选择当前地图`
2. 前端弹出确认框
3. 用户确认“机器人位于目标地图原点附近”
4. 前端请求后端 `confirm_selected_map`
5. 后端发现 `selected_map_id == ros_current_map_id`
6. 后端不发 `switch_map`
7. 后端直接返回 `map_confirm_passed`
8. 前端放行进入下一板块

### 9.2 当前地图不同

1. 前端点击 `选择当前地图`
2. 前端弹出确认框
3. 用户确认“机器人位于目标地图原点附近”
4. 前端请求后端 `confirm_selected_map`
5. 后端发现 `selected_map_id != ros_current_map_id`
6. 后端发送 `switch_map`
7. 后端立即告诉前端“切图中”
8. 前端确认按钮置灰，显示转圈/进度条
9. ROS 推 `map_status switching`
10. ROS 推 `map_status waiting_localization`
11. ROS 推 `map_ready`
12. 后端转成前端状态
13. 前端自动放行进入下一板块

### 9.3 切图失败

1. 前端点击 `选择当前地图`
2. 后端发 `switch_map`
3. ROS 返回失败
4. 后端把错误码和文案回给前端
5. 前端停留地图配置页
6. 解除按钮置灰
7. 明确提示失败原因

## 10. 验收重点

这份页面交互逻辑文档最终验收应重点看以下几点是否落地：

1. 机器人选择是否真的以“后端已连接 ROS”作为放行条件，而不是只看选中状态。
2. 地图配置是否真的支持“同图直接放行、异图才切图”的分支逻辑。
3. 切图时前端是否有完整的中间态，而不是点完按钮就瞬间跳页。
4. 点位页是否真的是“先草稿、后同步 ROS”。
5. 导航页是否区分了 ACK 和真实状态推送。
6. 播报等待、手动暂停、障碍暂停是否被前端当成三个不同状态处理。
7. 系统状态里是否展示并消费了 `robot_accid / robot_sn`。
8. 诊断页是否能回看切图、跳点、暂停恢复、播报等待等关键事件。
