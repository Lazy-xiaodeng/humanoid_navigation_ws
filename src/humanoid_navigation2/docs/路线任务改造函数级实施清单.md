# 路线任务改造函数级实施清单

## 1. 文档定位

本文档是路线任务改造的正式实施清单，目标是让开发、联调、评审和测试使用同一套口径。

本清单覆盖：

1. 首版范围边界。
2. 真实改造文件。
3. APP 与 ROS 协议。
4. ROS 内部状态模型。
5. 核心函数职责。
6. `NavigateThroughPoses` 接入方式。
7. 任意跳步、播报闭环、through 进度、首 task 处理。
8. 错误码、事件 payload、测试矩阵与开发顺序。

正文中的文件路径统一使用仓库相对路径，便于不同机器和不同工作区复用。

### 1.1 中文注释与说明标准

后续所有 route task 相关代码和本文档新增代码片段，都必须补充足够具体的中文注释。

代码注释最低要求：

1. 新增函数必须在函数入口附近说明“这个函数负责什么业务步骤”。
2. 新增关键分支必须说明“为什么走这个分支”，不能只重复代码本身。
3. 新增状态字段必须说明“谁写入、谁读取、什么时候清空”。
4. 新增事件 payload 组装处必须说明“APP 收到后应该如何消费”。
5. 新增错误码返回处必须说明“触发条件”和“APP 建议展示文案”。
6. 新增 through action 回调必须说明“如何过滤旧 goal / 旧 session 的晚到回调”。
7. 新增列表快照必须说明“为什么要 `list(...)` 拷贝，而不是直接引用内部运行态列表”。
8. 新增布尔、ID、role 归一化必须说明“输入可能是什么类型，归一化后用于哪类比较”。

文档代码片段说明要求：

1. 每个 Python/JSON 结构示例后必须有“中文注释”或“字段说明”，解释这段结构在运行时的用途。
2. 每个伪代码片段后必须说明该算法保护的业务不变量。
3. 每个协议字段必须至少写清楚来源、默认值、缺失处理和 APP/ROS 用途。
4. 每个事件示例必须写清楚触发时机和 APP 侧消费后的预期动作。
5. 每个 error code 必须写清楚推荐用户文案，避免 APP 临场猜测。

> 中文注释：这节不是要求把每一行代码都翻译成中文，而是要求关键业务意图必须写在代码旁边。路线任务涉及 APP、websocket、桥接层、状态机、Nav2 action 和播报闭环，任何一个分支只写“做了什么”都不够，还要写“为什么必须这样做”，否则后续联调时很难判断问题是协议、状态机还是 Nav2 回调晚到。

## 2. 首版范围红线

### 2.1 首版必须完成

1. APP 一次性下发完整 `route_task`。
2. `route_waypoints[]` 显式区分 `task` 与 `transit`。
3. 路线顺序只认 `route_waypoints[]` 数组顺序，不按 `waypoint_id` 数值推断。
4. 相邻 task 段自动吸收中间 transit。
5. 支持正向 jump。
6. 支持反向 jump。
7. jump 时跨过的中间 task 写入 `skipped_task_ids`。
8. jump 时中间 transit 自动吸收到新执行段。
9. 首版直接以 `NavigateThroughPoses` / through 能力作为验收目标。
10. `broadcast_requested -> broadcast_finished -> task_waypoint_completed` 播报闭环跑通。
11. `interrupt_broadcast=true` 完整支持。
12. 旧 session、重复命令、旧 Nav2 feedback/result 不得污染当前执行态。

### 2.2 首版明确不做

1. 过门专用 BT。
2. 门区姿态强约束。
3. heading guard。
4. doorway 专项避障增强。
5. `interrupt_broadcast=false` 的挂起跳步队列。
6. 多个 jump 请求排队。
7. route 编辑、插队、动态增删点。
8. `start_route_task` 抢占旧普通导航。

### 2.3 固定语义

1. 首版 through 是验收目标，不保留“逐点先跑通再升级”的实现口径。
2. “当前位置”不是虚拟 waypoint，不写入 `execution_waypoint_ids`。
3. `passed_transit_waypoint_ids` 只作用于当前 `active_segment`，不是全局去重表。
4. 例如 `7 -> 15` 经过 `11/12` 后，后续 `15 -> 3` 仍可重新经过 `12/11`。
5. transit 永远不推进主任务索引，不播报，不进入 completed/skipped task 集合。
6. `route_task_completed` 必须先携带摘要发事件，再清理 ROS 运行态。

## 3. 真实改造文件

### 3.1 主链路入口

当前真实主链路优先按以下路径理解：

1. `start_navigation.sh`
2. `robot_real.launch.py`
3. `navigation_fusion_sc.launch.py` 或 `navigation_fusion.launch.py`
4. `src/humanoid_navigation/humanoid_navigation/navigation_state_manager.py`
5. `src/humanoid_navigation/setup.py` 中的 `navigation_state_manager = humanoid_navigation.navigation_state_manager:main`

> 中文注释：`robot_real.launch.py` 是整机 bringup 入口，不直接创建 `navigation_state_manager`。它会根据 `relocalization_engine` include `navigation_fusion_sc.launch.py` 或 `navigation_fusion.launch.py`，再由这两个 APP 层 launch 启动已改造的 `navigation_state_manager`。不要在 `robot_real.launch.py` 里重复启动状态机，否则会出现同名节点和重复 action client。

> 中文注释：launch 文件里的 `executable='navigation_state_manager'` 必须能在 `setup.py` 的 `console_scripts` 中找到对应入口。否则 launch 配置看起来正确，但 ROS2 安装后可能找不到可执行脚本，导致 route task 主状态机无法启动。

首版主入口是：

1. `src/humanoid_navigation/humanoid_navigation/navigation_state_manager.py`

### 3.2 第一优先级文件

1. `src/humanoid_websocket/humanoid_websocket/websocket_server.py`
2. `src/humanoid_navigation/humanoid_navigation/dynamic_waypoints_manager.py`
3. `src/humanoid_navigation/humanoid_navigation/navigation_state_manager.py`
4. `src/humanoid_websocket/humanoid_websocket/data_integration_node_recoverable.py`
5. `src/humanoid_navigation/package.xml`

`package.xml` 依赖要求：

1. 必须声明 `nav2_msgs`，用于 `NavigateThroughPoses` / `NavigateToPose` action。
2. 必须声明 `action_msgs`，用于 `GoalStatus` 和 `CancelGoal`。
3. 直接在 Python 代码中 import 的 ROS 消息/action/service 包都应显式写入 `package.xml`，不要依赖其它包的传递依赖。

> 中文注释：这条是部署稳定性要求。代码在开发机上能 import，不代表机器人安装环境一定完整；显式声明依赖可以减少 colcon 构建、部署和新机器复现时的隐性问题。

### 3.3 第二优先级兼容文件

1. `src/humanoid_navigation/humanoid_navigation/navigation_state_manager_recoverable.py`

当前策略：

1. 首版 route task 验收路径不再依赖 `navigation_state_manager_recoverable.py`。
2. 默认 `navigation.launch.py`、`navigation_fusion.launch.py`、`navigation_fusion_sc.launch.py` 均应启动 `navigation_state_manager`。
3. `navigation_state_manager_recoverable.py` 作为旧入口保留，仅用于必要时人工回退旧导航链路。
4. 不为了兼容 recoverable 反向污染主链路设计。
5. 若现场必须继续使用 recoverable 入口，应先单独评审并迁移 route task 全量能力，而不是默认把它纳入首版验收。

## 4. 内部数据模型

### 4.1 `RouteWaypoint`

状态机内部只读取归一化后的结构，不在业务分支里反复读取原始 JSON。

```python
{
    "waypoint_id": "15",
    "waypoint_name": "实验室讲解点",
    "waypoint_role": "task",          # task | transit
    "need_broadcast": True,
    "broadcast_id": "lab_intro",
    "broadcast_blocking": True,
    "stop_and_align": True,
    "frame_id": "map",
    "position": [x, y, z],
    "orientation": [qx, qy, qz, qw],
    "source_index": 7,
    "raw_payload": {...}
}
```

> 中文注释：这个结构是状态机内部使用的“已归一化路线点”。后续 through 下发、jump 重建、播报触发都只读取这里的稳定字段，不再反复解析 APP 原始 JSON。`source_index` 用来保留 APP 数组顺序，避免把 `"15"` 这种 ID 数值大小误当成路线顺序；`raw_payload` 只用于日志和问题复盘，不作为业务判断主数据。

字段来源优先级：

1. `waypoint_role`: 优先 `route_waypoints[].waypoint_role`，其次 `route_waypoints[].properties.waypoint_role`。
2. `need_broadcast`: 优先 `route_waypoints[].need_broadcast`，其次 `route_waypoints[].properties.need_broadcast`。
3. `broadcast_id`: 优先 `route_waypoints[].broadcast_id`，其次 `route_waypoints[].properties.broadcast_id`。
4. `broadcast_blocking`: 优先 `route_waypoints[].broadcast_blocking`，其次 `route_waypoints[].properties.broadcast_blocking`。
5. `stop_and_align`: 优先 `route_waypoints[].stop_and_align`，其次 `route_waypoints[].properties.stop_and_align`。
6. `pose`: 优先 waypoint 自带 pose；如设计允许，再从本地点位缓存补齐。

默认值：

1. `task.need_broadcast` 默认 `false`。
2. `task.broadcast_blocking` 默认 `true`。
3. `task.stop_and_align` 默认 `true`。
4. `transit.need_broadcast` 强制 `false`。
5. `transit.broadcast_blocking` 强制 `false`。
6. `transit.stop_and_align` 强制 `false`。

首版实现说明：

1. `broadcast_blocking` 当前已归一化保存，但首版行为统一按阻塞播报处理。
2. `broadcast_blocking=false` 暂不启用非阻塞播报流程。
3. `stop_and_align` 当前已归一化保存，但首版未新增独立停车/对齐动作。
4. 首版以 Nav2 through 到达目标 task 后触发播报/完成流程为准。
5. 后续若实现非阻塞播报或独立停车对齐，应在状态机和 APP 协议中另行补充状态流转。

归一化失败即拒绝 `start_route_task`：

1. 缺少 `waypoint_id`。
2. 无法归一化出 `waypoint_role`。
3. 无法补齐 pose。
4. 路线中没有任何 `task`。

### 4.2 `RouteTaskState`

```python
{
    "task_session_id": "tour_20260611_001",
    "route_id": "route_demo_001",
    "route_waypoints": [RouteWaypoint, ...],
    "master_route_task_ids": ["3", "7", "15", "18"],
    "completed_task_ids": [],
    "skipped_task_ids": [],
    "current_anchor_task_id": "7",
    "current_anchor_task_index": 1,
    "current_target_task_id": "15",
    "current_target_task_index": 2,
    "active_segment": {...},
    "awaiting_broadcast": False,
    "waiting_broadcast_waypoint_id": "",
    "waiting_broadcast_id": "",
    "jump_interrupts_broadcast": False,
    "route_task_version": 3,
    "active_goal_generation": 5,
    "last_completed_task_id": "",
    "last_completed_broadcast": {
        "task_session_id": "",
        "waypoint_id": "",
        "broadcast_id": ""
    }
}
```

> 中文注释：这个结构表示“一次正在执行的路线任务会话”。`completed_task_ids` 和 `skipped_task_ids` 是 APP 展示整体进度的依据；`current_anchor_task_id` 和 `current_target_task_id` 是当前段从哪里到哪里的业务语义；`route_task_version` 与 `active_goal_generation` 是防止旧 session、旧 Nav2 goal 回调晚到污染新任务的两道保险。

关键约束：

1. `master_route_task_ids` 只包含主业务点 `task`。
2. `completed_task_ids` 只记录真正闭环完成的 `task`。
3. `skipped_task_ids` 只记录被 jump 跨过的 `task`。
4. `skipped_task_ids` 必须去重保存。
5. 已进入 `completed_task_ids` 的 task 不得再写入 `skipped_task_ids`。
6. `route_task_version` 用于隔离旧 session / 旧 route task 逻辑。
7. `active_goal_generation` 用于隔离旧 Nav2 feedback/result。
8. `last_completed_broadcast` 用于识别最近一次已完成播报的重复 `broadcast_finished` 幂等回执。

### 4.3 `ActiveSegment`

```python
{
    "segment_id": "seg_0003",
    "segment_direction": "forward",       # forward | backward
    "segment_start_task_id": "7",
    "segment_target_task_id": "15",
    "segment_start_source_index": 1,
    "segment_target_source_index": 7,
    "transit_waypoint_ids": ["11", "12"],
    "execution_waypoint_ids": ["11", "12", "15"],
    "passed_transit_waypoint_ids": ["11"],
    "current_segment_progress_index": 1,
    "segment_goal_generation": 5
}
```

> 中文注释：这个结构表示当前 through 段，而不是整条路线。`execution_waypoint_ids` 是本次要一次性发给 `NavigateThroughPoses` 的点序列，最后一个必须是目标 task；`passed_transit_waypoint_ids` 只记录当前段已经路过的 transit，新段建立后必须重新置空，所以 `15 -> 3` 可以重新经过 `12/11`，不会被上一段的记录全局去重掉。

段级规则：

1. `passed_transit_waypoint_ids` 是段级状态。
2. 它不是整条 route task 的全局去重。
3. 当前段结束或替换后必须清空。
4. 新段必须按 `route_waypoints[].source_index + direction` 重新收集 transit。
5. `execution_waypoint_ids` 只保存当前段尚未通过的 transit 和最终目标 task。
6. “当前位置”不写入 `execution_waypoint_ids`。

## 5. 协议口径

### 5.1 外层消息格式

```json
{
  "protocol_version": "1.0",
  "message_id": "command_xxx",
  "timestamp": 1718000000.123,
  "message_type": "command|push|response",
  "data_type": "navigation_control|navigation_status",
  "source": "app|websocket_server|data_integration",
  "destination": "websocket_server|all",
  "data": {},
  "metadata": {}
}
```

### 5.2 APP -> ROS 命令

`start_route_task` 必填字段：

1. `command_type`
2. `task_session_id`
3. `route_id`
4. `route_waypoints`

`jump_to_waypoint` 必填字段：

1. `command_type`
2. `task_session_id`
3. `target_waypoint_id`

`broadcast_finished` 必填字段：

1. `command_type`
2. `task_session_id`
3. `waypoint_id`
4. `broadcast_id`

### 5.3 业务 ack 唯一口径

系统中存在两类 ack，语义必须区分：

1. websocket 层 `command_ack` 只表示 websocket 已收包并完成基础转发。
2. route task 业务层真正的命令受理结果，统一以 `navigation_command_result` 为准。
3. `navigation_command_result` 首版统一通过 `/navigation/status` 下发。
4. 它在协议上作为独立 `event_type` 存在。
5. APP 必须以 `navigation_command_result` 作为 `start_route_task / jump_to_waypoint / broadcast_finished` 的业务 ack。
6. `navigation_command_result` 不是顶层 `data_type`，APP 应按 `data.event_type=navigation_command_result` 识别业务 ack。

示例：

```json
{
  "event_type": "navigation_command_result",
  "event_data": {
    "event_id": "event_001",
    "request_message_id": "command_001",
    "ack_type": "navigation_command_result",
    "command_type": "jump_to_waypoint",
    "task_session_id": "tour_20260611_001",
    "route_id": "route_demo_001",
    "status": "success",
    "result_reason": "",
    "error_code": "",
    "message": "jump request accepted"
  }
}
```

### 5.4 `already_current_target`

`already_current_target` 不作为 error code。

固定行为：

1. 返回 success ack。
2. ack 中带 `result_reason=already_current_target`。
3. 不取消当前 goal。
4. 不重发 goal。
5. 不修改 `active_segment`。
6. 不修改 `current_target_task_id`。

### 5.5 `navigation_busy`

首版不支持 `start_route_task` 抢占普通导航。

固定行为：

1. 若当前存在非 route task 导航正在执行，返回 `navigation_busy`。
2. 不主动取消旧普通导航。
3. 不承诺 `force_preempt` 能力。
4. 判断落在 `navigation_state_manager.py`，不放在 websocket 或桥接层。

## 6. 文件级改造清单

### 6.1 `websocket_server.py`

目标：把 APP 新协议完整扁平透传到 `/app/navigation_command`，不能再只保留旧字段。

必改函数：

1. `route_to_waypoint_manager()`

本层必须透传字段：

1. `command_type`
2. `task_session_id`
3. `route_id`
4. `route_waypoints`
5. `target_waypoint_id`
6. `interrupt_broadcast`
7. `broadcast_id`
8. `broadcast_result`
9. `broadcast_duration_sec`
10. `reason`

本层不做：

1. 不做 route task 语义校验。
2. 不判断 jump 是否合法。
3. 不计算 transit。
4. 不维护状态机。
5. `command_ack` 不替代业务层 `navigation_command_result`。

### 6.2 `dynamic_waypoints_manager.py`

目标：作为协议桥，优先把 route task 命令转发到 `/navigation/requests`，由状态机统一返回业务 ack。

必改函数：

1. `app_navigation_callback()`
2. `validate_navigation_command()`
3. `send_navigation_request()`

本层 route task 处理边界：

1. `start_route_task` 缺少 `task_session_id / route_id / route_waypoints` 时，只记录 warning，继续转发。
2. `jump_to_waypoint` 缺少 `task_session_id / target_waypoint_id` 时，只记录 warning，继续转发。
3. `broadcast_finished` 缺少 `task_session_id / waypoint_id / broadcast_id` 时，只记录 warning，继续转发。
4. route task 业务错误由 `navigation_state_manager.py` 统一返回 `navigation_command_result`。

> 中文注释：这里特意不在桥接层硬拒绝 route task 坏包，是为了 APP 侧只等待一套业务 ack。websocket 层 `command_ack` 表示已收包/已转发，真正的业务成功或失败统一看 `/navigation/status` 里的 `navigation_command_result`。

本层不做：

1. 不判断 route task 是否正在运行。
2. 不判断 target 是否是 task。
3. 不做 session 语义匹配。
4. 不判断是否 `navigation_busy`。

### 6.3 `navigation_state_manager.py`

目标：作为首版主状态机承载文件，实现 route task、jump、broadcast、through 进度和完成摘要。

新增状态字段：

1. `active_route_task`
2. `master_route_task_ids`
3. `completed_task_ids`
4. `skipped_task_ids`
5. `current_anchor_task_id`
6. `current_anchor_task_index`
7. `current_target_task_id`
8. `current_target_task_index`
9. `active_segment`
10. `awaiting_broadcast`
11. `waiting_broadcast_waypoint_id`
12. `waiting_broadcast_id`
13. `jump_interrupts_broadcast`
14. `route_task_version`
15. `active_goal_generation`
16. `last_completed_task_id`
17. `last_completed_broadcast`

命令分发入口：

1. `handle_navigation_command()` 收到 `command_type=start_route_task` 时，必须调用 `handle_start_route_task(command_data, request_data)`。
2. `handle_navigation_command()` 收到 `command_type=jump_to_waypoint` 时，必须调用 `handle_jump_to_waypoint(command_data, request_data)`。
3. `handle_navigation_command()` 收到 `command_type=broadcast_finished` 时，必须调用 `handle_broadcast_finished(command_data, request_data)`。
4. 三类 route task 命令不得落入旧普通导航 handler，也不得只在 websocket/桥接层处理后就结束。
5. 三类 route task 命令如果在 handler 内部发生未预期异常，也必须通过 `send_route_task_ack(..., status=error, error_code=internal_error)` 返回 `navigation_command_result`。
6. 未预期异常不得退回旧 `send_acknowledgment()` 作为 route task 业务 ack，否则 APP 会缺少统一 ack 口径。

> 中文注释：websocket 层和桥接层只负责透传，最终业务语义必须在状态机里收口。这里把分发入口写死，是为了防止后续重构时三类命令没有进入 route task 专属 handler，导致 APP 收不到统一的 `navigation_command_result`。

### 6.4 `handle_start_route_task()`

固定流程：

1. 校验当前是否已有 route task 运行。
2. 校验当前是否存在非 route task 普通导航。
3. 若存在普通导航，返回 `navigation_busy`，不主动抢占。
4. 使用 route task ID helper 归一化 `task_session_id / route_id / request_message_id`。
5. 使用归一化后的 `task_session_id / route_id` 做必填校验。
6. 归一化 `route_waypoints`。
7. 构建 `master_route_task_ids`。
8. 初始化 route task 运行态，且只保存归一化后的 ID。
9. 清空 `completed_task_ids`、`skipped_task_ids`、等待播报字段、`last_completed_broadcast`。
10. 按首 task 规则建立第一段 `active_segment`。
11. 通过 through goal 启动首段执行。
12. 返回 `navigation_command_result(success)`。

> 中文注释：`start_route_task` 是整条路线任务状态的源头。这里如果保存了 `"None"` 或 `"  route_demo  "` 这种未归一化 ID，后续 ack、事件、周期状态、jump 和 broadcast 校验都会继承错误。因此必填校验和 `active_route_task` 初始化都必须使用同一份归一化后的 ID。

禁止遗漏：

1. 首 task 若机器人已在附近，不能静默完成。
2. 首 task 若 `need_broadcast=true`，仍必须发 `broadcast_requested`。
3. 首 task 快速路径虽然不下发 through goal，也必须设置 `current_navigation_mode` 和 `navigation_start_time`，保证等待播报期间周期状态里的 `navigation_mode / navigation_duration` 与普通 through 路径一致。
4. 首 task 快速路径必须先返回 `navigation_command_result(success, result_reason=first_task_already_reached)`，再进入 `broadcast_requested` 或 `task_waypoint_completed` 流程，避免 APP 先收到业务事件却还没收到命令业务 ack。

> 中文注释：首 task 已在附近不是“跳过任务”，而是“无需移动即可到达首 task”。因此它仍然要进入完整 task 到达流程：需要播报就等待播报，不需要播报就完成 task 并推进下一段或完成路线。这里补齐 `navigation_start_time` 是为了让 APP 在等待播报时看到真实运行时长，而不是一直显示 0。

### 6.5 `handle_jump_to_waypoint()`

固定流程：

1. 校验 route task 正在运行。
2. 校验 `task_session_id` 匹配。
3. 校验 `target_waypoint_id` 存在。
4. 校验目标是 `task`。
5. 若目标已是当前目标，返回 success ack + `result_reason=already_current_target`，不改运行态。
6. 计算当前进度与目标之间的方向。
7. 按完整 route 区间重建 `active_segment`。
8. 更新 `skipped_task_ids`。
9. 若当前处于 `WAITING_BROADCAST` 且 `interrupt_broadcast=true`，先退出等待播报态。
10. 取消旧 goal。
11. 发布 `jump_updated`。
12. 下发新 through goal。

当前进度锚点规则：

1. jump 重建新段时，`segment_start_source_index` 必须来自当前真实进度，而不是来自旧目标 task。
2. 若当前处于 `WAITING_BROADCAST`，说明旧目标 task 已经到达，只是等待 APP 播报完成，此时新段锚点允许使用当前目标 task。
3. 若当前仍处于 through 导航途中，旧目标 task 尚未到达，不得把旧目标 task 写成 `segment_start_task_id` 或 `current_anchor_task_id`。
4. 若当前段已有 passed transit，`segment_start_source_index` 可落在最后一个 passed transit 上，但 `segment_start_task_id` 仍应表示最近已确认的业务 task 锚点。
5. jump 成功替换 `active_segment` 后，`current_anchor_task_id` 必须从新段的 `segment_start_task_id` 回填，不能简单等于跳转前的 `current_target_task_id`。

> 中文注释：这条规则用于区分“已经到 15 等播报后跳到 3”和“从 7 去 15 途中经过 11 后跳到 3”。前者可以把 15 作为锚点，后者不能把尚未到达的 15 当成锚点，否则后续再次 jump 或复盘事件会误报路线进度。

非法 jump 固定行为：

1. 不取消当前 Nav2 goal。
2. 不修改 `active_segment`。
3. 不修改 `awaiting_broadcast`。
4. 不推进或回退主任务索引。
5. 不清理当前播报等待态。

### 6.6 `handle_broadcast_finished()`

固定流程：

1. 校验当前是否处于 `WAITING_BROADCAST`。
2. 校验 `task_session_id` 匹配。
3. 校验 `waypoint_id` 匹配。
4. 校验 `broadcast_id` 匹配。
5. 匹配成功后才推进 task 完成。
6. 成功闭环后写入 `last_completed_broadcast`。
7. 若命中最近一次 `last_completed_broadcast`，可按幂等 success 处理，但不得重复推进状态机。

不允许：

1. 不匹配的 `broadcast_finished` 推进状态机。
2. 重复 `broadcast_finished` 重复发 `task_waypoint_completed`。

### 6.7 `rebuild_segment_from_current_progress()`

本函数必须基于完整 route 区间重算，不能只看旧 `active_segment` 剩余点。

固定算法：

1. 根据当前 through 进度解析 `progress_source_index`。
2. 根据新目标解析 `target_source_index`。
3. 根据二者关系计算 `direction`。
4. 在完整 `route_waypoints` 中按方向收集 `progress_source_index -> target_source_index` 区间内的 transit。
5. 只扣除当前 `active_segment` 内已经 passed 的 transit，不做全局去重。
6. 中间 task 写入 `skipped_task_ids`，并去重。
7. 已在 `completed_task_ids` 中的 task 不得再写入 skipped。
8. 生成 `execution_waypoint_ids = remaining_transit + [target_task_id]`。

不变量：

1. 新目标跨出旧 `active_segment` 原区间时，也不得漏收新区间中的 transit。
2. 不得只依赖“旧段剩余 transit + 新目标 task”的简化算法。
3. 不得创建“当前位置”虚拟 waypoint。

建议伪代码：

```python
def rebuild_segment_from_current_progress(target_task_id):
    progress_index = resolve_current_progress_source_index()
    target_index = get_source_index(target_task_id)
    direction = compute_direction(progress_index, target_index)

    candidate_transit = collect_transit_between_source_indices(
        progress_index,
        target_index,
        direction,
    )

    remaining_transit = [
        wid for wid in candidate_transit
        if wid not in active_segment.passed_transit_waypoint_ids
    ]

    skipped_tasks = collect_skipped_tasks_between_source_indices(
        progress_index,
        target_index,
        direction,
    )

    return build_active_segment_from_execution_ids(
        remaining_transit + [target_task_id],
        skipped_tasks=skipped_tasks,
        direction=direction,
    )
```

> 中文注释：这段伪代码的核心不是“从旧段里删几个点”，而是每次 jump 都回到完整 `route_waypoints[]`，按当前真实进度和新目标重新计算区间。这样可以保证正向跳、反向跳、跨出旧 active segment 的跳都不会漏掉中间 transit，也不会把尚未到达的旧目标 task 误当成新的锚点。

### 6.8 `start_active_segment_navigation()`

首版必须接入 `NavigateThroughPoses` 或等价 through action，不把逐点 `NavigateToPose` 串行发送作为 route task 主路径。

接入清单：

1. 新增导入 `NavigateThroughPoses`。
2. 新增 `ActionClient(self, NavigateThroughPoses, 'navigate_through_poses')`。
3. `start_active_segment_navigation()` 使用 `NavigateThroughPoses.Goal()`。
4. `goal_msg.poses` 由 `active_segment.execution_waypoint_ids` 顺序转换得到。
5. transit 与最终 target task 一起作为 `poses` 发给 Nav2。
6. 最后一个 pose 必须对应 `segment_target_task_id`。
7. 新增 through 专用 feedback callback。
8. 新增 through 专用 result callback。
9. through feedback/result 必须绑定 `active_goal_generation + route_task_version`。
10. 旧 `NavigateToPose` 仅保留给旧单点导航，不作为 route task 主路径。
11. route task 专用 `PoseStamped` 转换必须直接使用 `normalize_route_task_waypoints()` 产出的 `frame_id / position / orientation`。
12. route task 专用 `PoseStamped` 转换不得复用旧普通导航 `waypoint_to_pose_stamped()` 的默认字段填充逻辑。
13. `reset_route_task_state()` 必须把 `current_route_task_goal_generation` 置为 `-1`，并清零 `active_goal_generation`，保证失败或完成后晚到的 through 回调不能重新写入旧 goal handle。

> 中文注释：普通导航点位可能允许缺字段时填默认值，但 route task 已经在 `start_route_task` 阶段完成 pose 校验。through goal 构造时必须使用这份归一化结果，否则旧默认逻辑可能绕过清单约束，例如把缺失 orientation 静默改成默认四元数。

段启动失败清理规则：

1. `start_route_task` 首段启动失败时，必须先返回 `navigation_command_result(error)`，再清理 route task 专属状态和导航大状态。
2. 首段启动失败清理必须清空 `current_goal_handle / route_task_goal_handle / route_task_last_feedback_time`。
3. 首段启动失败清理必须让旧 through 回调失效，避免晚到回调推进已失败的路线任务。
4. 命令触发的 `send_goal_async()` 或 goal response callback 注册阶段抛异常时，必须先返回 `navigation_command_result(error, error_code=send_goal_failed)`，再进入 `handle_route_task_navigation_failed()` 发布失败复盘。
5. 自动下一段触发的 `send_goal_async()` 或 goal response callback 注册阶段抛异常时，不得伪造新的命令 ack，只进入 `handle_route_task_navigation_failed()`。
6. goal response rejected 时，必须进入 `handle_route_task_navigation_failed()`。
7. goal response future 异常时，必须进入 `handle_route_task_navigation_failed()`。
8. 自动下一段启动失败时，不得伪造新的命令 ack。
9. 自动下一段启动失败必须进入 `handle_route_task_navigation_failed()`，发布带 route task 上下文的 `navigation_failed`。

> 中文注释：段启动失败分三类。第一类是 APP 刚发 `start_route_task`，首段还没真正跑起来，此时 APP 需要业务错误 ack，ROS 也要把刚创建的运行态清干净；第二类是 through goal 已准备发送，但发送或 goal response 注册阶段失败，若这是 `start_route_task / jump_to_waypoint` 直接触发的动作，APP 仍然需要本次命令的 `navigation_command_result(error)`，随后再看 `navigation_failed` 做失败复盘；第三类是任务执行中自动推进下一段失败，此时没有新的 APP 命令，不能凭空补一个旧命令 ack，而应发布 `navigation_failed` 供 APP 展示失败复盘。无论哪一类失败，只要执行 route task reset，就必须让当前 through generation 失效，防止旧 goal response 晚到后重新写入旧 goal handle。

```bash

ros2 action info /navigate_through_poses
```

### 6.9 `data_integration_node_recoverable.py`

目标：确保新增事件第一时间推给 APP，避免播报和 through 联调被推送节流卡住。

必改函数：

1. `should_push_navigation_status_immediately()`
2. `publish_navigation_status_event()`

立即推送白名单必须包含：

1. `navigation_command_result`
2. `broadcast_requested`
3. `waypoint_passed`
4. `jump_updated`
5. `task_waypoint_completed`
6. `route_task_completed`
7. `navigation_failed`

> 中文注释：`navigation_failed` 虽然不是 route task 专属新事件名，但 route task 失败沿用这个通道，并通过 `route_task=true` 携带路线任务上下文。它必须立即推送，否则 APP 可能在 through 失败后仍停留在执行中，直到下一次周期状态刷新才感知失败。

数据集成层处理规则：

1. `navigation_status_callback()` 必须从 `/navigation/status` 原始 payload 中读取 `event_type`。
2. 若 `event_type` 命中立即推送白名单，必须调用 `publish_navigation_status_event(enhanced_status)`。
3. 立即推送应使用增强后的 `enhanced_status`，保留原始 route task 事件字段，同时补充当前 pose、path、速度和性能指标。
4. route task 离散事件不得只依赖周期状态推送，否则 APP 播报、跳点和完成 UI 会有明显延迟。
5. `maybe_publish_navigation_exception()` 处理 `navigation_failed` 时，必须先解包 `event_data`，再读取 `route_task / failure_code / route_id / current_target_task_id`。
6. 若只从顶层 `status_data` 读取 route task 字段，数据集成层会把路线任务失败误判成普通导航失败，导致 APP 异常标题、错误码和详情文案不准确。
7. route task 失败只通过 `/navigation/status` 的 `navigation_failed` 事件通知 APP，不得再额外发布旧 `/navigation/acknowledgments`。
8. 旧 `/navigation/acknowledgments` 兼容链路只服务旧普通导航 ack，不作为 route task 失败或异步事件的第二条推送通道。

> 中文注释：状态机负责发布事件，数据集成层负责把白名单事件实时推给 APP。这里锁住的是“从 `/navigation/status` 到 APP push”的最后一跳，避免 ROS 已经发事件但 APP 只能等周期状态刷新的问题。`navigation_failed` 比较特殊：外层只有 `event_type` 和状态包装字段，真正的 route task 失败上下文在 `event_data` 内，因此系统异常展示也必须读 `event_data`。同时要避免“双通道推送”：同一次 route task 失败不能既发 `navigation_failed`，又通过旧 ack 链路包装成 `navigation_command_result(command_type=navigation_failed)`。

## 7. 状态机流转

主状态口径：

1. 首版不新增 `NavigationState` 枚举值。
2. `NavigationState.IDLE` 仍表示没有 active route task。
3. `NavigationState.EXECUTING` 仍表示机器人正在执行导航动作。
4. route task 的细分阶段统一放在 `current_detailed_state`。
5. 这样做的目的，是不破坏旧单点、多点、展厅导航对 `NavigationState` 的既有判断。

route task 子状态：

1. `ROUTE_TASK_SEGMENT_NAVIGATING`：当前段已经通过 `NavigateThroughPoses` 下发，机器人正在从当前锚点/进度位置前往目标 task，途中 transit 只发 `waypoint_passed`，不推进主任务完成集合。
2. `WAITING_BROADCAST`：目标 task 已经到达，但该 task 需要 APP/播报系统完成播报确认；此时允许 `broadcast_finished` 完成当前 task，也允许 `jump_to_waypoint` 在 `interrupt_broadcast=true` 时打断等待。
3. `JUMP_REPLANNING`：已经收到合法 jump，请求正在取消旧 through goal、重建当前段并切换到新目标 task；该状态是短暂过渡状态，下一步应进入 `ROUTE_TASK_SEGMENT_NAVIGATING`。
4. `ROUTE_TASK_FIRST_TASK_ALREADY_REACHED`：首个 task 在启动时已经满足到达阈值，首版不再额外绕行，而是进入首 task 到达后的播报/完成流程。
5. `IDLE`：route task 已完成、失败后清理，或系统当前没有 active route task。

> 中文注释：这里的“子状态”不是新增 ROS 主状态枚举，而是写入 `current_detailed_state` 的字符串。APP 如果只关心大类，可以继续看 `current_state`；如果要展示 route task 细分进度，再看 `current_detailed_state` 和 route task 事件。

对外 `navigation_mode` 发布口径：

1. 首版不新增 `NavigationMode` 枚举值，避免破坏旧普通导航逻辑。
2. 但只要 ROS 内部存在 `active_route_task`，对 APP 发布的状态流和事件流必须使用 `navigation_mode=route_task`。
3. 非 route task 场景继续发布旧值：`single_point`、`multi_point`、`exhibition_tour` 或 `null`。
4. 状态机实现应通过统一 helper 生成对外 `navigation_mode`，不要在各个 payload 里直接读取 `current_navigation_mode.value`。

> 中文注释：route task 内部会复用 Nav2 through 和部分旧多点导航字段，但 APP 侧不能把它当普通 `multi_point`。统一发布 `route_task` 可以让 APP 正确分流路线任务 UI、业务 ack 和播报闭环事件。

周期状态 `route_task` 摘要：

1. 当 `active_route_task` 存在时，周期状态摘要必须额外带 `route_task` 对象。
2. `route_task.task_session_id / route_id` 用于 APP 关联当前路线任务。
3. `route_task.current_anchor_task_id / current_target_task_id` 用于展示当前从哪里到哪里。
4. `route_task.master_route_task_ids / completed_task_ids / skipped_task_ids` 用于展示主任务整体进度。
5. `route_task.awaiting_broadcast / waiting_broadcast_waypoint_id / waiting_broadcast_id` 用于展示是否正在等待 APP 播报完成回执。
6. `route_task.active_segment` 用于展示当前 through 段，包括 `segment_id`、方向、执行点、已通过 transit。
7. `route_task.last_feedback_age_sec` 用于联调观察 Nav2 through feedback 是否长期静默。
8. 所有列表字段必须是发布时刻快照，不得直接引用内部运行态列表。

> 中文注释：离散事件告诉 APP “刚刚发生了什么”，周期状态告诉 APP “现在处在哪”。这两个通道都要有 route task 上下文，联调时才能看清楚是不是卡在 through、卡在播报、还是已经失败清理。

启动流转：

```text
IDLE
-> start_route_task 校验 route_id/task_session_id/route_waypoints
-> build first active_segment
-> if first task already reached:
     current_detailed_state = ROUTE_TASK_FIRST_TASK_ALREADY_REACHED
     navigation_start_time = now
     broadcast_requested or task_waypoint_completed
   else:
     current_state = EXECUTING
     current_detailed_state = ROUTE_TASK_SEGMENT_NAVIGATING
```

正常段流转：

```text
ROUTE_TASK_SEGMENT_NAVIGATING
-> transit passed ...
-> target task reached
-> if need_broadcast:
     current_detailed_state = WAITING_BROADCAST
   else:
     task_waypoint_completed
     next segment or route_task_completed event
```

jump 流转：

```text
ROUTE_TASK_SEGMENT_NAVIGATING / WAITING_BROADCAST
-> validate jump
-> current_detailed_state = JUMP_REPLANNING
-> cancel old goal
-> rebuild active_segment
-> current_detailed_state = ROUTE_TASK_SEGMENT_NAVIGATING
```

优先使用 `NavigateThroughPoses` feedback。

6. APP 联调检查：

```text
start_route_task 正常启动 -> waypoint_passed -> broadcast_requested -> broadcast_finished -> task_waypoint_completed -> route_task_completed
jump_to_waypoint 正向/反向/等待播报中跳点 -> jump_updated -> 新 through 段继续执行
异常场景 -> navigation_command_result(error) 或 navigation_failed(route_task=true)
```

> 中文注释：APP 联调用来验证协议是否真的被消费正确。本地静态检查只能保证字段和事件在源码中存在，不能证明 APP 会按预期更新 UI、播报、进度条、错误提示或去重逻辑。联调时要重点确认 `passed_transit_waypoint_ids` 只作用于当前段，`15 -> 3` 这类反向跳可以重新经过 `12 / 11`，以及完成事件里的摘要字段能支撑 APP 复盘展示。

若 feedback 不足，fallback 为 pose + 阈值：

1. 获取当前 pose。
2. 计算到当前待通过 transit 的距离或投影关系。
3. 达到阈值后标记 passed。
4. 推进 `current_segment_progress_index`。
5. 发布 `waypoint_passed`。

固定口径：

1. through progress 只推进 transit passed。
2. task 完成由目标 task 到达逻辑负责。
3. 同一段同一 transit 只发一次 `waypoint_passed`。
4. 新段可重新发同一 transit 的 `waypoint_passed`。
5. goal response、feedback、result 三类 through 回调都必须同时检查 `route_task_version` 和 `active_goal_generation`。
6. through feedback 和 pose fallback 都只能调用 transit passed 标记逻辑，不得直接调用 task 到达或 task 完成逻辑。
7. through result 一旦进入成功、取消或失败终态，必须清理当前 route task goal handle。
8. result 成功进入 `WAITING_BROADCAST` 后，不应再保留已结束 through goal，否则后续 jump 可能误取消旧 goal。
9. route task 失败、完成或首段启动失败清理后，必须让 `current_route_task_goal_generation=-1`，否则旧 goal response 晚到时可能重新通过 generation 校验。

> 中文注释：第 5 条用来拦住旧 goal 的晚到回调；第 6 条用来保证“through 进度”和“业务 task 完成”分层。transit 只是路过进度，最终 task 是否完成必须由 through result success 之后的目标 task 到达流程决定。第 7、8 条用于保持 WAITING_BROADCAST 阶段状态干净：机器人已经到达目标 task，等待的是 APP 播报回执，不应再把已结束的 through goal 当成活动 goal。第 9 条用于覆盖失败/reset 场景：如果 reset 后 generation 还保留旧值，旧 goal response 仍可能晚到并通过校验。

## 9. 首 task 处理规则

1. route task 启动后，第一个 `task` 默认也是业务目标。
2. 若机器人不在首 task 附近，先导航到首 task。
3. 若机器人已经在首 task 附近，仍进入该点完成判定流程。
4. 若首 task `need_broadcast=true`，仍要发 `broadcast_requested`，收到 `broadcast_finished` 后才算完成。
5. 若首 task `need_broadcast=false`，可直接完成并进入下一段。
6. APP 不应因为机器人刚好在首 task 附近就直接显示“已完成”。

## 10. ROS -> APP 事件

### 10.1 `navigation_command_result`

业务 ack 事件，必须立即推送。

```json
{
  "event_type": "navigation_command_result",
  "event_data": {
    "event_id": "event_001",
    "request_message_id": "command_001",
    "ack_type": "navigation_command_result",
    "command_type": "jump_to_waypoint",
    "task_session_id": "tour_20260611_001",
    "route_id": "route_demo_001",
    "status": "success",
    "result_reason": "",
    "error_code": "",
    "message": "jump request accepted"
  }
}
```

### 10.2 `broadcast_requested`

触发时机：

1. 到达目标 task。
2. 首版不新增独立停车/对齐动作，以 Nav2 through 到达目标 task 后的状态为准。
3. `need_broadcast=true`。

> 中文注释：这里不要再理解为“必须先执行一个额外的 stop_and_align 行为再播报”。`stop_and_align` 字段当前只做归一化保存，首版实际触发点是 `NavigateThroughPoses` 成功到达目标 task。

APP 动作：

1. 进入等待播报/正在播报状态。
2. 根据 `broadcast_id` 启动播报。
3. 播报完成后发送 `broadcast_finished`。

完整 JSON 示例：

```json
{
  "event_type": "broadcast_requested",
  "event_data": {
    "event_id": "route_task_tour_20260611_001_broadcast_requested_12_1760000000000",

  }
}
```

### 10.3 `waypoint_passed`

触发口径：

1. ROS 内部确认当前段已通过该 transit。
2. 同一段内每个 transit 只触发一次。
3. 新段若再次包含该 transit，可再次触发。

APP 动作：

1. 更新 through 进度。
2. 不播报。
3. 不回命令。

完整 JSON 示例：

```json
{
```

1. jump 校验通过。
2. 新 `active_segment` 已重建。

APP 动作：

1. 更新当前目标 task。
2. 更新当前段 transit 列表。
3. 清理旧目标高亮。

触发时机：

2. 需播报 task 完成 `broadcast_finished` 闭环后。

7. `route_task_already_running`

`jump_to_waypoint`:

1. `invalid_task_session`
2. `route_task_not_running`
3. `invalid_target_waypoint`
4. `target_waypoint_not_task`
5. `interrupt_broadcast_false_not_supported`

`broadcast_finished`:

1. `route_task_not_running`
2. `broadcast_not_waiting`
3. `broadcast_context_mismatch`
4. `invalid_task_session`
5. `unsupported_broadcast_result`

旧普通导航命令在 route task 运行期间：

1. `route_task_active`
2. 该错误最终也会通过数据集成层包装为 `navigation_command_result` 推给 APP。
3. APP 可用 `event_data.command_type` 判断原始旧命令类型，用 `event_data.error_code=route_task_active` 判断被 route task 拦截。

2. `duplicate_broadcast_finished` 不是错误码。

### 11.1 APP 展示文案建议

`start_route_task` 错误码：

1. `missing_task_session_id`：路线任务缺少会话 ID，请重新发起任务。
2. `missing_route_id`：路线任务缺少路线 ID，请重新选择路线后再开始。
3. `invalid_route_waypoints`：路线点数据不完整，请刷新路线后重试。
4. `missing_task_waypoints`：路线中没有任务点，请重新配置路线。
5. `invalid_waypoint_role`：路线点角色配置异常，请检查 task/transit 设置。
6. `missing_waypoint_pose`：路线点缺少位姿信息，无法导航。
7. `route_task_already_running`：当前已有路线任务正在执行，请先完成当前任务。
8. `navigation_busy`：机器人正在执行其他导航，请稍后再开始路线任务。

`jump_to_waypoint` 错误码：

1. `invalid_task_session`：路线任务会话不匹配，请刷新任务状态。
2. `route_task_not_running`：当前没有正在执行的路线任务。
3. `invalid_target_waypoint`：目标任务点不存在，请重新选择目标点。
4. `target_waypoint_not_task`：只能跳转到任务点，不能跳转到途经点。
5. `interrupt_broadcast_false_not_supported`：当前版本跳转必须打断播报，请稍后重试或允许打断播报。

`broadcast_finished` 错误码：

1. `route_task_not_running`：当前没有正在执行的路线任务。
2. `broadcast_not_waiting`：当前没有等待完成的播报。
3. `broadcast_context_mismatch`：播报回执与当前任务点不匹配，请刷新任务状态。
4. `invalid_task_session`：路线任务会话不匹配，请刷新任务状态。
5. `unsupported_broadcast_result`：当前版本只支持 completed 播报结果。

旧普通导航命令错误码：

1. `route_task_active`：路线任务正在执行，当前版本不支持用普通导航命令控制路线任务。
2. `unknown_navigation_command`：导航命令类型不支持，请升级 APP 或检查 command_type。
3. `internal_error`：导航命令处理异常，请稍后重试或联系现场工程师查看日志。
4. `unknown_request_type`：导航请求类型不支持，请检查 APP data_type 或升级 APP。
5. `invalid_request_payload`：导航请求格式异常，请检查 APP 下发的数据结构。
6. `waypoint_not_found`：目标点位不存在，请刷新点位列表后重试。
7. `empty_waypoint_list`：点位列表为空，请至少选择一个点位后再开始导航。
8. `empty_exhibition_points`：没有可用的展台点位，请先配置展台点位。

`navigation_failed` 中 `route_task=true` 的展示建议：

1. 标题：路线任务导航失败。
2. 文案：路线任务在目标点 `{current_target_task_id}` 导航失败，请检查路线、定位或现场障碍物。
3. 若带 `failure_code`，APP 可用于区分失败类型并展示更具体的排障建议。
4. 若带 `route_id`，APP 可在详情中展示路线 ID。
5. 若带 `segment_id / segment_direction / execution_waypoint_ids`，APP 可在详情中展示失败段。
6. 若带 `completed_task_ids / skipped_task_ids`，APP 可展示失败前已完成和已跳过的任务点。

首版 `failure_code` 建议文案：

1. `send_goal_failed`：路线任务发送导航目标失败，请检查导航服务状态。
2. `goal_rejected`：导航服务拒绝了路线任务目标，请检查目标点或导航配置。
3. `goal_response_error`：导航服务响应异常，请稍后重试。
4. `feedback_timeout`：导航长时间没有进度反馈，请检查机器人定位、网络或现场障碍物。
5. `goal_canceled`：路线任务导航被取消。
6. `goal_failed`：路线任务导航执行失败，请检查路线或现场环境。
7. `result_error`：导航结果解析异常，请查看日志。
8. `target_task_missing`：目标任务点丢失，请刷新路线任务状态。
9. `next_segment_build_failed`：下一段路线构建失败，请检查路线点顺序和任务点配置。
10. `next_segment_start_failed`：下一段导航启动失败，请检查导航服务和路线点位姿。
11. `jump_segment_start_failed`：跳转后的导航段启动失败，请检查目标任务点和途经点配置。

> 中文注释：`failure_code` 是机器可读分类，`reason` 是人可读描述。APP 弹窗可以优先用 `failure_code` 选择文案，再把 `reason / route_id / current_target_task_id / segment_id` 放到详情里，避免只显示一段不可分类的英文错误。

success `result_reason`：

1. `already_current_target`：目标点已经是当前任务点，无需重复跳转。
2. `duplicate_broadcast_finished`：播报完成回执已处理，本次重复回执已忽略。
3. `first_task_already_reached`：机器人已在首个任务点附近，已直接进入任务流程。

## 12. 协议字段字典

### 12.1 字段处理总原则

1. websocket 层只负责透传字段，不判断路线语义。
2. `dynamic_waypoints_manager.py` 对 route task 只做日志提示和 ID 字符串化，不硬拒绝缺字段；业务错误统一交给状态机返回 `navigation_command_result`。
3. `navigation_state_manager.py` 负责最终语义校验、默认值归一化、错误码返回和事件发布。
4. 所有业务 ID 在 ROS 内部统一按字符串处理，避免数字 `15` 和字符串 `"15"` 比较不相等。
5. 状态机内 route task 业务 ID 必须通过统一 helper 归一化：`None` 转为空字符串，其它值执行 `str(value).strip()`。
6. 不得直接使用 `str(value)` 处理可为空的 ID，因为 `None` 会变成伪 ID `"None"`。
7. 不得直接使用 `value or ""` 处理 ID，因为数字 `0` 会被误当成缺失值。

> 中文注释：这一节是实现时的字段字典，不是给 APP 随意扩展字段的入口。若新增字段，必须同时补 websocket 透传、桥接层校验/归一化、状态机处理、事件示例和错误码文案。

> 中文注释：ID 归一化的目标是让 APP、websocket、桥接层和状态机对同一个业务对象有一致比较结果。例如 `15`、`"15"`、`" 15 "` 都应对齐为 `"15"`；但 `None` 不是合法业务 ID，不能变成字符串 `"None"` 继续参与 session 或 waypoint 匹配。

### 12.2 APP -> ROS 命令字段

`command_type`:

1. 来源：APP 下发 `payload.command_type`。
2. 默认值：无。
3. 缺失处理：websocket 层无法识别内层命令时拒绝；进入桥接层后的 route task 命令尽量转发给状态机返回业务 ack。
4. 允许值：首版新增 `start_route_task | jump_to_waypoint | broadcast_finished`。

`request_message_id`:

1. 来源：APP 外层 `message_id`，websocket 层写入导航控制消息。
2. 默认值：空字符串。
3. websocket 处理：若 APP 内层 `request_message_id` 缺失、为 `None` 或空字符串，回退使用外层 `message_id`。
4. 状态机处理：允许缺失，使用 route task ID 归一化 helper；不会把 `None` 转成字符串 `"None"`，缺失时写空字符串并记录日志。
5. 缺失影响：APP 无法用该字段反查原始按钮操作。
6. APP 用途：关联 `navigation_command_result` 和原始命令。

`task_session_id`:

1. 来源：APP 创建一次 route task 会话时生成。
2. 默认值：无。
3. 缺失处理：进入桥接层后继续转发给状态机；`start_route_task` 返回 `missing_task_session_id`，`jump_to_waypoint / broadcast_finished` 由状态机返回 `invalid_task_session` 或 `route_task_not_running` 等业务错误。
4. ROS 用途：所有 ack、事件、完成摘要的会话主键。
5. 状态机处理：使用 route task ID 归一化 helper；`None` 归一化为空字符串，首尾空格会被移除。

`route_id`:

1. 来源：APP 当前选择的路线 ID。
2. 默认值：无。
3. 缺失处理：`start_route_task` 返回 `missing_route_id`。
4. ROS 用途：写入 `active_route_task`，后续事件由 `publish_route_task_event()` 自动补齐。
5. 状态机处理：业务 ack 中使用 route task ID 归一化 helper，避免输出 `"None"` 伪 ID。

`route_waypoints`:

1. 来源：APP 一次性下发完整路线数组。
2. 默认值：空数组。
3. 缺失处理：进入桥接层后继续转发给状态机；状态机返回 `invalid_route_waypoints` 或 `missing_task_waypoints`。
4. ROS 用途：数组顺序就是路线执行和 jump 区间重算的唯一顺序依据。

`target_waypoint_id`:

1. 来源：APP 在 `jump_to_waypoint` 中指定的目标 task ID。
2. 默认值：无。
3. 缺失处理：进入桥接层后继续转发给状态机；状态机找不到目标并返回 `invalid_target_waypoint`。
4. 语义限制：目标必须是当前 route 内的 `task`，不能是 `transit`。
5. 状态机处理：使用 route task ID 归一化 helper；`" 15 "` 会按 `"15"` 查找，`None` 会变成空字符串并走 `invalid_target_waypoint`。

`interrupt_broadcast`:

1. 来源：APP 在 `jump_to_waypoint` 中显式传入。
2. 默认值：`route_task.default_interrupt_broadcast` 参数；websocket 层当前透传默认值为 `true`。
3. 缺失处理：状态机按默认值处理。
4. 类型处理：状态机使用 `route_task_bool()` 解析，支持 JSON boolean 和 `"true" / "false" / "1" / "0"` 字符串。
5. 失败处理：等待播报时若解析结果为 false，返回 `interrupt_broadcast_false_not_supported`。

`waypoint_id`:

1. 来源：APP 在 `broadcast_finished` 中回传当前播报完成的 task ID。
2. 默认值：无。
3. 缺失处理：进入桥接层后继续转发给状态机；状态机按上下文不匹配返回 `broadcast_context_mismatch`。
4. ROS 用途：必须等于 `waiting_broadcast_waypoint_id`。
5. 状态机处理：使用 route task ID 归一化 helper，避免 `None` 变成 `"None"` 后参与播报上下文匹配。

`broadcast_id`:

1. 来源：task waypoint 的播报配置，APP 在 `broadcast_finished` 中原样回传。
2. 默认值：空字符串。
3. 缺失处理：进入桥接层后继续转发给状态机；状态机按上下文不匹配返回 `broadcast_context_mismatch`。
4. ROS 用途：必须等于 `waiting_broadcast_id`，并用于重复回执幂等判断。
5. 状态机处理：使用 route task ID 归一化 helper，确保 `" broadcast_7 "` 能与等待上下文 `"broadcast_7"` 对齐。

`broadcast_result`:

1. 来源：APP 播报完成回执。
2. 默认值：`completed`。
3. 缺失处理：字段缺失或值为 `null` 时，状态机按 `completed` 处理。
4. 允许值：首版只接受 `completed`。
5. 归一化：状态机必须先转字符串，再执行 `strip().lower()`；例如 `"Completed"`、`" completed "` 归一化后都按 `completed` 处理。
6. 空字符串处理：APP 显式传入 `""` 不等同于缺失字段，归一化后仍应返回 `unsupported_broadcast_result`。
7. 失败处理：传入 `failed / cancelled / ""` 等其它值时返回 `unsupported_broadcast_result`。

> 中文注释：`broadcast_result` 是 APP 播报模块回传的结果字段，不参与路线顺序计算，只决定当前等待播报的 task 是否可以闭环完成。首版只支持完成态，但要容忍大小写和首尾空格差异；同时要区分“字段缺失”和“APP 明确传了空结果”，后者不能被误闭环。真正的失败/取消播报流程后续需要单独设计，不应在首版里伪装成完成。

### 12.3 `route_waypoints[]`

`waypoint_id`:

1. 类型：`string`
2. 必填：是
3. 来源：APP 路线点数据。
4. 默认值：无。
5. 缺失处理：进入桥接层后继续转发给状态机；状态机返回 `invalid_route_waypoints`。
6. 示例：`"15"`
7. 状态机处理：使用 route task ID 归一化 helper；数字 `15`、字符串 `"15"`、`" 15 "` 均保存为 `"15"`，`None` 或空字符串返回 `invalid_route_waypoints`。

> 中文注释：`route_waypoints[].waypoint_id` 是后续 jump 查找、through 段构建、transit passed 和完成事件的主键。它必须在路线任务启动时就归一化干净，否则后续命令里的 `target_waypoint_id="15"` 可能无法匹配路线数组里的 `" 15 "`。

`waypoint_role`:

1. 类型：`string`
2. 必填：是
3. 来源：优先读取 `route_waypoints[].waypoint_role`，缺失时读取 `route_waypoints[].properties.waypoint_role`。
4. 默认值：无。
5. 缺失处理：状态机返回 `invalid_waypoint_role`。
6. 允许值：`task | transit`
7. 归一化：状态机必须先转字符串，再执行 `strip().lower()`。
8. 示例：`"Task"`、`" task "` 应归一化为 `task`；归一化后仍不是 `task | transit` 时返回 `invalid_waypoint_role`。

`need_broadcast`:

1. 类型：`boolean`
2. 必填：否
3. 来源：优先读取显式字段，缺失时读取 `properties.need_broadcast`。
4. 默认值：`false`
5. 缺失处理：按 `false` 处理。
6. 仅 task 有意义，transit 强制 `false`。

`broadcast_id`:

1. 类型：`string`
2. 必填：当 `need_broadcast=true` 时必填。
3. 来源：优先读取显式字段，缺失时读取 `properties.broadcast_id`。
4. 默认值：空字符串。
5. 缺失处理：首版状态机不在归一化阶段强拒绝空播报 ID，但等待播报闭环时会以空字符串作为匹配值；APP 应避免 `need_broadcast=true` 且 `broadcast_id` 为空。
6. 状态机处理：使用 route task ID 归一化 helper；`" broadcast_7 "` 会保存为 `"broadcast_7"`，`None` 保存为空字符串。

> 中文注释：`broadcast_id` 是 `broadcast_requested` 和 `broadcast_finished` 闭环匹配字段。它可以为空以兼容首版历史数据，但如果有值必须先归一化，避免 APP 播报完成回执里的 `"broadcast_7"` 和路线点里的 `" broadcast_7 "` 对不上。

`broadcast_blocking`:

1. 类型：`boolean`
2. 必填：否。
3. 来源：优先读取显式字段，缺失时读取 `properties.broadcast_blocking`。
4. 默认值：task 为 `true`，transit 强制 `false`。
5. 缺失处理：task 按 `true` 保存。
6. 首版行为：字段只归一化保存，实际播报流程统一按阻塞闭环处理。

`stop_and_align`:

1. 类型：`boolean`
2. 必填：否。
3. 来源：优先读取显式字段，缺失时读取 `properties.stop_and_align`。
4. 默认值：task 为 `true`，transit 强制 `false`。
5. 缺失处理：task 按 `true` 保存。
6. 首版行为：字段只归一化保存，不新增独立停车/对齐动作。

`frame_id`:

1. 类型：`string`
2. 必填：否。
3. 来源：优先读取显式字段，缺失时读取 `properties.frame_id`。
4. 默认值：节点 `default_frame_id` 参数，当前默认为 `map`。
5. 缺失处理：字段缺失、`null` 或空字符串时，状态机保存默认 frame。
6. 状态机处理：使用 route task ID 归一化 helper 去首尾空格。

> 中文注释：`frame_id` 决定 route waypoint 转成 `PoseStamped` 后挂在哪个坐标系下。缺失时可以使用节点默认 frame，但不能把 `None` 或空字符串直接写进 PoseStamped header，否则 Nav2 goal 头部语义不完整。

`position`:

1. 类型：`array<number>`
2. 来源：APP 路线点位姿。
3. 默认值：无。
4. 缺失处理：`start_route_task` 归一化阶段返回 `missing_waypoint_pose`。
5. 示例：`[1.0, 2.0, 0.0]`
6. 归一化：状态机必须转换为三元素 `[x, y, z]` 浮点数组；若只提供 `[x, y]`，`z` 可按 `0.0` 补齐。
7. 失败处理：非数组、长度不足、无法转数字或出现 `NaN/Inf` 时，返回 `missing_waypoint_pose`。

> 中文注释：`position` 是 through goal 的核心位置信息。坏值如果拖到 `NavigateThroughPoses` 下发前才暴露，APP 已经收到 start 成功或状态机已进入执行态，排查成本会更高；因此首版在路线启动归一化阶段就拦截明显坏值。

`orientation`:

1. 类型：`array<number>`
2. 首版统一四元数。
3. 来源：APP 路线点位姿。
4. 默认值：无。
5. 缺失处理：`start_route_task` 归一化阶段返回 `missing_waypoint_pose`。
6. 示例：`[0.0, 0.0, 0.0, 1.0]`
7. 不允许同一字段有时传四元数、有时传 yaw。
8. 若 APP 只有 yaw，要么 APP 先转四元数后下发，要么双方另约定显式 `yaw` 字段由 ROS 归一化。
9. 归一化：状态机必须转换为四元素 `[x, y, z, w]` 浮点数组。
10. 失败处理：字段缺失、长度不足、无法转数字或出现 `NaN/Inf` 时，返回 `missing_waypoint_pose`。

> 中文注释：`orientation` 不允许静默默认成 `[0, 0, 0, 1]`，因为这会在 APP 缺朝向数据时悄悄改变机器人到点后的朝向。首版要求 APP 明确下发四元数，后续如需 yaw 兼容，应新增显式字段和归一化规则，而不是复用 orientation 混传。

### 12.4 ROS -> APP ack 字段

`status`:

1. 类型：`string`
2. 来源：状态机业务处理结果。
3. 默认值：无。
4. 缺失处理：不允许缺失。
5. 允许值：`success | error`

`error_code`:

1. 类型：`string`
2. 来源：状态机错误分支。
3. 默认值：空字符串。
4. 缺失处理：`status=success` 时允许为空；`status=error` 时必须带具体错误码。

`result_reason`:

1. 类型：`string`
2. 来源：状态机 success 分支中的补充原因。
3. 默认值：空字符串。
4. 缺失处理：普通 success 可为空。
5. 示例：`already_current_target`

## 13. 状态字段生命周期

`active_route_task`:

1. 创建：`handle_start_route_task()` 成功受理后。
2. 清空：`complete_route_task()` 最后阶段。
3. 非法 jump 不得清空。

`completed_task_ids`:

1. 创建：route task 启动时置空。
2. 更新：`finalize_task_waypoint_completion()`。
3. transit 不得写入。

`skipped_task_ids`:

1. 创建：route task 启动时置空。
2. 更新：合法 jump 时写入中间被跨过的 task。
3. 去重保存。
4. 已 completed 的 task 不得写入。

`active_segment`:

1. 创建：首段、task 完成后的下一段、合法 jump 重建段。
2. 更新：through feedback 仅更新其进度字段。
3. 非法 jump 和旧 goal callback 不得改写。

`passed_transit_waypoint_ids`:

1. 创建：新段建立时置空。
2. 更新：through feedback 或 fallback pose 判定。
3. 清空：段替换时必须清空。
4. 只作用于当前段。

`awaiting_broadcast`:

1. 创建：到达需要播报的 task 后置为 `true`。
2. 清空：合法 `broadcast_finished` 或合法打断 jump。
3. 非法 jump 不得清空。

`last_completed_broadcast`:

1. 创建：route task 启动时置空。
2. 更新：成功处理 `broadcast_finished` 后写入。
3. 使用：收到重复 `broadcast_finished` 时做幂等判断。
4. 清空：route task 结束或新 route task 启动。

`route_task_version`:

1. 每次新 route task 启动递增。
2. 用于隔离旧 session / 旧 route task 回调。

`active_goal_generation`:

1. 每次新 through goal 发出时递增。
2. 用于隔离旧 feedback / result。

## 14. 测试用例矩阵

### 14.1 启动类

1. 正常启动 route task。
2. route 中没有 task，返回 `missing_task_waypoints`。
3. waypoint role 非法，返回 `invalid_waypoint_role`。
4. 已有 route task 运行，再次启动返回 `route_task_already_running`。
5. 当前有普通导航运行，启动 route task 返回 `navigation_busy`，且不取消旧导航。

### 14.2 through 类

1. 正常经过 transit，发 `waypoint_passed`。
2. 同一段重复 feedback 不重复发 `waypoint_passed`。
3. 旧 goal feedback/result 晚到被 generation/version 拦截。

### 14.3 播报类

1. 到达需要播报的 task，先发 `broadcast_requested`，不直接完成 task。
2. 合法 `broadcast_finished` 推进 task 完成。
3. 不匹配的 `broadcast_finished` 不推进状态机。
4. 重复 `broadcast_finished` 命中 `last_completed_broadcast` 后幂等 success，不重复推进。

### 14.4 jump 类

1. 正向 jump 自动吸收中间 transit。
2. 反向 jump 按反向顺序吸收 transit。
3. 当前段内再次 jump，已 passed transit 不重复加入。
4. 新段允许重新经过历史段 transit。
5. 非法 jump 到 transit 返回 `target_waypoint_not_task`，状态不变。
6. 非法 jump 到不存在点返回 `invalid_target_waypoint`，状态不变。
7. `already_current_target` 返回 success + `result_reason`，状态不变。
8. 播报等待中 `interrupt_broadcast=true` jump 成功，并清理等待播报态。
9. 播报等待中 `interrupt_broadcast=false` 返回 `interrupt_broadcast_false_not_supported`。

### 14.5 完成类

1. 最后一个 task 完成后发 `route_task_completed`。
2. `route_task_completed` 先发摘要，再清状态。
3. `completed_task_ids / skipped_task_ids / result / completed_at` 完整。

### 14.6 协议联调类

1. `navigation_command_result` 能从 `/navigation/status` 正确推送到 APP。
2. `broadcast_requested` 能即时推送到 APP。
3. `waypoint_passed` 能即时推送到 APP。
4. `jump_updated` 能即时推送到 APP。

1. transit passed 能推进。
2. `waypoint_passed` 只发一次。
3. task 不由 feedback 直接完成。

### 任务 F：播报闭环

完成标志：

1. `broadcast_requested` 可推送。
2. `broadcast_finished` 匹配校验正确。
3. 重复播报回执幂等。

### 任务 G：jump 主流程

完成标志：

1. 正向 jump 正确。
2. 反向 jump 正确。
3. 当前段 passed transit 扣除正确。
4. 完整 route 区间重算不漏 transit。
5. 非法 jump 不污染状态。

### 任务 H：完成摘要与启动入口收口

完成标志：

1. `route_task_completed` 摘要完整。
2. 先发事件后清状态。
3. 默认 launch 启动已改造的 `navigation_state_manager`。
4. recoverable 旧入口不作为首版验收路径。

## 16. 风险清单

1. websocket 层继续丢新字段。
2. 桥接层做了过多业务判断。
3. 按 `waypoint_id` 数值推断 route 顺序。
4. transit 被错误播报或推进主任务。
5. 首版又退回逐点 `NavigateToPose`。

10. `broadcast_requested` 或 `navigation_command_result` 未加入立即推送白名单。
11. `broadcast_finished` 不做严格上下文匹配。
12. 非法 jump 提前改写运行态。
13. 旧 goal feedback/result 晚到污染当前段。
14. 首 task 在附近时被静默跳过。
15. `route_task_completed` 发前先清状态。

## 18. 最终协议与边界补充

本节用于收口第二轮评审提出的协议一致性、事件语义和实现边界。后续实现时，本节与前文同等有效，不作为可选建议。

### 18.1 ID 与时间字段统一

所有对外协议中的业务 ID 统一按字符串处理，不允许 APP 有时传数字、有时传字符串。

必须按字符串处理的字段包括：

1. `waypoint_id`
2. `target_waypoint_id`
3. `route_id`
4. `task_session_id`
5. `broadcast_id`
6. `segment_id`
7. `event_id`
8. `request_message_id`

固定规则：

1. ROS 内部比较 ID 前必须先转成字符串。
2. APP 下发数字 ID 时，桥接层可以转字符串，但状态机内部不得保留数字 ID。
3. ROS 推送给 APP 的 ID 一律输出字符串。
4. `timestamp` 统一使用 Unix epoch seconds，类型为 number，允许小数。
5. 不使用本地格式化时间字符串作为协议主时间字段。

### 18.2 command 与 event 字段边界

APP -> ROS 使用 `command_type`，ROS -> APP 使用 `event_type`。

固定规则：

1. `start_route_task`、`jump_to_waypoint`、`broadcast_finished` 必须出现在 APP 下发 payload 的 `command_type`。
2. `navigation_command_result`、`broadcast_requested`、`waypoint_passed`、`jump_updated`、`task_waypoint_completed`、`route_task_completed` 必须出现在 ROS 推送 payload 的 `event_type`。
3. `navigation_command_result.event_data.command_type` 仅表示“本次 ack 对应的原始命令类型”，不是新的 ROS 事件类型。
4. `navigation_command_result` 不是顶层 `data_type`，顶层 `data_type` 仍然只能是 `navigation_control | navigation_status`。
5. APP 判断业务 ack 时，使用 `data.event_type == "navigation_command_result"`，不要使用顶层 `data_type` 判断。

### 18.3 request_message_id 与 event_id

为避免 websocket 收包 ack、业务 ack、异步事件互相混淆，首版协议补充两个追踪字段。

`request_message_id`：

1. 来源：APP 下发命令外层 `message_id`。
2. 写入位置：ROS 返回的 `navigation_command_result.event_data.request_message_id`。
3. 缺失处理：若 APP 未带外层 `message_id`，ROS 可置空字符串，但日志必须记录。
4. APP 用途：把业务 ack 对回原始按钮操作或原始命令。

`event_id`：

1. 来源：ROS 生成。
2. 写入位置：所有 ROS -> APP route task 事件的 `event_data.event_id`。
3. 生成规则：优先使用事件 payload 或命令数据中的 `task_session_id`，其次使用当前 `active_route_task.task_session_id`。
4. 格式建议：`task_session_id + event_type + monotonic_counter + timestamp_ms` 或 UUID。
5. 缺失处理：若确实没有 `task_session_id`，允许使用 `no_session`，但不应在命令已带 session 时退化成 `no_session`。
6. APP 用途：事件去重、日志追踪、问题复盘。

首版必须带 `event_id` 的事件：

1. `navigation_command_result`
2. `broadcast_requested`
3. `waypoint_passed`
4. `jump_updated`
5. `task_waypoint_completed`
6. `route_task_completed`

### 18.4 枚举值收口

`navigation_command_result.event_data.status`：

1. `success`
2. `error`

`route_task_completed.event_data.result`：

1. `success`
2. `cancelled`
3. `failed`

首版只要求跑通 `success`，但字段枚举先预留 `cancelled | failed`，避免后续协议破坏。

`broadcast_finished.broadcast_result`：

1. 首版只接受 `completed`。
2. ROS 状态机必须对该字段执行字符串化、`strip()` 和 `lower()` 后再比较。
3. 字段缺失或值为 `null` 时可按默认 `completed` 处理。
4. 若 APP 传入其它值，返回 `unsupported_broadcast_result`。
5. 不得把 `failed`、`cancelled`、空字符串当作播报完成。

### 18.5 error_code 与 result_reason

`error_code` 只用于 `status=error`。

`result_reason` 只用于 `status=success` 下的特殊成功原因。

首版 `result_reason` 允许值：

1. `already_current_target`
2. `duplicate_broadcast_finished`

固定规则：

1. `already_current_target` 不进入 error code 表。
2. 重复 `broadcast_finished` 命中 `last_completed_broadcast` 时，可以返回 success + `result_reason=duplicate_broadcast_finished`。
3. 非法命令必须返回 `status=error + error_code`，不要用 `result_reason` 表示失败原因。

### 18.6 事件 payload 必带字段补充

以下事件除前文已列字段外，必须补齐 `event_id`、`timestamp`、`task_session_id`、`route_id`。

> 中文注释：`publish_status_update()` 外层已经有一份发布时间，但 route task 的业务事件体 `event_data` 也必须自带 `timestamp`。这样 APP 如果只消费 `event_data`，仍能按业务事件发生时间排序、去重和复盘；同时也避免数据集成层或 websocket 包装结构变化后，前端失去事件时间字段。

`navigation_command_result` 额外必须带：

1. `request_message_id`
2. `command_type`
3. `status`
4. `error_code`
5. `result_reason`
6. `message`

`waypoint_passed` 额外必须带：

1. `segment_id`
2. `waypoint_id`
3. `waypoint_role=transit`
4. `passed_transit_waypoint_ids`
5. `current_target_task_id`

`jump_updated` 额外必须带：

1. `segment_id`
2. `target_waypoint_id`
3. `segment_direction`
4. `execution_waypoint_ids`
5. `skipped_task_ids`
6. `interrupt_broadcast`
7. `interrupted_broadcast`

`interrupted_broadcast` 字段说明：

1. 类型：`object`
2. 默认：`{}`
3. 仅当 jump 打断正在等待的播报时填写。
4. 示例：`{"waypoint_id": "7", "broadcast_id": "broadcast_7"}`

`task_waypoint_completed` 额外必须带：

1. `segment_id`
2. `waypoint_id`
3. `completed_task_ids`
4. `next_target_task_id`

`route_task_completed` 额外必须带：

1. `completed_task_ids`
2. `skipped_task_ids`
3. `completed_at`
4. `result`
5. `summary`

列表字段快照规则：

1. `waypoint_passed.passed_transit_waypoint_ids` 必须是发布事件当刻的当前段快照。
2. `jump_updated.execution_waypoint_ids` 必须是 jump 后新段的执行列表快照。
3. `jump_updated.skipped_task_ids` 必须是本次 jump 合并后的跳过 task 快照。
4. `task_waypoint_completed.completed_task_ids` 必须是当前 task 闭环完成后的完成集合快照。
5. `route_task_completed.completed_task_ids / skipped_task_ids` 必须是 reset 之前的最终摘要快照。
6. `navigation_failed` 若 `route_task=true`，其中的 `execution_waypoint_ids / passed_transit_waypoint_ids / completed_task_ids / skipped_task_ids` 也必须是失败现场快照。

> 中文注释：这里的“快照”是为了避免 ROS 内部运行态继续推进、替换 `active_segment` 或执行 `reset_route_task_state()` 后，影响 APP 已经收到的事件复盘语义。实现上不要把内部列表对象直接塞进 payload，应使用 `list(...)` 生成独立副本。

### 18.7 task 与 transit 触发边界

`task` 固定能力：

1. 可以成为 jump 目标。
2. 可以触发 `broadcast_requested`。
3. 可以触发 `task_waypoint_completed`。
4. 可以推进 `completed_task_ids`。
5. 可以推进下一段或最终完成 route task。

`transit` 固定能力：

1. 只能作为 through 途经点。
2. 只能触发 `waypoint_passed`。
3. 不能成为合法 jump 目标。
4. 不能触发播报。
5. 不能触发 `task_waypoint_completed`。
6. 不能进入 `completed_task_ids` 或 `skipped_task_ids`。

补充规则：

1. `task.need_broadcast=false` 时，到达后仍必须触发 `task_waypoint_completed`。
2. `transit.need_broadcast` 即使 APP 误传为 `true`，归一化后也必须强制为 `false`。

### 18.8 jump 边界补充

跳转到已完成 task：

1. 若目标是当前 route 内的合法 `task`，首版允许跳转。
2. 需要按当前进度到目标 task 的完整 route 区间重建 `active_segment`。
3. 中间 transit 按方向重新吸收。
4. 到达该 task 后重新执行 task 完成流程。
5. `completed_task_ids` 保持去重，不重复追加同一个 task。

跳转到最后一个 task：

1. 若目标是最后一个合法 task，允许跳转。
2. 到达并完成该 task 后，直接发布 `route_task_completed`。
3. 不再创建下一段。

跳转成功 ack 时机：

1. 不建议收到命令后立刻返回业务 success。
2. 推荐在完成合法性校验、旧 goal 取消已发起、新 `active_segment` 已建立、新 through goal 已发起后，返回 `navigation_command_result(success)`。
3. websocket 层 `command_ack` 仍可立即表示“已收包”，但它不是业务成功。
4. `jump_updated` 也必须在新 through goal 已经成功发起后再发布；它表示 APP 可以切换到新执行段 UI，而不只是 ROS 本地完成了路径段重建。
5. 如果新 through goal 发起失败，ROS 不发布 `jump_updated`，APP 只消费 `navigation_command_result(error)` 或 `navigation_failed(route_task=true)`，避免 UI 先切到新段又立刻被失败状态打回。

> 中文注释：`jump_updated` 的语义比“重建 active_segment 完成”更强，它是 APP 更新当前路线执行段的依据。因此发布它之前必须确认 `NavigateThroughPoses` 的新 goal 已经发起成功；否则 APP 会收到一个看似成功的段更新，随后又收到启动失败，造成播报 UI、路线高亮和错误提示相互打架。

等待播报中 jump：

1. `WAITING_BROADCAST` 状态下，合法 jump 且 `interrupt_broadcast=true` 时，ROS 必须清理当前播报等待状态。
2. ROS 发布 `jump_updated` 后，APP 必须退出旧播报 UI 或停止等待旧播报回执；由于该事件只会在新 through goal 发起成功后发布，APP 可以把它当作“切换到新段执行”的可靠信号。
3. `jump_updated.event_data.interrupted_broadcast` 使用对象表达被打断播报的上下文。
4. 未打断播报时，`interrupted_broadcast={}`。

### 18.9 失败、取消与旧导航兼容

首版不新增 `route_task_failed` 或 `route_task_cancelled` 事件作为验收目标。

固定规则：

1. 正常完成统一使用 `route_task_completed(result=success)`。
2. 导航失败、取消、急停等异常场景，首版先沿用现有普通导航失败/取消状态通道。
3. 不得为了 route task 改坏旧单点导航、多点导航、展厅导航的既有语义。
4. route task 运行期间，旧普通导航命令应返回 busy/reject，不允许静默抢占 route task。
5. 已有普通导航运行期间，`start_route_task` 返回 `navigation_busy`，不允许静默抢占普通导航。
6. 首版只允许一个 active route task，不做队列、不做并发、不做后台 pending。
7. route task 运行中再次收到 `start_route_task`，返回 `route_task_already_running`。
8. route task 失败清理时必须使用 route task 专用安全取消，不能复用通用 `cancel_navigation()`。
9. 专用安全取消必须捕获旧 goal handle，只允许旧 cancel 回调清理同一个旧对象，避免旧回调晚到时清空新 route task goal。
10. `navigation_failed` 若 `route_task=true`，必须携带路线任务复盘上下文。
11. `cancel_navigation` 若由 APP 发送，也按旧普通导航控制命令拒绝；首版不把它定义为 route task 专属取消能力。

> 中文注释：第 8、9 条是为了防止“失败后马上重启路线”时出现幽灵回调。旧 goal 的 cancel 结果可能晚于新 goal response 返回，如果用通用取消回调无条件清空 `current_goal_handle`，新路线会被旧回调误伤。第 11 条用于消除 APP 命名歧义：如果前端把停止按钮命名为 `cancel_navigation`，首版仍应返回 `route_task_active`，而不是悄悄取消路线任务或进入未知命令分支。真正的路线任务取消需要单独协议、事件和 APP 文案评审。

route task `navigation_failed` 复盘字段：

1. `task_session_id`
2. `route_id`
3. `failure_code`
4. `current_target_task_id`
5. `segment_id`
6. `segment_direction`
7. `execution_waypoint_ids`
8. `passed_transit_waypoint_ids`
9. `completed_task_ids`
10. `skipped_task_ids`
11. `failed_at`

### 18.10 waypoint_role 缺失策略

route task 模式下，`waypoint_role` 是必需业务字段。

固定规则：

1. 优先读取 `route_waypoints[].waypoint_role`。
2. 其次读取 `route_waypoints[].properties.waypoint_role`。
3. 两处都缺失时，`start_route_task` 返回 `invalid_waypoint_role`。
4. 该限制只约束 route task 新协议，不反向要求旧普通导航必须携带 `waypoint_role`。

### 18.11 参数与日志口径

建议新增或确认以下参数：

1. `route_task.first_task_reached_tolerance_m`
2. `route_task.transit_passed_tolerance_m`
3. `route_task.transit_projection_passed_enabled`
4. `route_task.nav2_feedback_timeout_sec`
5. `route_task.goal_cancel_timeout_sec`
6. `route_task.default_interrupt_broadcast`

ROS 参数生效规则：

1. `route_task.first_task_reached_tolerance_m` 用于 `start_route_task` 首 task 已在附近时的快速到达判断。
2. `route_task.transit_passed_tolerance_m` 用于 pose fallback 判断 transit 是否已经通过。
3. `route_task.transit_projection_passed_enabled` 用于控制是否启用“沿上一执行点到 transit 的投影越过”兜底判定。
4. `route_task.nav2_feedback_timeout_sec` 必须在 `ROUTE_TASK_SEGMENT_NAVIGATING` 阶段生效；若 `NavigateThroughPoses` 长时间没有 feedback，应进入 route task 专用失败流程并发布 `navigation_failed(route_task=true)`。
5. `route_task.nav2_feedback_timeout_sec <= 0` 表示关闭 feedback 静默超时检查。
6. 新 through 段下发时可以先初始化 feedback 计时，但 goal response accepted 后必须重新刷新计时点，避免 action server 排队/调度延迟被误算成 feedback 静默。
7. `WAITING_BROADCAST` 阶段不得触发 Nav2 feedback 超时，因为此时机器人已经到达目标 task，等待的是 APP 播报完成回执。
8. `route_task.default_interrupt_broadcast` 用于 `jump_to_waypoint.interrupt_broadcast` 缺失时的默认值，并且必须通过 `route_task_bool()` 解析。
9. `route_task.goal_cancel_timeout_sec` 当前作为取消旧 through goal 的联调观察参数保留；若后续要实现取消超时升级处理，必须补充独立事件和静态护栏。

> 中文注释：这里把“参数存在”和“参数实际影响行为”分开写，是为了避免 launch 中配置了参数但状态机没有使用。尤其是 feedback timeout，如果不生效，Nav2 action 卡住时 APP 会长期停留在路线任务执行中，无法得到失败复盘事件。

APP 侧建议参数：

1. `route_task.command_ack_timeout_sec`
2. `route_task.business_ack_timeout_sec`
3. `route_task.broadcast_finished_retry_count`

ROS 日志必须覆盖的追踪字段：

1. `task_session_id`
2. `route_id`
3. `segment_id`
4. `current_anchor_task_id`
5. `current_target_task_id`
6. `route_task_version`
7. `active_goal_generation`
8. `request_message_id`
9. `event_id`

必须记录的关键场景：

1. `start_route_task` accepted/rejected。
2. `jump_to_waypoint` accepted/rejected。
3. `broadcast_finished` matched/mismatched/duplicate。
4. `waypoint_passed`。
5. old feedback/result ignored。
6. `route_task_completed` summary published。
