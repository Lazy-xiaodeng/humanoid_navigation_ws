# 路线任务改造思路稳定版

## 1. 文档目的

本文档用于把当前“整轮路线任务 + 任意跳步 + task/transit 辅助点 + 播报协同”的需求理解、代码落点和关键边界整理成一份相对稳定的评审稿。

这份文档的目标不是直接替代实施清单，而是作为开工前的稳定需求基线，帮助确认：

1. 需求语义是否已经统一
2. 真实运行入口是否已经判断清楚
3. 第一优先级改动点是否已经收敛
4. 哪些边界行为必须在编码前先钉死
5. 哪些问题属于首版主需求
6. 哪些问题应后置为增强项

---

## 2. 需求稳定结论

### 2.1 本次不是旧版多点导航小修补

这次需求不是在旧版“沿 A-B-C-D 顺序继续走”的基础上，只把中间点弱化成途经点。

本次需求本质上是引入一套新的“整轮路线任务”模型：

1. APP 一次性下发整轮路线
2. ROS 自主推进任务执行
3. APP 负责播报、跳步、交互和状态展示

### 2.2 点位角色稳定结论

每个点位在路线任务中必须显式区分两种角色：

1. `task`
   - 有业务语义
   - 可作为跳步目标
   - 可触发播报
   - 完成后推进主任务进度
2. `transit`
   - 仅作为辅助 through 点
   - 不触发播报
   - 不作为任务完成点
   - 不推进主任务索引

### 2.3 正常执行稳定结论

如果存在：

```text
10(task) -> 11(transit) -> 12(transit) -> 13(task)
```

则从 `10` 到 `13` 的执行语义为：

```text
10 -> 11 -> 12 -> 13
```

其中：

1. `11/12` 自动吸收为 through 点
2. `11/12` 不播报
3. `11/12` 不等待
4. `11/12` 不停靠成任务完成点
5. `13` 才是本段真正目标

### 2.4 跳步稳定结论

如果当前存在：

```text
7(task) -> 8(task) -> 9(task) -> 10(task) -> 11(transit) -> 12(transit) -> 13(task) -> 14(task) -> 15(task)
```

当用户从 `7` 跳到 `15` 时，稳定语义为：

```text
7 -> 11 -> 12 -> 15
```

而不是：

```text
7 -> 8 -> 9 -> 10 -> 13 -> 14 -> 15
```

也就是说：

1. 中间 `task` 全部跳过
2. 中间 `transit` 自动吸收
3. 吸收严格按路线顺序进行
4. 最终目标直接是目标 `task`

### 2.5 跳步完成后的续走稳定结论

跳到哪个 `task` 点，哪个 `task` 点完成后，就从它继续沿主任务序列向后执行。

例如：

1. `A -> D`
   - `D` 完成后继续 `E`
2. `F -> B`
   - `B` 完成后继续 `C`

不会回去补中间被跳过的任务点。

### 2.6 播报协同稳定结论

播报只针对 `task`。

闭环固定为：

1. ROS 到达需要播报的 `task`
2. ROS 推送 `broadcast_requested`
3. APP 播报
4. APP 回传 `broadcast_finished`
5. ROS 再继续

`transit` 永远不进入播报闭环。

## 3. 关键边界稳定结论

### 3.1 当前段中再次跳步

如果当前段中部分 `transit` 已经通过，再次跳步时：

1. 必须基于当前位置和剩余未通过点重建
2. 已通过的 `transit` 不允许重复加入
3. 不需要创建“当前位置”的虚拟 waypoint
4. Nav2 自然从当前 pose 起步
5. 新的 `execution_waypoint_ids` 只保留：
   - 剩余 `transit`
   - 目标 `task`

### 3.2 `passed_transit_waypoint_ids` 只对当前段生效

`passed_transit_waypoint_ids` 的作用范围必须收紧。

正确语义应为：

1. 它是 `active_segment` 级状态
2. 只用于解决“同一段尚未完成时再次跳步，不要重复跑已经通过的 transit”
3. 它不能作为整轮 route task 的全局永久去重表
4. 当前段完成后，这组 through 进度应重置
5. 新段必须重新基于 `route_waypoints` 和 direction 规则收集 transit

例如：

```text
route_waypoints:
3(task) -> 7(task) -> 11(transit) -> 12(transit) -> 15(task)
```

第一次从 `7` 跳到 `15`：

```text
7 -> 11 -> 12 -> 15
```

如果这段已经完成，后续再从 `15` 跳到 `3`，则 `11/12` 作为反向区间中的 transit 可以重新被吸收。

也就是说：

1. 同一段内不重复跑
2. 跨段或反向新跳步可以重新经过

### 3.3 正向/反向跳步必须 direction-aware

`collect_transit_waypoints_between_tasks()` 不能只按正向思路写。

必须明确：

1. 正向跳步按原路线顺序收集 `transit`
2. 反向跳步按反向执行顺序处理 `transit`
3. 不能拿同一份正向列表同时服务正向和反向跳步

### 3.4 路线拓扑依据是 `route_waypoints` 数组顺序

自动吸收 `transit` 的依据只能是：

1. APP 下发的 `route_waypoints` 数组顺序

不能是：

1. `waypoint_id` 数字大小
2. 空间距离临时推断
3. ROS 自行重新排序

也就是说：

1. `waypoint_id` 只是身份标识
2. 路线顺序只能来自 APP 下发顺序

### 3.5 反向跳步不能让 ROS 猜回程路径

如果回程需要专门的辅助点，必须由路线数据本身表达。

ROS 不应：

1. 根据点位编号猜回程点
2. 根据空间位置自动猜安全回程路径

如果正反向都要安全通行，路线本身必须能表达反向所需的辅助点顺序。

### 3.6 第一版收窄 `interrupt_broadcast`

第一版建议明确收窄为：

1. 完整支持 `interrupt_broadcast = true`
2. 暂不实现 `interrupt_broadcast = false` 的挂起跳步队列
3. `false` 先保留字段和日志

这样可以避免首版状态机复杂度过高。

### 3.7 跳步目标合法性由 ROS 兜底

即使 APP UI 只允许选择 `task`，ROS 侧仍必须再次校验：

1. `target_waypoint_id` 是否存在
2. 是否属于当前路线
3. 是否为 `task`
4. 当前 route task 是否仍在执行

如果不合法：

1. 拒绝跳步
2. 返回错误 ack
3. 保持当前任务状态不变
4. 不取消当前 Nav2 goal
5. 不修改 `active_segment`
6. 不修改 `awaiting_broadcast`
7. 不推进或回退主任务索引

### 3.8 route task 结束条件和收尾

建议结束条件固定为：

1. 最后一个 `task` 已到达
2. 若需要播报，则已收到对应 `broadcast_finished`
3. 没有剩余 `active_segment`

结束时建议顺序为：

1. 先构造最终完成摘要
2. 发布 `route_task_completed`
3. 再清理 route task 运行态
4. 再清理等待播报状态
5. 再清理活动执行段
6. 再拒绝或忽略旧 session 命令

最终完成摘要建议至少包含：

1. `task_session_id`
2. `route_id`
3. `completed_waypoint_id`
4. `completed_task_ids`
5. `skipped_task_ids`
6. `completed_at`
7. `result`

### 3.9 重复命令、旧 session、旧回调必须隔离

建议作为固定规则：

1. 旧 `task_session_id` 命令一律拒绝或忽略
2. route task 完成后收到旧 `broadcast_finished` 一律忽略
3. route task 完成后收到旧 `jump_to_waypoint` 一律拒绝
4. 重复 `broadcast_finished`
   - 若与当前已完成记录一致，则幂等成功，不重复推进
5. 错误 `broadcast_finished`
   - 若与当前等待态不匹配，则忽略或返回错误
6. 重复跳到当前目标 task
   - 返回“已是当前目标”，不重发 goal
7. 旧 Nav2 goal result 回调
   - 不能污染新执行段状态

### 3.10 `waypoint_role` 入口必须统一归一化

建议统一来源优先级：

1. 优先读取 `route_waypoints[].waypoint_role`
2. 若没有，再兼容读取 `route_waypoints[].properties.waypoint_role`
3. 入口处统一归一化为内部 `RouteWaypoint.waypoint_role`
4. 状态机内部只读取归一化后的角色

不要让状态机内部同时到处判断：

1. `waypoint_role`
2. `properties.waypoint_role`

### 3.11 through 执行不等于不维护中间进度

首版要做丝滑 through，这个方向是正确的。

但必须明确：

1. 使用 `NavigateThroughPoses` 并不代表可以不维护中间 transit 进度
2. 再次跳步时仍然需要知道哪些 transit 已经过了
3. 因此状态管理器必须维护 `active_segment_progress`

建议中间进度来源为：

1. 优先使用 Nav2 action feedback 中的当前 waypoint / remaining waypoint 信息
2. 若当前 Nav2 版本 feedback 不足，则由状态管理器根据机器人当前 pose 与 transit 阈值自行判断
3. 判定出的 through 进度只更新当前 `active_segment`

### 3.12 `waypoint_passed` 的触发口径需要固定

建议首版不要追求“几何意义上的精确穿越瞬间”，而采用更稳定的一致性口径：

1. 当状态管理器确认某个 transit 已被当前段进度越过时，触发 `waypoint_passed`
2. 不要求必须精确到机器人刚好穿过该点的瞬时几何事件
3. 事件语义以“执行段内部已确认ผ่าน该 transit”为准

这样实现成本更稳，也更适合与跳步重建逻辑对齐。

### 3.13 route task 启动时的第一个 task 规则需要写死

启动整轮路线任务时，需要明确第一段怎么开始。

建议在后续实施清单中写死：

1. 如果机器人不在第一个 `task` 附近
   - 应先导航到第一个 `task`
2. 如果机器人已经在第一个 `task` 附近
   - 是否直接把它当作 anchor
   - 是否仍要按业务完成一次
   - 是否立即触发 `broadcast_requested`

这部分必须固定口径，避免实现者各自理解。

当前建议优先口径为：

1. route task 启动时，第一个 `task` 默认作为首个业务目标
2. 如果机器人不在第一个 `task` 附近
   - 先导航到第一个 `task`
3. 如果机器人已经在第一个 `task` 附近
   - 仍需要按业务规则判定该点是否需要完成一次
   - 不能未经明确规则就默认它已完成
4. 第一个 `task` 如果配置了播报
   - 则在到达/确认处于该点后，仍应按统一规则触发 `broadcast_requested`

## 4. 首版主需求与后置增强项

### 4.1 首版主需求

当前首版主需求应只覆盖：

1. APP 一次性下发整轮路线
2. ROS 自主推进 route task
3. `task` 推进主任务，`transit` 只做 through
4. 正常相邻 task 段自动吸收 transit
5. 任意正向/反向跳步
6. 播报闭环
7. 首版即实现丝滑 through
8. 旧 session / 重复命令 / 旧回调隔离

### 4.2 暂不纳入首版主需求

以下问题暂不并入首版路线任务主需求：

1. 过门时强制朝向约束
2. 门区限速
3. 门洞姿态校验
4. heading guard
5. 过门专用 BT
6. planner/controller 为门区单独调优

这些属于后续实测后再设计的增强项，不应在首版主需求里继续膨胀范围。

### 5.1 当前仓库存在两条应用层链路

已确认：

1. `navigation.launch.py`
   - 启动 `navigation_state_manager_recoverable`
2. `navigation_fusion.launch.py`
   - 启动 `navigation_state_manager`

### 5.2 最近一次真实实机主入口

根据最近一次真实启动链路核实结果：

1. `start_navigation.sh`
   - 实际启动 `robot_real.launch.py`
2. `robot_real.launch.py`
   - 包含 `navigation_fusion.launch.py`
3. `navigation_fusion.launch.py`
   - 实际启动 `navigation_state_manager.py`

因此当前最近一次真实实机主状态管理入口应优先按：

1. `navigation_state_manager.py`

处理。

### 5.3 当前入口优先级结论

当前更合理的改造优先级为：

1. 第一优先级改 `navigation_state_manager.py`
2. 第二优先级再同步 `navigation_state_manager_recoverable.py`

`navigation_state_manager_recoverable.py` 当前应视为兼容补齐入口，而不是首要施工入口。

## 9. 稳定后的施工顺序

建议按下面顺序推进：

### 第一步：先打通协议透传

改：

1. `websocket_server.py`
2. `dynamic_waypoints_manager.py`

目标：

1. `start_route_task`
2. `jump_to_waypoint`
3. `broadcast_finished`

这三类新命令能完整穿到状态管理器。

### 第二步：让 `navigation_state_manager.py` 能理解新命令

先打通：

1. `start_route_task`
2. `jump_to_waypoint`
3. `broadcast_finished`

### 第三步：先确保 `broadcast_requested` 实时推送可用

在联调播报闭环前，把：

1. `broadcast_requested`

加入立即推送白名单。

### 第四步：先跑通正常路线闭环

包括：

1. 整轮路线任务启动
2. 相邻 task 之间自动吸收 transit
3. 到 task 后发 `broadcast_requested`
4. 收到 `broadcast_finished` 后继续

### 第五步：实现任意跳步

包括：

1. 正向跳步
2. 反向跳步
3. 中间 task 跳过
4. 中间 transit 自动吸收
5. 已通过 transit 不重复加入
6. 旧 goal cancel 和旧回调隔离

### 第六步：补齐剩余实时事件

补：

1. `waypoint_passed`
2. `jump_updated`
3. `task_waypoint_completed`
4. `route_task_completed`

### 第七步：首版即接入丝滑 through

首版不是“先逐点、后优化”，而是要直接满足客户对辅助点无痕通过的要求。

因此首版建议直接接入：

1. `NavigateThroughPoses`
2. 或等价整段 through goal

要求：

1. `transit` 连续通过
2. `transit` 不停车
3. `transit` 不旋转对齐
4. `transit` 不等待播报
5. 最终 `task` 才执行停靠、对齐和播报闭环

执行接口从一开始就应按整段 `active_segment` 设计，逐点执行不能作为“先跑通再升级”的正式实施路径，也不能作为客户验收方案。

这里再明确两条：

1. 首版 through 是验收目标，不是后续优化项
2. 如果实现过程中为了调试临时做逐点执行，只能作为短期 debug fallback，不能写进稳定方案主路径

### 第八步：最后同步到 recoverable 版

等主链路稳定后，再同步到：

1. `navigation_state_manager_recoverable.py`

## 10. 建议补充的验收用例

1. 正常执行 `10(task) -> 11(transit) -> 12(transit) -> 13(task)`
2. 正向跳步 `7(task) -> 15(task)`，中间吸收 `11/12(transit)`
3. 反向跳步 `15(task) -> 3(task)`，重新按反向区间吸收 `12/11(transit)`
4. 当前段未完成时再次跳步，已通过 transit 不重复加入
5. 当前段已完成后再次跳步，相关 transit 可按新段重新吸收
6. 播报等待中 `interrupt_broadcast=true` 跳步
7. `interrupt_broadcast=false` 首版返回暂不支持或拒绝
8. 非法跳到 transit，当前导航不受影响
9. 非法跳到不存在点，当前导航不受影响
10. 重复 `broadcast_finished` 幂等成功但不重复推进
11. 旧 session 命令被拒绝或忽略
12. 旧 Nav2 goal result 晚到，不污染新执行段
13. 最后一个 task 播报完成后发布 `route_task_completed`

---

## 11. 稳定后的高风险点

1. 把 `navigation_state_manager_recoverable.py` 误当主入口先改
2. websocket 层新字段透传不全
3. `broadcast_requested` 不实时推送，导致播报闭环误判
4. 把 `transit` 错当成推进主进度的点
5. 再次跳步时重复跑已通过 transit
6. 旧 Nav2 goal 回调污染新执行段
7. route task 结束后旧命令继续生效
8. 把 `route_waypoints` 顺序误写成按 `waypoint_id` 排序
9. 反向跳步时让 ROS 自行猜回程路径
10. `waypoint_role` 来源不统一，状态机内部读值不一致
11. 丝滑 through 被当成后续优化项，导致首版验收口径偏掉
12. through 执行中不维护中间 transit 进度，导致再次跳步无法正确重建

---

## 12. 当前稳定结论

截至这版，当前思路已经可以视为一份相对稳定的开发前需求基线。

最关键的稳定结论是：

1. 当前主运行入口优先按 `navigation_state_manager.py` 处理
2. `route_waypoints` 数组顺序是路线拓扑唯一依据
3. `task` 推进主任务，`transit` 只做 through
4. 跳步时中间 `task` 跳过，中间 `transit` 自动吸收
5. 再次跳步必须基于当前位置和剩余未通过点重建
6. `passed_transit_waypoint_ids` 只对当前 `active_segment` 生效，不是全局去重表
7. 第一版就要实现丝滑 through，逐点执行不能作为最终方案
8. `broadcast_requested / broadcast_finished` 闭环必须先打通
9. 旧 session、重复命令、旧 goal 回调必须全部隔离
10. 首版暂不纳入过门朝向/限速/门区姿态增强项

如果这份稳定版通过下一轮评审，下一步就可以进入“函数级实施清单”阶段，把每个文件具体改哪些函数、哪些字段、哪些事件 payload、哪些 ack/error、哪些状态流转顺序逐项写死。
