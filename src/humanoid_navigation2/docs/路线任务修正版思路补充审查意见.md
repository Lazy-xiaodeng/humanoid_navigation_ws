# 路线任务修正版思路补充审查意见

## 1. 文档目的

本文档用于审查《路线任务改造思路整理 (1).md》这一版修正版思路。

当前结论是：

1. 这版没有明显方向性错误
2. 可以作为后续开发依据
3. 但仍建议补充若干边界行为，避免编码时出现理解分叉

本文档只记录本轮新发现的补充审查点，不推翻前面已经确认过的主方案。

## 2. 总体结论

《路线任务改造思路整理 (1).md》已经修正了上一轮的主要问题：

1. 已经把 `navigation_state_manager.py` 放回当前真实主入口优先级
2. 已经把 `navigation_state_manager_recoverable.py` 降为兼容补齐项
3. 已经补充 `dynamic_waypoints_manager.validate_navigation_command()` 当前不会自动生效的问题
4. 已经补充当前段再次跳步时，已通过 `transit` 不应重复加入的语义
5. 已经补充 `interrupt_broadcast` 的语义框架

因此这版可以继续往“具体函数级实施清单”和“代码实现”推进。

但建议在真正开工前，再补充以下 7 个边界点。

## 3. 补充点一：明确“当前位置”不是临时 waypoint

修正版文档中写到：

1. 新跳步应基于机器人当前物理位置重建
2. 新段应从“当前位置 + 剩余未通过点 + 新目标 task”构建

这句话方向是对的，但建议再补一句实现含义：

1. “当前位置”不需要额外创建一个临时 waypoint
2. Nav2 action 本身会从机器人当前 pose 起步
3. 新的 `execution_waypoint_ids` 只需要包含：
   - 剩余需要执行的 `transit`
   - 最终目标 `task`

建议补充说明：

```text
这里的“当前位置”是导航 action 的自然起点，不需要写入 route_waypoints，也不需要创建虚拟 waypoint。重建后的 execution_waypoint_ids 只保存后续需要经过的 transit 和最终目标 task。
```

## 4. 补充点二：正向 / 反向跳步的区间判断要 direction-aware

修正版文档中写到：

1. 当前段中尚未通过的剩余点，若仍位于新目标的顺序区间内，则可继续保留

这里建议进一步明确：

1. 顺序区间必须按跳步方向判断
2. 正向跳步和反向跳步不能用同一个简单区间判断

建议补充规则：

1. 正向跳步：
   - 当前顺序索引小于目标顺序索引
   - 只吸收当前索引到目标索引之间的 `transit`
   - 执行顺序按原路线正向排列
2. 反向跳步：
   - 当前顺序索引大于目标顺序索引
   - 只吸收目标索引到当前索引之间的 `transit`
   - 执行顺序需要按反向路径处理

建议补充说明：

```text
collect_transit_waypoints_between_tasks() 必须带 direction 语义。正向跳步按原始顺序收集 transit；反向跳步需要按反向执行顺序收集 transit，不能简单使用正向列表。
```

## 5. 补充点三：第一版收窄 `interrupt_broadcast` 实现范围

修正版文档中既提到：

1. `interrupt_broadcast = true` 时打断播报
2. `interrupt_broadcast = false` 时挂起跳步请求

也提到第一版可以先只支持 `interrupt_broadcast = true`。

这里建议明确第一版取舍，避免实现范围膨胀。

推荐第一版策略：

1. 完整支持 `interrupt_broadcast = true`
2. `interrupt_broadcast = false` 先保留协议字段
3. 如果收到 `false`，可以：
   - 返回暂不支持
   - 或记录日志并按当前策略处理
4. 暂不实现“播报完成后自动执行挂起跳步”

建议补充说明：

```text
第一版建议只实现 interrupt_broadcast=true。interrupt_broadcast=false 暂不实现挂起队列，只保留字段和日志，避免 WAITING_BROADCAST 与 pending_jump_request 组合导致状态机复杂度过高。
```

## 6. 补充点四：实时事件推送应提前到播报闭环联调前

修正版文档中将 `data_integration_node_recoverable.py` 的实时事件推送放在第五步。

建议稍微提前：

1. 至少 `broadcast_requested` 要在正常播报闭环联调前加入实时推送白名单
2. 否则 ROS 侧即使发出事件，APP 也可能无法实时收到
3. 这会导致误判为状态机没有工作

建议补充说明：

```text
在联调 broadcast_requested / broadcast_finished 闭环前，必须先把 broadcast_requested 加入 data_integration_node_recoverable.py 的立即推送白名单。jump_updated、waypoint_passed、task_waypoint_completed 可随跳步阶段补齐。
```

## 7. 补充点五：跳步目标合法性必须在 ROS 侧兜底

修正版文档中已经说明 `task` 可作为跳步目标，`transit` 不作为任务完成点。

但建议明确：

1. APP UI 应只允许选择 `task`
2. ROS 侧仍必须兜底校验
3. 如果 APP 发来的 `target_waypoint_id` 是 `transit`，ROS 不能执行跳步

建议行为：

1. 拒绝跳步
2. 返回错误 ack
3. 可选推送 `jump_rejected`
4. 当前导航任务保持原状态

建议补充说明：

```text
jump_to_waypoint.target_waypoint_id 必须是 task。即使 APP 侧已做过滤，ROS 侧仍需校验。如果目标是 transit 或不存在，应拒绝跳步并保持当前任务状态。
```

## 8. 补充点六：跳步时当前 Nav2 action 的取消流程要明确

修正版文档已经说明跳步会重建执行段，但还需要明确当前导航 action 的处理。

收到 `jump_to_waypoint` 后，ROS 侧应该：

1. 记录跳步请求
2. 取消当前 Nav2 goal
3. 等待取消完成或进入可切换状态
4. 构建新的 `active_segment`
5. 发送新的导航 goal
6. 推送 `jump_updated`

如果不明确这一点，容易出现：

1. 旧 goal 未取消
2. 新 goal 已发送
3. 两个 action 状态交叉
4. 到点回调误触发旧目标的完成逻辑

建议补充说明：

```text
jump_to_waypoint 不能只改内存态后直接发送新目标，必须处理当前 Nav2 goal 的取消和旧回调隔离。建议引入 goal generation / route_task_version，避免旧 goal result 回调污染新执行段。
```

## 9. 补充点七：定义 route task 结束条件和清理动作

修正版文档重点描述了执行中逻辑，但建议补上任务结束收尾规则。

建议结束条件：

1. 最后一个 `task` 已到达
2. 如果需要播报，则已收到对应 `broadcast_finished`
3. 没有剩余 `active_segment`

结束时建议：

1. 发布 `route_task_completed`
2. 清理 `active_route_task`
3. 清理 `awaiting_broadcast`
4. 清理 `active_segment`
5. 清理 `pending_jump_request`
6. 保留必要的最后任务摘要用于 UI 展示和日志

建议补充说明：

```text
最后一个 task 完成且播报闭环结束后，ROS 应发布 route_task_completed，并清理 route_task 运行态，避免任务结束后继续响应旧 broadcast_finished 或旧 jump_to_waypoint。
```

## 10. 建议另一台 Codex 修改文档时直接补入的摘要

可以把下面这段直接补进它的思路文档：

```text
补充边界规则：

1. 跳步重建中的“当前位置”不是临时 waypoint，Nav2 会自然从当前 pose 起步，execution_waypoint_ids 只保存剩余 transit 和目标 task。
2. collect_transit_waypoints_between_tasks() 必须带 direction 语义，正向和反向跳步的 transit 收集顺序不同。
3. 第一版建议只完整支持 interrupt_broadcast=true；interrupt_broadcast=false 先保留字段和日志，不实现挂起跳步队列。
4. broadcast_requested 必须在播报闭环联调前加入 data_integration_node_recoverable.py 的立即推送白名单。
5. jump_to_waypoint.target_waypoint_id 必须是 task；如果目标不存在或是 transit，ROS 应拒绝跳步并保持当前任务状态。
6. jump_to_waypoint 必须取消当前 Nav2 goal，并隔离旧 goal result 回调，避免旧目标完成污染新执行段。
7. 最后一个 task 完成且播报闭环结束后，应发布 route_task_completed 并清理 route_task 运行态。
```

## 11. 最终结论

《路线任务改造思路整理 (1).md》这版已经可以作为开发依据。

本轮新增意见主要是边界补强：

1. 跳步重建不要创建虚拟 waypoint
2. 正反向跳步的 transit 区间判断要带方向
3. 第一版收窄 `interrupt_broadcast=false`
4. 实时事件推送要提前
5. ROS 侧兜底校验跳步目标必须是 `task`
6. 跳步要处理当前 Nav2 goal 取消
7. 要定义 `route_task_completed` 和任务清理规则

这些补充不改变主方案，只是把实现时最容易分叉的边界钉清楚。
