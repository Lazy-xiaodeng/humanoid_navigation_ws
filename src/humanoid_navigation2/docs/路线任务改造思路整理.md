# 路线任务改造思路整理

## 1. 文档目的

本文档用于把当前对“整轮路线任务 + 任意跳步 + task/transit 辅助点 + 播报协同”需求的理解，整理成一份可核对的实施说明。

这份文档不是最终代码实现，也不是详细开发计划，主要用于确认：

1. 我们当前理解的需求语义是否正确
2. 当前仓库真实链路是否判断正确
3. 需要优先修改哪些文件
4. 每个文件准备怎么改
5. 推荐按什么顺序施工
6. 开工前需要钉死哪些边界行为

---

## 2. 当前确认的需求语义

### 2.1 不是旧版“沿主任务点顺序继续走”

这次最终需求不是旧版那种：

1. 沿 `A -> B -> C -> D` 继续执行
2. 只是把中间某些点降级成途经点

这次要做的是新的“整轮路线任务”模型。

### 2.2 APP 一次性下发整轮任务

APP 不再采用“到一个点，再发下一个点”的逐点派单方式。

而是：

1. 一次性下发整轮有序路线任务
2. ROS 自主推进任务执行
3. APP 主要负责：
   - 用户交互
   - 跳步
   - 播报
   - 状态展示

### 2.3 点位分两种角色

每个点位都需要显式区分：

1. `task`
   - 任务点
   - 有业务语义
   - 可作为跳步目标
   - 可触发播报
   - 完成后推进主任务进度
2. `transit`
   - 辅助点 / 途经点
   - 无讲解语义
   - 不触发播报
   - 不作为任务完成点
   - 不推进主任务索引

### 2.4 正常执行规则

如果路线中存在：

```text
10(task) -> 11(transit) -> 12(transit) -> 13(task)
```

则从 `10` 到 `13` 的默认执行效果应为：

```text
10 -> 11 -> 12 -> 13
```

其中：

1. `11/12` 由 ROS 自动吸收进入执行段
2. `11/12` 不播报
3. `11/12` 不等待
4. `11/12` 不推进主任务进度
5. `13` 才是本段真正的目标任务点

### 2.5 跳步规则

如果当前存在：

```text
7(task) -> 8(task) -> 9(task) -> 10(task) -> 11(transit) -> 12(transit) -> 13(task) -> 14(task) -> 15(task)
```

当用户从 `7` 跳到 `15` 时，正确语义是：

```text
7 -> 11 -> 12 -> 15
```

不是：

```text
7 -> 8 -> 9 -> 10 -> 13 -> 14 -> 15
```

也就是说：

1. 中间 `task` 点不执行
2. 中间 `transit` 点自动吸收
3. 吸收时严格按顺序执行
4. 最终目标是目标 `task` 点

### 2.6 跳步完成后的续走规则

跳到哪个 `task` 点，哪个 `task` 点完成后，就从它继续沿主任务序列向后执行。

示例：

1. `A -> D`
   - `D` 完成后继续 `E`
2. `F -> B`
   - `B` 完成后继续 `C`

不会回头补中间被跳过的任务点。

### 2.7 播报协同规则

播报只针对 `task` 点。

闭环规则为：

1. ROS 到达需要播报的 `task` 点
2. ROS 推送 `broadcast_requested`
3. APP 执行播报
4. APP 播报完成后回传 `broadcast_finished`
5. ROS 收到后才继续执行

`transit` 点不进入播报闭环。

### 2.8 当前段中再次跳步的重建规则

这里需要明确一个关键语义。

假设当前执行段为：

```text
7(task) -> 11(transit) -> 12(transit) -> 15(task)
```

如果机器人已经通过了 `11`，此时再次收到新的跳步命令，新的执行段不能简单按“锚点 task 到目标 task”整段重建。

应遵循：

1. 新跳步应基于机器人当前物理位置重建
2. 当前段中已经通过的 `transit` 不应重新加入
3. 当前段中尚未通过的剩余点，若仍位于新目标的顺序区间内，则可继续保留
4. 新段应从“当前位置 + 剩余未通过点 + 新目标 task”构建，而不是从历史锚点重新起跑

这里再补一条实现含义：

1. “当前位置”不需要额外创建一个临时 waypoint
2. Nav2 action 会自然从机器人当前 pose 起步
3. 重建后的 `execution_waypoint_ids` 只需要保存：
   - 剩余需要执行的 `transit`
   - 最终目标 `task`

一句话说：

**再次跳步时要面向“当前剩余执行路径”重建，而不是面向“原始整段”重建。**

### 2.9 正向 / 反向跳步需要 direction-aware

路线任务中的 `transit` 收集逻辑不能只写成一个默认正向区间函数。

必须明确：

1. 正向跳步
   - 当前顺序索引小于目标顺序索引
   - 只吸收当前索引到目标索引之间的 `transit`
   - 执行顺序按原路线正向排列
2. 反向跳步
   - 当前顺序索引大于目标顺序索引
   - 只吸收目标索引到当前索引之间的 `transit`
   - 执行顺序需要按反向路径处理

一句话说：

**`collect_transit_waypoints_between_tasks()` 必须带 direction 语义，不能拿同一份正向列表同时服务正向和反向跳步。**

### 2.10 播报等待中跳步的语义

当系统处于 `WAITING_BROADCAST` 时收到跳步，需要明确：

1. 若 `interrupt_broadcast = true`
   - 当前播报等待可被打断
   - 清理当前等待播报状态
   - 切换到新的执行段
2. 若 `interrupt_broadcast = false`
   - 第一版先不实现挂起跳步队列
   - 只保留协议字段和日志
   - 可返回“暂不支持”
   - 或按当前策略拒绝

第一版建议明确收窄为：

1. 完整支持 `interrupt_broadcast = true`
2. 暂不实现 `interrupt_broadcast = false` 的“播报结束后自动执行挂起跳步”

这样可以避免 `WAITING_BROADCAST` 与 `pending_jump_request` 组合导致状态机复杂度过高。

### 2.11 跳步目标合法性必须由 ROS 兜底

虽然 APP UI 应该只允许用户选择 `task` 点作为跳步目标，但 ROS 侧仍必须兜底。

规则应为：

1. `jump_to_waypoint.target_waypoint_id` 必须是 `task`
2. 如果目标点不存在
   - 拒绝跳步
   - 返回错误 ack
   - 保持当前任务状态不变
3. 如果目标点是 `transit`
   - 拒绝跳步
   - 返回错误 ack
   - 保持当前任务状态不变

第一版可以先不单独推 `jump_rejected` 事件，但内部和 ack 语义必须明确。

### 2.12 route task 结束条件和清理动作

路线任务除了执行中逻辑，还要定义结束条件。

建议结束条件为：

1. 最后一个 `task` 已到达
2. 如果该点需要播报，则已收到对应 `broadcast_finished`
3. 没有剩余 `active_segment`

结束时建议：

1. 发布 `route_task_completed`
2. 清理 `active_route_task`
3. 清理 `awaiting_broadcast`
4. 清理 `active_segment`
5. 清理 `pending_jump_request`
6. 保留必要的最后任务摘要用于 UI 展示和日志

这一步很重要，因为它能避免任务结束后继续响应旧 `broadcast_finished` 或旧 `jump_to_waypoint`。

### 2.13 重复命令、旧 session 和过期回调的处理

除了正常流程，还建议提前定义幂等性和过期输入的处理原则。

建议统一规则：

1. 旧 `task_session_id` 的命令一律拒绝或忽略
2. route task 已完成后收到旧 `broadcast_finished` 一律忽略
3. route task 已完成后收到旧 `jump_to_waypoint` 一律拒绝
4. 重复收到同一个 `broadcast_finished`
   - 若当前不在对应等待态，忽略或返回幂等成功
5. 跳到当前目标 `task`
   - 可直接返回“已是当前目标”
6. 跳到当前已完成的 anchor `task`
   - 应按当前任务状态给出明确响应，不允许打乱主进度
7. 旧 Nav2 goal 的 result 回调
   - 不能污染新的执行段状态

一句话说：

**所有重复命令、旧 session 命令和过期 goal 回调都必须被隔离，不能影响当前生效中的 route task。**

## 3. 当前仓库链路理解

### 3.1 APP 到 ROS 的导航命令链路

当前仓库里的导航命令主链路判断如下：

1. APP 通过 websocket 发命令到 `websocket_server`
2. `websocket_server` 把导航控制消息发布到 `/app/navigation_command`
3. `dynamic_waypoints_manager` 订阅 `/app/navigation_command`
4. `dynamic_waypoints_manager` 再包装成 `/navigation/requests`
5. `navigation_state_manager` 或 `navigation_state_manager_recoverable` 订阅 `/navigation/requests`
6. 状态管理器执行导航并管理当前 Nav2 goal 生命周期
7. 状态管理器把状态发布到 `/navigation/status`
8. `data_integration_node_recoverable` 订阅 `/navigation/status`
9. `data_integration` 再把关键状态推送给 APP

### 3.2 当前各层职责

当前更合理的职责边界是：

1. `websocket_server`
   - 协议入口
   - 字段透传
2. `dynamic_waypoints_manager`
   - 点位数据保管
   - 最小必要校验
   - 请求转发
3. `navigation_state_manager`
   - 路线任务状态机
   - 跳步语义
   - transit 吸收逻辑
   - 播报等待逻辑
   - Nav2 goal 生命周期管理
4. `data_integration_node_recoverable`
   - 关键状态事件实时推送

因此：

1. 不建议把跳步路径重建放在 websocket 层
2. 不建议把 route_task 状态机放在点位管理层
3. 核心路线任务逻辑应集中在状态管理器

## 4. 运行入口判断

### 4.1 当前仓库中存在两个应用层入口

当前已确认：

1. `navigation.launch.py`
   - 启动的是 `navigation_state_manager_recoverable`
2. `navigation_fusion.launch.py`
   - 启动的是 `navigation_state_manager`

### 4.2 最近一次真实实机主链路优先级

根据最近一次真实启动核实结果：

1. `start_navigation.sh`
   - 实际启动的是 `robot_real.launch.py`
2. `robot_real.launch.py`
   - 实际包含的是 `navigation_fusion.launch.py`
3. `navigation_fusion.launch.py`
   - 实际启动的是 `navigation_state_manager.py`

因此，当前最近一次真实实机主状态管理入口应优先按：

1. `navigation_state_manager.py`

处理。

### 4.3 当前优先结论

当前不能把：

1. `navigation_state_manager_recoverable.py`

作为第一优先级主施工入口。

更合理的优先级应为：

1. 第一优先级先改 `navigation_state_manager.py`
2. 第二优先级再把核心路线任务能力同步到 `navigation_state_manager_recoverable.py`

### 4.4 兼容性结论

虽然当前最近一次真实实机主入口应优先按普通版处理，但仓库中仍保留：

1. `navigation.launch.py`
2. `navigation_state_manager_recoverable.py`

这条链路。

因此仍需要后续做兼容补齐，避免保留链路后续失配。

## 6. 每个文件准备怎么改

### 6.1 `websocket_server.py`

#### 当前问题

当前 `navigation_control` 转发时，只保留了旧字段：

1. `waypoint_id`
2. `waypoint_ids`
3. `exhibition_ids`

这会导致新需求里的整轮任务和跳步字段在第一层就丢失。

#### 计划改动

这里主要做协议透传增强，不做业务计算。

准备增加透传字段：

1. `task_session_id`
2. `route_id`
3. `route_waypoints`
4. `target_waypoint_id`
5. `interrupt_broadcast`
6. `broadcast_id`
7. `broadcast_result`
8. `broadcast_duration_sec`
9. `reason`

准备支持透传的新命令：

1. `start_route_task`
2. `jump_to_waypoint`
3. `broadcast_finished`

#### 本文件改造原则

1. 只做字段透传
2. 不在这一层计算 transit
3. 不在这一层判断任务推进逻辑
4. 保持旧导航命令兼容

---

### 6.2 `dynamic_waypoints_manager.py`

#### 当前职责判断

当前更适合作为：

1. 点位数据保管员
2. APP 命令最小校验层
3. 向状态管理器转发请求的桥接层

#### 计划改动

##### 1. 扩展新命令校验能力

需要在 `validate_navigation_command()` 中支持：

1. `start_route_task`
2. `jump_to_waypoint`
3. `broadcast_finished`

建议校验内容如下：

1. `start_route_task`
   - 校验 `route_waypoints` 非空
   - 每个点必须有 `waypoint_id`
   - 每个点必须有 `waypoint_role`
   - `waypoint_role` 只能是 `task` 或 `transit`
2. `jump_to_waypoint`
   - 校验 `target_waypoint_id`
   - 校验 `task_session_id`
3. `broadcast_finished`
   - 校验 `task_session_id`
   - 校验 `waypoint_id`
   - 校验 `broadcast_id`

##### 2. 注意当前校验链路并未自动生效

这里有一个实现层面的关键事实需要明确：

1. 当前 `app_navigation_callback()` 收到命令后
2. 是直接调用 `send_navigation_request()`
3. 并不会自动调用 `validate_navigation_command()`

因此这里不能只写“补校验规则”，还要二选一明确落法：

1. 要么把 `validate_navigation_command()` 真正接入 `app_navigation_callback()`
2. 要么第一版先不把这里作为强校验入口，只做透传

当前更建议第一版策略是：

1. 优先先保证新字段透传
2. 只做最小必要校验
3. 不在这一层做复杂业务拦截

##### 3. 透传整轮任务字段

在 `send_navigation_request()` 中，确保新字段原样透传到状态管理器：

1. `task_session_id`
2. `route_id`
3. `route_waypoints`
4. `target_waypoint_id`
5. `interrupt_broadcast`
6. `broadcast_id`
7. `broadcast_result`
8. `broadcast_duration_sec`

##### 4. 保持点位属性透传能力

第一版不建议改 `Waypoint.msg`，优先沿用 `properties`：

1. `properties.waypoint_role`
2. `properties.need_broadcast`
3. `properties.broadcast_id`
4. `properties.broadcast_blocking`
5. `properties.stop_and_align`

#### 本文件改造原则

1. 可以理解命令结构
2. 可以做最小必要校验
3. 不能承担路线任务状态机
4. 不能承担跳步路径重建
5. 尽量少侵入旧点位逻辑

---

### 6.3 `navigation_state_manager.py`

这是当前最近一次真实实机主入口版状态管理器，也是路线任务逻辑最主要的落点。

#### 计划改动方向

##### 1. 增加 route_task 内存态

建议新增一组路线任务状态字段，至少包括：

1. `active_route_task`
2. `master_route_task_ids`
3. `ordered_route_waypoints`
4. `current_anchor_task_id`
5. `current_anchor_task_index`
6. `current_target_task_id`
7. `current_target_task_index`
8. `active_segment`
9. `awaiting_broadcast`
10. `pending_jump_request`
11. `passed_transit_waypoint_ids`
12. `current_segment_progress_index`
13. `waiting_broadcast_waypoint_id`
14. `waiting_broadcast_id`
15. `jump_interrupts_broadcast`
16. `route_task_version`
17. `active_goal_generation`

##### 2. 扩展命令分发

在 `handle_navigation_command()` 中新增：

1. `handle_start_route_task()`
2. `handle_jump_to_waypoint()`
3. `handle_broadcast_finished()`

##### 3. 建立主任务序列模型

`start_route_task` 后需要：

1. 保存完整有序 `route_waypoints`
2. 从中提取只包含 `task` 的 `master_route_task_ids`
3. 建立按原始顺序访问的路线索引
4. 初始化第一段执行段

这里要明确：

1. `master_route_task_ids` 只包含 `task`
2. `transit` 不进入主任务序列

##### 4. 实现 transit 自动吸收

建议新增辅助方法：

1. `build_active_segment()`
2. `collect_transit_waypoints_between_tasks()`
3. `get_task_index()`
4. `get_waypoint_role()`
5. `rebuild_segment_from_current_progress()`

语义要求：

1. 正常执行时自动吸收相邻任务点之间的 `transit`
2. 跳步时自动吸收锚点与目标点之间的 `transit`
3. 中间 `task` 点不执行
4. `transit` 按顺序加入
5. `transit` 不推进主任务索引
6. 当前段已通过的 `transit` 再次跳步时不能重复加入
7. 新段构建要基于当前剩余执行路径，而不是只基于历史锚点
8. 正向和反向跳步的 `transit` 收集顺序必须不同

##### 5. 实现播报闭环

到达目标 `task` 点后：

1. 如果 `need_broadcast = false`
   - 直接继续下一段
2. 如果 `need_broadcast = true`
   - 发布 `broadcast_requested`
   - 进入等待态

收到 `broadcast_finished` 后：

1. 校验当前确实在等待播报
2. 校验 `task_session_id`
3. 校验 `waypoint_id`
4. 校验 `broadcast_id`
5. 清掉等待态
6. 将当前任务点设为新的锚点
7. 继续向后执行

同时建议显式支持：

1. `interrupt_broadcast = true` 时的跳步打断
2. 第一版先不真正支持 `interrupt_broadcast = false` 的挂起跳步队列

##### 6. 发布新状态事件

至少需要支持：

1. `broadcast_requested`
2. `waypoint_passed`
3. `jump_updated`
4. `task_waypoint_completed`
5. `route_task_completed`

同时在状态摘要中补充：

1. `task_session_id`
2. `route_id`
3. `awaiting_broadcast`
4. `active_segment`
5. `current_anchor_task_id`
6. `current_target_task_id`
7. `waiting_broadcast_waypoint_id`
8. `waiting_broadcast_id`
9. `passed_transit_waypoint_ids`

##### 7. 跳步时当前 Nav2 goal 的取消与隔离

收到 `jump_to_waypoint` 后，不能只改内存态后直接发送新目标。

建议流程明确为：

1. 记录跳步请求
2. 取消当前 Nav2 goal
3. 等待取消完成或进入可切换状态
4. 构建新的 `active_segment`
5. 发送新的导航 goal
6. 推送 `jump_updated`

同时建议引入：

1. `goal generation`
2. 或 `route_task_version`

用于隔离旧 goal result 回调，避免旧目标完成结果污染新执行段。

##### 8. route task 结束和收尾

当最后一个 `task` 完成，且如有播报则闭环也结束后，需要：

1. 发布 `route_task_completed`
2. 清理 route task 运行态
3. 清理等待播报状态
4. 清理活动执行段
5. 拒绝或忽略旧 session 命令

#### 第一版实现建议

第一版先不急着接 `NavigateThroughPoses`。

建议先：

1. 用现有逐点执行能力把语义跑通
2. 确认任务推进和跳步语义正确
3. 再升级为丝滑 through

这里再补两个第一版约束建议：

1. 第一版即使使用逐点执行，也要保证“再次跳步不重复跑已通过 transit”
2. 语义正确优先于动作连续性

---

### 6.4 `navigation_state_manager_recoverable.py`

这是兼容补齐用的 recoverable 入口版状态管理器，不是当前最近一次真实实机主入口。

#### 计划改动原则

这里要做的事情，和普通版大体一致：

1. 增加 `route_task` 内存态
2. 扩展 `handle_navigation_command()`
3. 增加：
   - `handle_start_route_task()`
   - `handle_jump_to_waypoint()`
   - `handle_broadcast_finished()`
4. 实现：
   - `build_active_segment()`
   - `collect_transit_waypoints_between_tasks()`
5. 发布：
   - `broadcast_requested`
   - `waypoint_passed`
   - `jump_updated`
   - `task_waypoint_completed`
   - `route_task_completed`

#### 与普通版的区别

这里要特别注意：

1. 不要破坏已有 recoverable 恢复逻辑
2. 不要破坏已有暂停/恢复/失败态语义
3. 路线任务逻辑应尽量叠加到现有保护框架中
4. 旧 goal 回调也必须与新段隔离

#### 当前建议

当前更合理的顺序应为：

1. 先在 `navigation_state_manager.py` 完整实现
2. 再把核心逻辑同步到 recoverable 版

### 6.5 `data_integration_node_recoverable.py`

这个文件决定 APP 能不能实时收到新事件。

#### 当前问题

当前立即推送白名单里主要还是旧事件，不包含路线任务新增事件。

#### 计划改动

在 `should_push_navigation_status_immediately()` 中加入：

1. `broadcast_requested`
2. `waypoint_passed`
3. `jump_updated`
4. `task_waypoint_completed`
5. `route_task_completed`

同时确认增强状态和推送包装时，不会裁掉以下字段：

1. `task_session_id`
2. `route_id`
3. `active_segment`
4. `awaiting_broadcast`
5. `current_anchor_task_id`
6. `current_target_task_id`

这里建议前置一条：

1. 在联调 `broadcast_requested / broadcast_finished` 闭环前
2. 必须先把 `broadcast_requested` 加入立即推送白名单

否则 ROS 侧即使发出等待播报事件，APP 也可能无法实时收到，容易误判为状态机没生效。

#### 本文件改造原则

1. 保证新事件实时推送
2. 不重新定义业务语义
3. 不影响旧事件转发

## 7. 当前推荐施工顺序

建议按下面顺序做，风险最低：

### 第一步：先打通协议透传

先改：

1. `websocket_server.py`
2. `dynamic_waypoints_manager.py`

目标：

1. APP 发 `start_route_task` 时，ROS 状态管理器能完整收到 `route_waypoints`
2. APP 发 `jump_to_waypoint` 时，ROS 状态管理器能完整收到 `target_waypoint_id`
3. APP 发 `broadcast_finished` 时，ROS 状态管理器能完整收到播报相关字段

### 第二步：让 `navigation_state_manager.py` 先理解新命令

先在状态管理器里把命令入口打通：

1. `start_route_task`
2. `jump_to_waypoint`
3. `broadcast_finished`

先不追求丝滑，只让它先“能理解”。

### 第三步：先补 `broadcast_requested` 实时推送

在联调播报闭环之前，先把：

1. `broadcast_requested`

加入 `data_integration_node_recoverable.py` 的立即推送白名单。

### 第四步：先做正常路线任务闭环

先实现：

1. 整轮路线任务启动
2. 相邻任务点间自动吸收 transit
3. 到 `task` 点后推 `broadcast_requested`
4. 收到 `broadcast_finished` 再继续

先把正常路线闭环跑通，再做跳步。

### 第五步：再做任意跳步

跳步要补齐：

1. 正向跳步
2. 反向跳步
3. 中间 task 跳过
4. 中间 transit 自动吸收
5. 已通过 transit 不重复加入
6. 当前 goal 取消与旧回调隔离
7. 目标 task 完成后从该点继续向后执行

### 第六步：补齐其余实时事件推送

在 `data_integration_node_recoverable.py` 中继续补：

1. `waypoint_passed`
2. `jump_updated`
3. `task_waypoint_completed`
4. `route_task_completed`

确保 APP 能实时看到路线任务关键事件。

### 第七步：最后再做丝滑 through

第一版语义正确后，再考虑：

1. `NavigateThroughPoses`
2. transit 无痕 through
3. task 最终停靠与对齐

### 第八步：最后同步到 recoverable 版

等主链路稳定后，再把核心逻辑同步到：

1. `navigation_state_manager_recoverable.py`

## 8. 当前不建议优先做的事

为了降低风险，当前不建议一开始就做下面几件事：

### 8.1 不建议先改 `Waypoint.msg`

第一版优先复用 JSON 和 `properties` 透传，减少：

1. 消息定义变更
2. 编译依赖影响
3. 旧链路兼容风险

### 8.2 不建议把 `task/transit` 混进旧 `WaypointType`

现有 `WaypointType` 语义是：

1. `navigation_target`
2. `exhibition_point`
3. `obstacle_point`
4. `charging_point`
5. `rest_point`
6. `landmark_point`

而这次的 `task/transit` 是另一套维度。

当前更建议：

1. 旧 `type` 保持不动
2. 新语义通过 `properties.waypoint_role` 承载

### 8.3 不建议一开始就重构整个旧多点导航框架

更稳妥的方式是：

1. 保留现有单点/多点/展台导航能力
2. 在旁边增加一套 `route_task` 逻辑
3. 先实现新能力，不破坏旧入口

### 8.4 不建议第一版就完整实现挂起跳步队列

第一版如果同时做：

1. `interrupt_broadcast = true`
2. `interrupt_broadcast = false`
3. 待播报结束自动执行挂起跳步

状态机会明显膨胀。

更稳妥的做法是：

1. 第一版只完整支持 `interrupt_broadcast = true`
2. `false` 先保留字段和日志

## 9. 当前最重要的风险点

### 风险 1：主入口判断反了

如果把 `navigation_state_manager_recoverable.py` 当成当前主施工入口，就可能出现：

1. 大量改动落在兼容链路
2. 最近一次真实实机主链路却没有先受益
3. 现场表现成“改了很多但没优先生效”

### 风险 2：websocket 新字段没透传

如果 `route_waypoints`、`task_session_id`、`target_waypoint_id`、`broadcast_id` 在 websocket 层就丢了，状态管理器后面写得再完整也跑不起来。

### 风险 3：`broadcast_requested` 没进实时推送白名单

如果在联调播报闭环前没有先把：

1. `broadcast_requested`

加入立即推送白名单，APP 侧很容易误判为“ROS 没进等待播报态”。

### 风险 4：把 transit 推进了主任务索引

这是路线任务语义错误的高风险点。

必须保证：

1. `transit` 只作为 through point
2. 只有 `task` 完成后才推进主任务进度

### 风险 5：再次跳步把已通过 transit 又跑一遍

如果不显式记录当前段 through 进度，后续实现很容易：

1. 从历史锚点重建整段
2. 把已经通过的 `transit` 再次加入
3. 造成路径重复和状态错乱

因此必须补充：

1. 已通过 `transit` 记录
2. 当前段剩余执行列表
3. 基于当前位置的重建逻辑

### 风险 6：旧 Nav2 goal 回调污染新执行段

如果跳步时只发送新 goal、不隔离旧 goal 回调，就可能出现：

1. 旧 goal 尚未完全结束
2. 新 goal 已开始执行
3. 旧 goal 的到点或完成回调晚到
4. 把新执行段误判为旧目标完成

因此必须有：

1. goal cancel 流程
2. goal generation 或 route_task_version
3. 旧回调忽略策略

### 风险 7：任务结束后旧命令继续生效

如果不显式定义 route task 结束清理，就可能出现：

1. 最后一个 task 已经结束
2. 旧 `broadcast_finished` 还在继续改变状态
3. 旧 `jump_to_waypoint` 还在继续打断空任务

因此任务结束必须：

1. 发布 `route_task_completed`
2. 清掉运行态
3. 拒绝或忽略旧 session 命令

### 风险 8：第一版实现范围膨胀

如果第一版同时追求：

1. 正常路线闭环
2. 正反向跳步
3. 已通过 transit 重建
4. 广播等待打断
5. 挂起跳步队列
6. `NavigateThroughPoses`

很容易把状态机复杂度推高，增加返工概率。

因此第一版应坚持：

1. 语义正确优先
2. 复杂并发场景收窄
3. 丝滑体验后置

---

## 10. 当前结论

基于目前文档、代码阅读和两轮审查反馈，当前改造思路可以总结为：

1. 新需求本质是“整轮路线任务”，不是旧版多点导航的小修补
2. 路线任务核心语义是：
   - `task` 推进主任务
   - `transit` 只做 through
3. 跳步时直接跳向目标 `task`
4. 中间 `task` 跳过
5. 中间 `transit` 自动按顺序吸收
6. 到 `task` 点后通过 `broadcast_requested / broadcast_finished` 做播报闭环
7. 跳步目标完成后，从该点继续向后执行
8. 当前段中再次跳步时，要基于当前位置和剩余未通过点重建，不能重复跑已通过 `transit`
9. “当前位置”只是 Nav2 的自然起点，不需要创建虚拟 waypoint
10. 正向和反向跳步必须按 direction-aware 规则收集 `transit`
11. 第一版先完整支持 `interrupt_broadcast = true`，暂不实现 `false` 的挂起跳步队列
12. route task 结束后必须发布 `route_task_completed` 并清理运行态
13. 重复命令、旧 session 命令和旧 goal 回调必须被隔离

从代码落点上看：

1. `websocket_server.py` 负责把新字段透传进 ROS
2. `dynamic_waypoints_manager.py` 负责保管点位和转发请求
3. `navigation_state_manager.py` 负责当前主链路的路线任务状态机和 goal 生命周期管理
4. `data_integration_node_recoverable.py` 负责把新状态事件实时推给 APP
5. `navigation_state_manager_recoverable.py` 作为兼容链路补齐项

从施工顺序上看：

1. 先打通协议
2. 再在 `navigation_state_manager.py` 落状态机骨架
3. 先确保 `broadcast_requested` 已进入实时推送白名单
4. 先跑正常闭环
5. 再做跳步
6. 再补其余实时事件推送
7. 最后做丝滑 through
8. 最后同步到 recoverable 版

本轮修正后，当前需要特别保留四条关键结论：

1. 当前最近一次真实实机主入口应优先按 `navigation_state_manager.py` 处理
2. 跳步重建必须显式处理“当前段已通过 transit 不重复加入”的语义
3. 播报闭环联调前，必须先确保 `broadcast_requested` 已进入实时推送白名单
4. 跳步不仅要重建内存态，还必须处理当前 Nav2 goal 取消和旧回调隔离

如果这份修正版思路文档和你的预期一致，下一步就可以再审一轮，然后继续细化成“具体改哪些函数、新增哪些字段、事件 payload 长什么样”的实施清单。
