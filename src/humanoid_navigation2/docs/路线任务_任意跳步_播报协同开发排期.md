## 2. 排期假设

本排期按以下前提估算：

1. ROS 开发 1 人
2. app 开发 1 人
3. 双方可以并行开发
4. 联调时两侧都能及时响应
5. 现有工作区和 app 工程都允许新增协议字段和状态机逻辑

本排期目标分为两档：

1. `10 个工作日`
   - 产出第一版完整联调版本
   - 主流程可跑通，可演示，可做室内联调
2. `15 个工作日`
   - 产出较稳定版本
   - 能覆盖更多异常和现场测试场景

## 3. 版本目标定义

### 3.1 10 个工作日版本目标

需要满足：

1. app 一次下发整轮路线任务
2. ROS 自主推进路线，不再依赖 app 逐点下发
3. 到播报点位后，ROS 通知 app 可以播报
4. app 播报完成后，通知 ROS 继续执行
5. 支持任意前跳和后跳
6. 跳步时中间点自动降级为途经点
7. 跳步中间点不停车、不对齐、不播报
8. 基于 `NavigateThroughPoses` 实现第一版丝滑通过

### 3.2 15 个工作日版本目标

在 10 天版本基础上补强：

1. 正在播报时跳步更稳定
2. 连续多次跳步更稳定
3. 播报超时处理
4. 断线重连后的状态恢复
5. 重复命令和旧任务命令防护
6. 实机参数调优

## 4. 总体时间线

### 第 1-2 天：协议与骨架

ROS 侧：

1. 扩展 websocket 到 ROS 的导航控制字段透传
2. `dynamic_waypoints_manager.py` 新增：
   - `start_route_task`
   - `jump_to_waypoint`
   - `broadcast_finished`
3. `navigation_state_manager.py` 增加路线任务数据结构骨架
4. 增加新的状态事件定义：
   - `route_task_started`
   - `waypoint_passed`
   - `broadcast_requested`
   - `route_jump_replanned`

app 侧：

1. 新建任务状态对象
2. 支持发送 `start_route_task`
3. 支持发送 `jump_to_waypoint`
4. 支持发送 `broadcast_finished`
5. 支持接收 `broadcast_requested`

联调目标：

1. app 能发新协议
2. ROS 能收到并打印核心字段
3. ROS 能推 `broadcast_requested` 的假消息给 app

### 第 3-4 天：正常任务 + 播报闭环

ROS 侧：

1. 实现 `route_task` 基础状态机
2. 加载 `master_route`
3. 到正式停靠点后进入 `WAITING_BROADCAST`
4. 收到 `broadcast_finished` 后继续下一段
5. 打通导航事件推送到 websocket

app 侧：

1. 收到 `broadcast_requested` 后开始播报
2. 播报结束后回发 `broadcast_finished`
3. 新增任务态和播报态 UI 展示
4. 实现 `broadcast_id` 到本地播报资源的映射

联调目标：

1. 正常整轮任务不再逐点下发
2. 到播报点后能停下
3. app 播报完成后 ROS 继续

### 第 5-6 天：任意跳步主逻辑

ROS 侧：

1. 实现 `jump_to_waypoint`
2. 支持正向截段和反向截段
3. 中间点执行属性改写为 `pass_through`
4. 目标点执行属性保持 `target_stop`
5. 当前导航动作取消并切新段

app 侧：

1. UI 增加跳步入口
2. 发送 `jump_to_waypoint`
3. 收到 `route_jump_replanned` 后刷新当前子路线
4. 播报中跳步时停止本地播报并切换状态

联调目标：

1. `A -> D`
2. `D -> B`
3. `G -> C`
均能按原始完整路线正确重建执行段

### 第 7-8 天：丝滑执行与事件细化

ROS 侧：

1. 引入 `NavigateThroughPoses`
2. `active_segment` 转为 through poses
3. 中间点以途经点方式通过
4. 最终目标点保持正式停靠
5. 必要时采用：
   - 先 through poses
   - 再最终停靠对齐

app 侧：

1. 增加“途经点”和“正式停靠点”区分展示
2. 增加“当前跳步目标点”展示
3. 优化跳步过程中的任务路线 UI

联调目标：

1. 跳步时中间点明显比逐点任务更顺
2. 中间点不播报
3. 最终目标点仍能停靠播报

### 第 9 天：异常与保护

ROS 侧：

1. 播报等待超时保护
2. 重复 `broadcast_finished` 去重
3. 旧任务命令拦截
4. 跳步中断播报保护
5. 当前任务结束后旧命令无效

app 侧：

1. 过期事件忽略
2. 播报资源缺失时跳过策略
3. 重复点击跳步节流
4. 本地状态恢复与重置

联调目标：

1. 常见误操作不会把状态机打乱
2. 常见缺资源场景能优雅降级

### 第 10 天：联调回归与演示验收

ROS 侧：

1. 补日志
2. 补调试输出
3. 梳理验收脚本和测试步骤

app 侧：

1. 补调试面板或日志页
2. 展示当前 `task_session_id`
3. 展示当前 `broadcast_id`

联调用例：

1. 正常路线 `A-B-C-D`
2. A 点播报后继续
3. A 到 B 路上跳到 D
4. A 点播报中跳到 D
5. D 再跳回 B
6. 跳步后中间点只途经不播报
7. 播报完成消息重复发送不会出问题

## 9. 风险点

1. `NavigateThroughPoses` 的实机表现可能需要额外调参
2. 反向跳步可能受现场路线与业务规则限制
3. websocket server 现有字段透传能力不足，必须先补
4. 旧逻辑和新逻辑并存时，建议加功能开关
5. 正在播报时跳步是高风险边界场景，必须重点测试

## 10. 验收标准

### 10.1 基础验收

1. app 一次下发整轮路线任务成功
2. ROS 自主推进，不再依赖 app 逐点派发
3. 到播报点可停下等待
4. app 播报完后 ROS 自动继续

### 10.2 跳步验收

1. 支持前跳
2. 支持后跳
3. 跳步后中间点不播报
4. 跳步后最终目标点正常停靠播报

### 10.3 丝滑验收

1. 跳步中间点不出现明显“停车 + 等待 + 播报”
2. 中间点只作为途经点通过
3. 最终点才正式停靠

### 10.4 稳定性验收

1. 重复 `broadcast_finished` 不会打乱状态
2. 过期任务事件不会污染当前任务
3. 播报中跳步不会卡死
4. 任务结束后旧命令无效

## 12. 排期结论

建议对外采用以下说法：

1. `10 个工作日`
   - 交付第一版完整联调版本
2. `15 个工作日`
   - 交付较稳定、适合现场反复测试的版本

如果中途发现：

1. `NavigateThroughPoses` 实机效果与预期差距较大
2. 现场业务不允许反向跳步
3. app 侧现有状态机耦合太重

则需要适当顺延并单独评估风险项。
