## 2. 排期基准与目标

### 2.1 人力假设

本排期按以下前提估算：

1. ROS 开发 1 人
2. APP 开发 1 人
3. 两侧可并行开发
4. 联调阶段双方可同步响应
5. 当前工程允许新增协议字段、状态机与 UI 字段

### 2.2 版本目标

分两档推进：

1. `10 个工作日`
   - 产出第一版完整联调版本
   - 主流程跑通
   - 可演示
   - 可做室内联调与基础实机验证
2. `15 个工作日`
   - 产出较稳定版本
   - 覆盖更多异常与现场场景
   - 完成主要体验调优

## 3. 当前最终需求对应的开发目标

10 天版本至少需要满足：

1. APP 一次性下发整轮路线任务
2. 每个点位支持 `task / transit` 类型
3. ROS 自主推进主任务，不再依赖 APP 逐点下发
4. 正常执行时自动吸收相邻任务点之间的中间辅助点
5. 跳步时直接跳到目标任务点，不执行中间任务点
6. 跳步时自动吸收当前点与目标点之间的中间辅助点
7. 辅助点不播报、不等待、不做最终停靠对齐
8. 任务点到达后由 ROS 通知 APP 开始播报
9. APP 播报完成后通知 ROS 继续
10. 跳步目标完成后从该目标任务点继续沿主任务序列往后执行

15 天稳定版在此基础上补强：

1. 正在播报时跳步更稳定
2. 连续多次跳步更稳定
3. 播报超时与异常恢复更稳
4. 断线重连后状态恢复更清晰
5. 现场参数与 through 体验更好

## 4. 总体时间线

### 第 1-2 天：协议、模型、骨架

ROS 侧：

1. 扩展 websocket 导航控制字段透传
2. `dynamic_waypoints_manager.py` 新增：
   - `start_route_task`
   - `jump_to_waypoint`
   - `broadcast_finished`
3. `navigation_state_manager.py` 增加 `route_task` 数据结构骨架
4. 支持 `route_waypoints` 中的 `waypoint_role`
5. 增加状态事件定义：
   - `route_task_started`
   - `waypoint_passed`
   - `broadcast_requested`
   - `jump_updated`
   - `task_waypoint_completed`

APP 侧：

1. 路线点位模型增加 `waypoint_role`
2. 支持配置 `task / transit`
3. 支持发送：
   - `start_route_task`
   - `jump_to_waypoint`
   - `broadcast_finished`
4. 支持接收：
   - `broadcast_requested`
   - `waypoint_passed`
   - `jump_updated`

联调目标：

1. APP 能发新协议
2. ROS 能收到并解析点位类型
3. ROS 能推送可播报假消息给 APP

### 第 3-4 天：正常任务闭环

ROS 侧：

1. 实现 `route_task` 基础状态机
2. 建立主任务序列 `master_route_task_ids`
3. 实现相邻任务点之间自动吸收辅助点
4. 到任务点后进入 `WAITING_BROADCAST`
5. 收到 `broadcast_finished` 后继续下一段

APP 侧：

1. 收到 `broadcast_requested` 后开始播报
2. 播报结束后回发 `broadcast_finished`
3. 增加任务态和播报态 UI 展示
4. 完成 `broadcast_id` 与本地资源映射

联调目标：

1. 正常整轮任务不再逐点下发
2. `10(task) -> 11(transit) -> 12(transit) -> 13(task)` 可正确执行
3. `11/12` 不播报、不停顿
4. `13` 到达后可播报并在播报完成后继续

### 第 5-6 天：任意跳步主逻辑

ROS 侧：

1. 实现 `jump_to_waypoint`
2. 支持前跳与后跳
3. 跳步时直接切换目标任务点
4. 自动收集当前点与目标点之间的中间辅助点
5. 重建 `active_segment`
6. 取消当前导航动作并切换新执行段

APP 侧：

1. UI 增加跳步入口
2. 跳步目标只允许选择 `task` 点
3. 发送 `jump_to_waypoint`
4. 收到 `jump_updated` 后刷新当前目标与执行段展示
5. 播报中跳步时停止本地播报并切换状态

联调目标：

1. `A -> D`
2. `D -> B`
3. `G -> C`
均能正确切换目标任务点

重点确认：

1. 中间任务点不执行
2. 中间辅助点自动吸收
3. 跳步目标完成后从该点继续向后执行

### 第 7-8 天：丝滑执行与体验细化

ROS 侧：

1. 接入 `NavigateThroughPoses`
2. `active_segment` 转为 through poses 执行
3. 辅助点以 through point 无痕通过
4. 最终目标任务点保持正式停靠
5. 必要时拆成：
   - through poses 路段
   - 最终停靠与姿态对齐

APP 侧：

1. 区分展示任务点与辅助点
2. 展示当前跳步目标点
3. 展示本次执行段中的自动吸收辅助点
4. 优化路线执行页文案与状态表现

联调目标：

1. 辅助点通过更丝滑
2. 辅助点不播报
3. 辅助点不过度停顿
4. 目标任务点仍能正常停靠播报

### 第 9 天：异常与保护

ROS 侧：

1. 播报等待超时保护
2. 重复 `broadcast_finished` 去重
3. 旧任务命令拦截
4. 跳步打断播报保护
5. 当前任务结束后旧命令失效

APP 侧：

1. 过期事件忽略
2. 播报资源缺失时跳过策略
3. 重复点击跳步节流
4. 本地状态恢复与重置

联调目标：

1. 常见误操作不会打乱状态机
2. 播报异常场景可降级
3. 跳步和播报并发场景可收敛

### 第 10 天：联调回归与演示验收

ROS 侧：

1. 补日志
2. 补调试输出
3. 梳理验收步骤与测试脚本

APP 侧：

1. 补调试页面或日志入口
2. 展示当前 `task_session_id`
3. 展示当前 `broadcast_id`

联调用例：

1. 正常路线 `10 -> 11 -> 12 -> 13`
2. 到任务点后播报再继续
3. 路上从 `7` 跳到 `15`
4. 播报中从 `A` 跳到 `D`
5. 从 `F` 跳回 `B`
6. 跳步后自动吸收中间辅助点
7. 跳步目标完成后从目标点继续向后执行
8. 重复发送播报完成消息不会出问题

## 6. ROS 侧详细任务拆分

### 6.1 协议接入层

涉及文件：

1. `src/humanoid_websocket/humanoid_websocket/websocket_server.py`
2. `src/humanoid_navigation/humanoid_navigation/dynamic_waypoints_manager.py`

任务项：

1. 透传 `task_session_id`
2. 透传 `route_id`
3. 透传 `route_waypoints`
4. 透传 `waypoint_role`
5. 透传 `target_waypoint_id`
6. 透传 `broadcast_id`

### 6.2 任务状态机

任务项：

1. 增加 `route_task` 对象
2. 维护 `master_route_task_ids`
3. 维护当前目标任务点索引
4. 维护 `active_segment`
5. 维护 `awaiting_broadcast`

### 6.3 辅助点吸收逻辑

任务项：

1. 正常执行时收集相邻任务点之间的辅助点
2. 跳步时收集当前点与目标点之间的辅助点
3. 中间任务点在跳步时不执行
4. 辅助点只作为 through point

### 6.4 导航执行层

任务项：

1. `active_segment` 转为 through poses
2. 辅助点无痕通过
3. 目标任务点最终停靠
4. 到任务点后触发播报等待

### 6.5 状态推送层

任务项：

1. 推送 `broadcast_requested`
2. 推送 `waypoint_passed`
3. 推送 `jump_updated`
4. 推送 `task_waypoint_completed`

## 7. APP 侧详细任务拆分

### 7.1 数据模型

任务项：

1. 点位模型增加 `waypoint_role`
2. 区分 `task / transit`
3. 增加播报属性模型
4. 增加整轮任务 session 模型

### 7.2 协议与状态

任务项：

1. 发送 `start_route_task`
2. 发送 `jump_to_waypoint`
3. 发送 `broadcast_finished`
4. 接收 `broadcast_requested`
5. 接收 `waypoint_passed`
6. 接收 `jump_updated`
7. 接收 `task_waypoint_completed`

### 7.3 播报联动

任务项：

1. 根据 `broadcast_requested` 启动播报
2. 播报完成回传 `broadcast_finished`
3. 跳步时打断本地播报
4. 播报异常时执行降级策略

### 7.4 UI 改造

任务项：

1. 点位配置页增加点位类型选择
2. 跳步弹窗只展示任务点
3. 路线执行页展示当前目标任务点
4. 路线执行页展示辅助点 through 状态

## 8. 推荐排期结论

如果目标是尽快做出第一版可演示版本，建议按 `10 个工作日` 执行。

如果目标是直接上较稳定版本，建议按 `15 个工作日` 执行，并预留至少 2 天实机现场调优空间。

结合当前需求复杂度，更稳妥的判断是：

1. `10 天` 可以做出完整联调版
2. `15 天` 更接近可稳定交付版
