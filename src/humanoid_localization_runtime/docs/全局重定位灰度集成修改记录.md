# 全局重定位灰度集成修改记录

## 2026-07-19：三级模式与 RO 后提交链路

### 修改目标

把全局重定位算法的运行能力与正式系统控制权分离。系统统一使用
`integration_mode` 管理副作用，不再依赖 `dry_run` 和 `auto_apply` 两个容易冲突的布尔组合。

模式参数由定位运行层 YAML 统一提供：

```text
localization_trust_supervisor.ros__parameters.integration_mode: off|shadow|enforce
global_relocalization_coordinator.ros__parameters.integration_mode: off|shadow|enforce
```

默认值为 `shadow`。

### 模式权限

| 能力 | off | shadow | enforce |
|---|---:|---:|---:|
| 自动发起全局搜索 | 否 | 是 | 是 |
| 验证候选合同 | 否 | 是 | 是 |
| 发布诊断和结果 | 是 | 是 | 是 |
| 写入正式 RO | 否 | 否 | 是 |
| 授权正式 bridge | 否 | 否 | 是 |
| 自动暂停/恢复路线 | 否 | 否 | 是 |

`enable_global_relocalization` 继续只控制算法节点和协调器是否启动；
`integration_mode` 控制节点启动后是否拥有正式系统副作用权限。

### 三条运行链路

#### off

```text
Fast-LIO/雷达 -> RO -> bridge -> map->odom -> TF -> 导航
```

协调器不发起全局搜索，不写 RO 和 bridge，路线层不因全局恢复状态自动暂停。

#### shadow

```text
定位异常诊断 -> 全局搜索 -> 候选合同验证 -> shadow结果记录
正式链路仍为 RO -> bridge -> TF -> 导航
```

shadow 会保留 `startup_requires_global_relocalization` 和
`recovery_requires_global_relocalization` 诊断字段，但
`localization_recovery_required=false`，路线运行层也会校验模式，因此不会取消 goal、停车或自动续跑。

#### enforce

```text
定位监督要求恢复
-> 路线暂停并缓存当前 active segment
-> 全局候选通过 attempt/map/stamp 合同验证
-> 候选只注入 RO
-> 等待同时间戳 ro_trusted_global_anchor_commit
-> 发布审核后的 map->odom 给 bridge
-> bridge ACCEPTED global_recovery
-> 连续 RO normal 和 trust 稳定帧确认
-> 恢复缓存路线
```

RO trusted 超时、bridge 接受超时或上层终止都会取消本次尝试；不会绕过 RO 直接提交 bridge。

## 2026-07-20：RO 精修提交、抖动防误触发与完整 TF 验收

### 修复的闭环漏洞

1. 全局候选不再绕过 RO 精匹配直接授权 bridge。RO 保留全局候选锚点，在至少 2.0 s 后对 5 帧不同点云帧的 normal match 做一致性校验，只有 `map->odom` 波动不超过 0.05 m/3 deg 才发布 trusted commit 和 RO 精修结果。
2. 协调器同时校验 global attempt/map/candidate stamp 与 RO `anchor_stamp`，再按 RO commit stamp 取对应的 refined `map->odom`。原始全局 `map->odom` 不再作为 bridge 发布值。
3. 单次 `HOLD large_jump` 只记录观测，不立即停车。只有 bridge 进入 `DEGRADED`，或 HOLD 持续至少 3.0 s 且出现至少 3 次独立更新，才进入强制恢复。
4. 恢复稳定计数改为使用 `ro_verification_epoch`。同一条 RO 状态的重复发布不能凑够恢复帧数。
5. 路线层在 enforce 中暂停并缓存当前路线进度；定位恢复后只续发未完成点。上层在恢复期间终止任务时，不会自动重启。

### 正式成功口径

压测只在以下链路全部完成时计为成功：

```text
全局候选合同通过
-> RO trusted commit
-> 协调器发布 RO refined map->odom
-> bridge ACCEPTED global_recovery
-> map->odom TF 有至少 20 个连续稳定样本
-> 样本位置误差全部 <= 0.20 m，且无 >0.10 m/3 deg 跳变
```

### Bag 困难候选专项验证

本节不是随机全量成功率。输入是从历史多假设、单源召回和 RO 交接难例中抽取的 40 个已接受候选，用于对新增安全门控做极限验证，不能代表随机启动点的总体通过率。

验证使用真实 bag 点云、正式 RO 配置和 bridge，每次两个隔离 ROS domain 并行；CPU 百分比是两个并发进程组的多核峰值，不是单核占用。

| 样本组 | 完整 TF 成功 | <=5 cm | <=10 cm | <=20 cm | bridge 后误发布/不稳定 | TF 最大误差 | 峰值 CPU | 峰值 RSS |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 冷启动第一组 10 点 | 8/10 | 7 | 8 | 8 | 0 | 0.058 m | 566% | 236 MB |
| 冷启动留出组 10 点 | 4/10 | 3 | 3 | 4 | 0 | 0.145 m | 585% | 238 MB |
| 恢复第一组 10 点 | 9/10 | 8 | 9 | 9 | 0 | 0.052 m | 554% | 235 MB |
| 恢复留出组 10 点 | 2/10 | 1 | 1 | 2 | 0 | 0.154 m | 531% | 235 MB |

在这个困难候选专项集内，冷启动为 12/20（60%），恢复为 11/20（55%）。所有已通过 bridge 的 23 例都满足 20 cm 稳定 TF 口径，未出现误接受或发布后跳变。失败样本包括两类：一类只有 0-4 个连续 NORMAL 帧；另一类虽有较多 NORMAL 帧，但 refined `map->odom` 在 0.05 m/3 deg 门槛内不稳定，因此未提交。

### 与历史 98%-100% 指标的区别

历史有两类指标，需要分开：

1. `blind_safe_cluster/repeat_audit018` 的 98%-100% commit 试验：使用隔离实验分支的 atomic verified-candidate 协议。已经上游筛选的候选到达专用话题后，RO 在候选时刻零延迟提交；某些 98/98 的分母是已接纳候选，不是全部随机点。
2. 历史随机 `3x100` 完整 TF 试验：确实要求 bridge 接受和 20 帧稳定 TF，冷启动为 292/300（97.33%），恢复为 287/300（95.67%）。但该链路仍基于 atomic trusted handoff：RO commit delay 基本为 0，不要求 RO 先做当前正式代码里的 2.0 s 独立收敛和 0.05 m/3 deg refined `map->odom` 一致性证明。当时 295 个候选全部被 bridge 接受，但其中冷启动 3 例、恢复 8 例最终 TF 超过 0.20 m。

因此，随机 97.33%/95.67% 可以作为旧 atomic handoff 的总体可用率；60%/55% 只是困难候选在新安全闭环下的通过率。当前正式新闭环的随机总体成功率尚未得到，必须在同一批 seed41/42/43 随机点上重放才能公平比较。

另用真实 coordinator 跑通冷启动和恢复各 1 例，TF 尾段最大误差分别为 0.0030 m 和 0.0037 m；困难候选 1 例只有 4 帧 normal match，RO 不提交、bridge 不接受，安全拒绝。

| 随机组 | 冷启动完整成功 | 恢复完整成功 | 冷启动 RO/bridge | 恢复 RO/bridge |
|---|---:|---:|---:|---:|
| seed41 | 84/100 | 82/100 | 84/84 | 82/82 |
| seed42 | 76/100 | 76/100 | 76/76 | 77/77 |
| seed43 | 83/100 | 83/100 | 83/83 | 83/83 |
| 合计 | **243/300（81.00%）** | **241/300（80.33%）** | **243/243** | **242/242** |

冷启动 243 个成功样本中，233 个 `<=5 cm`、241 个 `<=10 cm`，最大误差 0.157 m；恢复 241 个成功样本中，217 个 `<=5 cm`、239 个 `<=10 cm`，最大误差 0.151 m。冷启动/恢复成功样本中位 TF 误差分别为 0.0036 m/0.0134 m，P95 为 0.0475 m/0.0663 m。

失败漏斗：

- 两种模式都有 5/300 没有全局候选。
- 冷启动 52/295 候选没有 RO commit：31 例最大连续 NORMAL 少于 5，21 例虽有至少 5 个 NORMAL，但未通过当前提交时间/一致性窗口。
- 恢复 53/295 候选没有 RO commit：23 例最大连续 NORMAL 少于 5，30 例未通过提交时间/一致性窗口。
- 冷启动没有 bridge 后失败。恢复有 1 例（`repeat_audit018_20260742_17971`）在 bridge 后无跳变地稳定在 0.2051 m，超过 0.20 m 门槛 5.1 mm，仍按失败计数。

RO commit 的 bag 时间延迟中位数均约 2.40 s，P95 为冷启动 2.60 s、恢复 2.50 s。单例 wall time 包含节点启动和 bag 窗口，中位数为 9.54 s/11.60 s。观测到的 RO+bridge 进程组峰值约 642% CPU、437 MB RSS；coordinator 运行在测试主进程中，未纳入该资源峰值。

与旧 atomic handoff 的 97.33%/95.67% 相比，当前正式新闭环分别下降 16.33/15.34 个百分点。安全后半段明显收紧：bridge 后超差/不稳定从旧方案的 3 例冷启动+8 例恢复降为 0+1；但 RO commit 门槛也是当前主要的成功率损失点。

### 路线与模式回归

- 冷启动不会提前下发 Nav2 goal。
- 行走中恢复会取消当前 action、发零速，并在 3 个不同 RO epoch 后续发剩余路线。
- 已通过 transit 不会重跑；只剩 task 时直接恢复 task。
- 恢复期间上层 stop 后不会续跑。
- shadow 状态不取消 goal、不发零速。

### 结论与上线边界

本次修改已补齐“RO 真精修后才提交”、“候选与 commit 相关”、“短暂抖动不误停”和“独立帧才允许恢复路线”四个安全闭环。困难候选专项证明新门控没有误发布，但不能据此推导随机总体成功率。在用同一组随机点完成新旧口径对照前，正式默认继续保持 `shadow`；`enforce` 只能用于可回退的灰度机器人。

## 2026-07-20 在线故障防抖闭环补强

### 触发权限修正

1. 路线层不再根据 `bridge_holding_last_good_tf`、`large_jump` 或其他状态文本直接停车，只响应 trust supervisor 防抖确认后的显式 `localization_recovery_required=true`。
2. large-jump 仍使用 `3.0 s + 至少 3 次更新`，bridge 直接进入 `DEGRADED` 时立即确认。单次或短时 HOLD 只冻结 last-good TF，不取消 Nav2 goal。
3. RO `LOST/LOW_ACCURACY` 只有连续至少 3.0 s 且包含至少 3 个不同时间戳状态帧时才锁存在线恢复；恢复为正常状态会清除未成熟观察。
4. RO 完全停止上报时不能累计状态帧，因此单独以连续陈旧 3.0 s 确认。两类 RO 在线故障只在系统曾进入过 `trusted_ro` 后启用，排除开机点云、节点未就绪和冷启动交接期。
5. 自动全局候选注入 RO 只是精配初值，不再提前清除恢复锁。只有人工显式定位，或 bridge 接受 RO 精修后的 `global_recovery`，才能解除锁存。
6. 当时一键启动 launch 透传 `global_relocalization_integration_mode`；该方式已被 2026-07-21 的统一 YAML 配置入口替代，实机默认仍为 `shadow + 真实雷达`。

### 搜索超时依据

当前正式精度层历史 P95 总耗时约 14.4-21.4 s，不叠加 2.5D 时观测最大值约 27.2 s。原 30 s 只剩约 2.8 s 调度余量；实验性叠加层曾出现 36.6 s 长尾。因此单次 attempt 调整为 45 s，最多 3 次、重试间隔 2 s 保持不变，接受精度和质量门槛均未放宽。

### 正式 enforce bag 回放

使用正式一键 launch、真实 RO/bridge/全局算法，回放 `/airy_points + /airy_imu`，地图状态和底层 Walk 状态由验证监控器提供。定位可信后发送一条四点整路线；`control` 表示显式在线恢复控制次数。

| 窗口 | 冷启动结果 | 路线下发 | bridge HOLD | control | 定位暂停 | 结论 |
|---|---|---:|---:|---:|---:|---|
| bag44 offset 600 s / 70 s | 成功，进入 `trusted_ro` | 是 | 11 | 0 | 0 | 一次暂停来自障碍物状态机，与定位无关 |
| bag45 offset 300 s / 60 s | 成功，进入 `trusted_ro` | 是 | 5 | 0 | 0 | 路线未被定位逻辑取消 |
| bag46 offset 900 s / 60 s | 未接受，保持冷启动门控 | 否 | 0 | 0 | 0 | 轨迹支持不足，45 s 后安全重试，无误放行 |
| bag46 offset 0 s / 70 s | 第二次搜索成功，进入 `trusted_ro` | 是 | 0 | 0 | 0 | 路线通过两个 transit，无定位介入 |

这四个窗口证明短时 HOLD 不再造成频繁停车，冷启动失败时也不会绕过门控下发路线。持续故障后的停车、剩余路线缓存、3 个独立 RO epoch 后续跑，以及恢复期间上层 stop 不续跑，继续由正式运行态 smoke 覆盖。

## 2026-07-20 定位可信与 Nav2 就绪竞态修复

### 问题与处理

bag46 完整回放中，定位先进入 `can_start_navigation=true`，但 Nav2 lifecycle 尚未全部 ACTIVE。路线运行层随即释放整路线；首个 task 已在到达容差内，因此直接发送最终对齐 `NavigateToPose`，该目标被尚未就绪的 `bt_navigator` 拒绝。原代码只有 `NavigateThroughPoses` 拒绝重试，最终对齐会直接判定路线失败。

本次把启动条件改为以下条件同时成立：

```text
机器人 Walk 且控制层可导航
-> 地图 ready
-> 定位可信并允许启动
-> planner_server/controller_server/behavior_server/bt_navigator 全部 ACTIVE
-> NavigateThroughPoses 与 NavigateToPose action server 均可用
-> 仅释放一次缓存的整路线
```

路线只需由上层发送一次。等待期间 `stop_route_task` 会删除缓存；Nav2 后续就绪时不会复活已终止任务。两种 Nav2 action 都使用 15 s 拒绝重试窗口，500 ms 后重试；目标一旦接受、取消或失败，重试窗口立即清理，避免污染同一路段之后的定位恢复重发。

### 修改范围

- `humanoid_route_runtime` 新增 Nav2 lifecycle `GetState` 客户端和 action readiness 门控。
- 周期状态新增 `nav2_ready`、`nav2_lifecycle_gate_required` 和各核心节点 ACTIVE 状态。
- 正式 YAML 默认启用 lifecycle 门控，拒绝重试窗口由 8 s 调整为 15 s。
- 新增 `nav2_readiness_pending_smoke.py`，覆盖等待、单次释放、最终对齐拒绝重试和等待期间终止。

### 验证结果

1. 定位已可信、Nav2 未 ACTIVE：产生 1 次 `navigation_pending`，Nav2 goal 下发数为 0。
2. 四个节点 ACTIVE 后：缓存路线只释放一次；`NavigateToPose` 模拟连续拒绝 2 次，第三次接受并完成，`route_task_completed=1`、`navigation_failed=0`。
3. 第二条路线在 pending 期间由上层 stop：`navigation_pending_cancelled=1`；Nav2 后续 ACTIVE，新增 goal 数为 0。
4. 原有定位恢复回归通过：当前 transit 段暂停后只续发剩余点；全部 transit 已通过时只恢复最终 task；均需要 3 个独立 RO epoch 才恢复。
5. `humanoid_route_runtime` 定向构建通过。

### bag46 正式启动窗口复验

导航栈停止后，使用当前 Todesk 工作区正式一键 launch、`enforce` 模式和 bag46 前段重新复现原竞态：

- wall 90.912 s：定位可信，上层发送 25 点整路线。
- wall 90.913 s：Nav2 尚未启动，路线进入 `navigation_pending`，没有 action goal 下发。
- wall 95.958 s：四个核心 lifecycle 节点全部 ACTIVE，两种 action 可用，缓存路线释放；等待约 5.045 s。
- `bt_navigator` 接受 `NavigateToPose` 并进入 EXECUTING，首点完成后正常推进下一导航点。
- `Action server is inactive`、goal rejected 和 `navigation_failed` 均为 0；监控判定 `passed=true`。

该复验使用真实全局重定位、RO、bridge、Nav2 lifecycle 和 Nav2 action，不使用假 action server。验证在目标被接受并稳定观察 5 s 后结束，因此证明的是启动竞态已闭环，不代表 bag46 全程 25 点导航完成率。

## 2026-07-20 活动路线恢复门控与搜索耗尽闭环

### 统一活动路线派发门控

所有可能重新向 Nav2 下发活动 segment 的入口统一检查：机器人为 Walk 且控制层可导航、当前地图 ready、定位可信且允许导航、Nav2 四个核心 lifecycle 节点 ACTIVE、两种 Nav2 action 可用。覆盖范围包括下一 task、播报完成、定位恢复、障碍恢复、goal 拒绝重试和 Nav2 重启恢复。

条件不满足时进入 `ACTIVE_ROUTE_DISPATCH_WAITING`：取消旧 goal、发布零速、保留 active segment 和已通过 transit，并发布 `navigation_resume_deferred`。只有条件全部恢复后才发布 `navigation_resumed` 并续发一次，避免“事件已报恢复但 action 实际未接单”。手动 `resume_route_task` 同样使用完整门控。

障碍等待期间如果定位同时丢失，即使 costmap/ROI 已确认 clear，也继续保持停车；定位恢复可信后才退出障碍等待。等待 APP 播报时没有活动 Nav2 goal，Nav2 readiness 丢失不会重发当前 task；`broadcast_finished` 准备下一段时再执行门控。

### Nav2 运行中掉线

新增 1.5 s readiness 丢失防抖。短暂服务查询或 action graph 抖动只记录观察，不停车；连续超过门槛后取消当前 goal、缓存 segment 并零速。Nav2 恢复后续发被取消 segment，再按原路线推进。

### 搜索耗尽策略

单轮仍为 45 s × 最多 3 次，接受条件不变。三次耗尽后：

- 路线保持缓存和停止，不误放行；
- 路线层向 APP 发布 `navigation_relocalization_failed`，携带 session/route/map/attempt；
- 协调器冷却 30 s 后自动开启新一轮低频搜索；
- 上层 `stop_route_task` 会锁住自动触发，不再重新搜索或恢复路线。

### 回归结果

1. 0.7 s Nav2 readiness 抖动：无停车、无 deferred、goal 无重复。
2. 持续 Nav2 掉线：产生 1 次 deferred，未在掉线期间下发新 goal；恢复后只重发被取消 segment，并完成两 task 路线。
3. 启动 pending、两次最终对齐拒绝后重试、等待期间 stop 均继续通过。
4. 搜索耗尽事件成功关联缓存路线；测试尺度冷却后自动启动新周期，上层 stop 后不再启动。
5. 障碍清除但定位不可信：持续保持停止 4 s；定位可信后才恢复并完成路线。
6. 原有定位恢复两分支通过：只续发剩余 transit；transit 全部完成时只恢复最终 task；均等待 3 个独立 RO epoch。

### 仍保留的上线边界

正式一键启动默认仍为 `shadow`，切换 `enforce` 属于灰度发布决策，不在本次代码修复中自动打开。路线缓存仍为进程内状态，路线运行节点自身崩溃重启后需要 APP 按 session/route 幂等重发；`hall1` 也仍需真实地图和全局重定位数据库后才能完成多地图上线验收。

## 2026-07-20 RO 延时观察与候选绝对一致性门控

保持原有 `5 帧 + 0.05 m/3 deg` refined `map->odom` 一致性，不通过减少帧数或放宽内部离散度提高成功率。协调器等待 RO trusted commit 的时间由 5 s 调整为 8 s；RO 同时保存全局候选对应的 `map->odom`，只有 refined 结果与候选不超过 `0.40 m/5 deg` 时才累计提交帧。候选时刻暂时缺少同步 odom 时，会在后续 NORMAL 帧重试建立候选约束。

同批 seed41/42/43 原失败样本共 104 例重放，新增门控实际追回冷启动 20 例、恢复 22 例，42 例全部完成 coordinator、RO trusted commit、bridge 接受和稳定 TF；冷启动新增样本最大误差 0.0771 m，恢复最大误差 0.1755 m，bridge 后误接受为 0。已知仅延长观察时会在 0.8842 m 错误局部极值提交的样本，被候选门控阻止早期错误提交，后续以 0.0730 m 正确结果完成。

## 2026-07-21 定位参数 YAML 归位

正式 RoboSense 导航 launch 不再内联 bridge、可信度监督和恢复协调器的门槛、超时与话题参数，统一加载 `humanoid_localization_runtime/config/localization_runtime.yaml`。同时删除会覆盖 YAML 的 coordinator `apply_timeout_sec: 5.0`，正式值统一为已验证的 `8.0`。

一键启动链路新增 `localization_runtime_config_file` 配置文件入口。`integration_mode` 不再作为逐级 launch 参数透传，由所选 YAML 内 `localization_trust_supervisor` 与 `global_relocalization_coordinator` 两个同名参数共同表达，防止启动层和节点配置出现两套值。

`map -> odom` 的所有权保持不变：只有 `prior_map_odom_bridge` 发布。RoboSense、全局重定位节点及 coordinator 仅提供或审核候选，不直接发布该 TF。

进一步将该约束落实到代码层：删除 RoboSense 节点原有的可选 `map->odom` 广播器及其 YAML 开关；旧 Open3D 节点也不再发送 `map->odom`，只保留 `/odom2map` 候选话题和非 `odom` 子坐标系的调试 TF。专用建图入口中的 SLAM Toolbox 仍可维护建图所需 TF，但不会与任何导航 launch 或 bridge 同时启动。

两条导航入口的 map server、lifecycle manager、定位就绪等待、地面动态 TF 和 bridge 参数均改为读取节点所属 YAML。Open3D 入口通过 `localization_runtime.yaml` 加载通用值，再用 `localization_runtime_open3d.yaml` 只覆盖输入话题、坐标系、confidence 和保护模式差异。launch 仅保留时间源、功能启停、配置文件选择、地图/行为树路径、静态外参和启动顺序。
