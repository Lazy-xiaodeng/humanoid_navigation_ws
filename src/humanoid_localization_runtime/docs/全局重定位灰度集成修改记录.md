# 全局重定位灰度集成修改记录

## 2026-07-19：三级模式与 RO 后提交链路

### 修改目标

把全局重定位算法的运行能力与正式系统控制权分离。系统统一使用
`integration_mode` 管理副作用，不再依赖 `dry_run` 和 `auto_apply` 两个容易冲突的布尔组合。

正式导航 launch 参数：

```text
global_relocalization_integration_mode:=off|shadow|enforce
```

默认值为 `shadow`。

### 模式权限

| 能力 | off | shadow | enforce |
|---|---:|---:|---:|
| 自动发起全局搜索 | 否 | 是 | 是 |
| 验证候选合同 | 否 | 是 | 是 |
| 发布诊断和结果 | 是 | 是 | 是 |
| 写入正式 RO | 否 | 否 | 是 |
| 授权正式 bridge | 否 | 否 | 是 |
| 自动暂停/恢复路线 | 否 | 否 | 是 |

`enable_global_relocalization` 继续只控制算法节点和协调器是否启动；
`integration_mode` 控制节点启动后是否拥有正式系统副作用权限。

### 三条运行链路

#### off

```text
Fast-LIO/雷达 -> RO -> bridge -> map->odom -> TF -> 导航
```

协调器不发起全局搜索，不写 RO 和 bridge，路线层不因全局恢复状态自动暂停。

#### shadow

```text
定位异常诊断 -> 全局搜索 -> 候选合同验证 -> shadow结果记录
正式链路仍为 RO -> bridge -> TF -> 导航
```

shadow 会保留 `startup_requires_global_relocalization` 和
`recovery_requires_global_relocalization` 诊断字段，但
`localization_recovery_required=false`，路线运行层也会校验模式，因此不会取消 goal、停车或自动续跑。

#### enforce

```text
定位监督要求恢复
-> 路线暂停并缓存当前 active segment
-> 全局候选通过 attempt/map/stamp 合同验证
-> 候选只注入 RO
-> 等待同时间戳 ro_trusted_global_anchor_commit
-> 发布审核后的 map->odom 给 bridge
-> bridge ACCEPTED global_recovery
-> 连续 RO normal 和 trust 稳定帧确认
-> 恢复缓存路线
```

RO trusted 超时、bridge 接受超时或上层终止都会取消本次尝试；不会绕过 RO 直接提交 bridge。

### 修改文件

- `humanoid_localization_runtime/scripts/global_relocalization_coordinator.py`
  - 新增 `off/shadow/enforce`；非法值安全回退到 `off`。
  - shadow 候选只发布 `shadow_observed`，不写正式话题。
  - enforce 改为 RO trusted 后再发布 bridge 恢复变换。
- `humanoid_navigation2/humanoid_navigation2/localization_trust_supervisor.py`
  - 发布 `integration_mode` 和 `global_relocalization_side_effects_enabled`。
  - 只有 enforce 对外发布有效恢复控制要求。
- `humanoid_route_runtime/src/navigation_state_manager.cpp`
  - 读取可信状态中的模式。
  - 只有 enforce 可以触发路线自动暂停和恢复。
- `humanoid_navigation2/launch/navigation2_robosense_lidar.launch.py`
  - 新增 launch 参数并将正式默认值设为 `shadow`。
- `humanoid_localization_runtime/config/localization_runtime.yaml`
  - 参考配置改为单一 `integration_mode: shadow`。

### 验证记录

以下验证均在 Todesk 工作区完成，使用独立 ROS domain：

2. `global_relocalization_coordinator_smoke.py`：

   - shadow 验证候选但 RO/bridge 发布数均为零；
   - enforce 中 RO trusted 前 bridge 发布数为零，trusted 后才提交。
3. `global_relocalization_mode_smoke.py`：
   - shadow 保留诊断标志但控制位为 false；

4. `global_relocalization_handoff_smoke.py`：
   - RO -> bridge -> 连续 RO normal -> trust 恢复闭环通过。
5. `global_relocalization_failure_smoke.py`：

```bash
colcon build --packages-select \
  humanoid_localization_runtime humanoid_navigation2 humanoid_route_runtime \
  --symlink-install
```

7. 路线运行回归通过：
   - 当前 transit 段暂停后只恢复剩余点；

   - 恢复期间上层 stop 后不再重启导航；

### 当前上线边界

默认保持 `shadow`。目前 enforce 已具备代码闭环，但尚未完成多 bag 和实机灰度观察，不能直接作为量产默认值。
正式切换前还需确认正常导航误暂停为零，并针对 bridge 接受后稳定 TF 超出 0.20 m 的历史样本继续加强在线后验门控。

## 2026-07-20：RO 精修提交、抖动防误触发与完整 TF 验收

### 修复的闭环漏洞

1. 全局候选不再绕过 RO 精匹配直接授权 bridge。RO 保留全局候选锦标，在至少 2.0 s 后对 5 帧不同点云帧的 normal match 做一致性校验，只有 `map->odom` 波动不超过 0.05 m/3 deg 才发布 trusted commit 和 RO 精修结果。
2. 协调器同时校验 global attempt/map/candidate stamp 与 RO `anchor_stamp`，再按 RO commit stamp 取对应的 refined `map->odom`。原始全局 `map->odom` 不再作为 bridge 发布值。
3. 单次 `HOLD large_jump` 只记录观测，不立即停车。只有 bridge 进入 `DEGRADED`，或 HOLD 持续至少 3.0 s 且出现至少 3 次独立更新，才进入强制恢复。
4. 恢复稳定计数改为使用 `ro_verification_epoch`。同一条 RO 状态的重复发布不能凑够恢复帧数。
5. 路线层在 enforce 中暂停并缓存当前路线进度；定位恢复后只续发未完成点。上层在恢复期间终止任务时，不会自动重启。

### 正式成功口径

压测只在以下链路全部完成时计为成功：

```text
全局候选合同通过
-> RO trusted commit
-> 协调器发布 RO refined map->odom
-> bridge ACCEPTED global_recovery
-> map->odom TF 有至少 20 个连续稳定样本
-> 样本位置误差全部 <= 0.20 m，且无 >0.10 m/3 deg 跳变
```

### Bag 困难候选专项验证

本节不是随机全量成功率。输入是从历史多假设、单源召回和 RO 交接难例中抽取的 40 个已接受候选，用于对新增安全门控做极限验证，不能代表随机启动点的总体通过率。

验证使用真实 bag 点云、正式 RO 配置和 bridge，每次两个隔离 ROS domain 并行；CPU 百分比是两个并发进程组的多核峰值，不是单核占用。

| 样本组 | 完整 TF 成功 | <=5 cm | <=10 cm | <=20 cm | bridge 后误发布/不稳定 | TF 最大误差 | 峰值 CPU | 峰值 RSS |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 冷启动第一组 10 点 | 8/10 | 7 | 8 | 8 | 0 | 0.058 m | 566% | 236 MB |
| 冷启动留出组 10 点 | 4/10 | 3 | 3 | 4 | 0 | 0.145 m | 585% | 238 MB |
| 恢复第一组 10 点 | 9/10 | 8 | 9 | 9 | 0 | 0.052 m | 554% | 235 MB |
| 恢复留出组 10 点 | 2/10 | 1 | 1 | 2 | 0 | 0.154 m | 531% | 235 MB |

在这个困难候选专项集内，冷启动为 12/20（60%），恢复为 11/20（55%）。所有已通过 bridge 的 23 例都满足 20 cm 稳定 TF 口径，未出现误接受或发布后跳变。失败样本包括两类：一类只有 0-4 个连续 NORMAL 帧；另一类虽有较多 NORMAL 帧，但 refined `map->odom` 在 0.05 m/3 deg 门槛内不稳定，因此未提交。

### 与历史 98%-100% 指标的区别

历史有两类指标，需要分开：

1. `blind_safe_cluster/repeat_audit018` 的 98%-100% commit 试验：使用隔离实验分支的 atomic verified-candidate 协议。已经上游筛选的候选到达专用话题后，RO 在候选时刻零延迟提交；某些 98/98 的分母是已接纳候选，不是全部随机点。
2. 历史随机 `3x100` 完整 TF 试验：确实要求 bridge 接受和 20 帧稳定 TF，冷启动为 292/300（97.33%），恢复为 287/300（95.67%）。但该链路仍基于 atomic trusted handoff：RO commit delay 基本为 0，不要求 RO 先做当前正式代码里的 2.0 s 独立收敛和 0.05 m/3 deg refined `map->odom` 一致性证明。当时 295 个候选全部被 bridge 接受，但其中冷启动 3 例、恢复 8 例最终 TF 超过 0.20 m。

因此，随机 97.33%/95.67% 可以作为旧 atomic handoff 的总体可用率；60%/55% 只是困难候选在新安全闭环下的通过率。当前正式新闭环的随机总体成功率尚未得到，必须在同一批 seed41/42/43 随机点上重放才能公平比较。

另用真实 coordinator 跑通冷启动和恢复各 1 例，TF 尾段最大误差分别为 0.0030 m 和 0.0037 m；困难候选 1 例只有 4 帧 normal match，RO 不提交、bridge 不接受，安全拒绝。

### 同批随机 3x100 新闭环对照

2026-07-20 使用历史 seed41/42/43 的同一批随机点和冻结全局候选，经过真实 coordinator、当前正式 RO 独立提交、bridge 和 20 帧稳定 TF 重放。每组仍以原始 100 点为分母，无候选直接计失败。

| 随机组 | 冷启动完整成功 | 恢复完整成功 | 冷启动 RO/bridge | 恢复 RO/bridge |
|---|---:|---:|---:|---:|
| seed41 | 84/100 | 82/100 | 84/84 | 82/82 |
| seed42 | 76/100 | 76/100 | 76/76 | 77/77 |
| seed43 | 83/100 | 83/100 | 83/83 | 83/83 |
| 合计 | **243/300（81.00%）** | **241/300（80.33%）** | **243/243** | **242/242** |

冷启动 243 个成功样本中，233 个 `<=5 cm`、241 个 `<=10 cm`，最大误差 0.157 m；恢复 241 个成功样本中，217 个 `<=5 cm`、239 个 `<=10 cm`，最大误差 0.151 m。冷启动/恢复成功样本中位 TF 误差分别为 0.0036 m/0.0134 m，P95 为 0.0475 m/0.0663 m。

失败漏斗：

- 两种模式都有 5/300 没有全局候选。
- 冷启动 52/295 候选没有 RO commit：31 例最大连续 NORMAL 少于 5，21 例虽有至少 5 个 NORMAL，但未通过当前提交时间/一致性窗口。
- 恢复 53/295 候选没有 RO commit：23 例最大连续 NORMAL 少于 5，30 例未通过提交时间/一致性窗口。
- 冷启动没有 bridge 后失败。恢复有 1 例（`repeat_audit018_20260742_17971`）在 bridge 后无跳变地稳定在 0.2051 m，超过 0.20 m 门槛 5.1 mm，仍按失败计数。

RO commit 的 bag 时间延迟中位数均约 2.40 s，P95 为冷启动 2.60 s、恢复 2.50 s。单例 wall time 包含节点启动和 bag 窗口，中位数为 9.54 s/11.60 s。观测到的 RO+bridge 进程组峰值约 642% CPU、437 MB RSS；coordinator 运行在测试主进程中，未纳入该资源峰值。

与旧 atomic handoff 的 97.33%/95.67% 相比，当前正式新闭环分别下降 16.33/15.34 个百分点。安全后半段明显收紧：bridge 后超差/不稳定从旧方案的 3 例冷启动+8 例恢复降为 0+1；但 RO commit 门槛也是当前主要的成功率损失点。

### 路线与模式回归

- 冷启动不会提前下发 Nav2 goal。
- 行走中恢复会取消当前 action、发零速，并在 3 个不同 RO epoch 后续发剩余路线。
- 已通过 transit 不会重跑；只剩 task 时直接恢复 task。
- 恢复期间上层 stop 后不会续跑。
- shadow 状态不取消 goal、不发零速。

### 结论与上线边界

本次修改已补齐“RO 真精修后才提交”、“候选与 commit 相关”、“短暂抖动不误停”和“独立帧才允许恢复路线”四个安全闭环。困难候选专项证明新门控没有误发布，但不能据此推导随机总体成功率。在用同一组随机点完成新旧口径对照前，正式默认继续保持 `shadow`；`enforce` 只能用于可回退的灰度机器人。
