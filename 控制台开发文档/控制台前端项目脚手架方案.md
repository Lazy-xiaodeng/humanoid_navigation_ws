# 控制台前端项目脚手架方案

## 1. 文档目的

本文档用于给“机器人导航控制台”前端项目提供一个可直接落地的脚手架方案，目标是让开发同学在 Win 环境或独立前端仓库中，可以按统一结构快速开工，而不是边做边想目录怎么摆、状态怎么拆、mock 放哪里、接口层怎么接。

## 2. 目标原则

脚手架设计应满足以下目标：

1. 首先服务 Web 控制台开发。
2. 能支撑当前确认的双状态主页面。
3. 能先跑 mock，再无缝切到真实接口。
4. 能承接后续地图管理、点位管理、日志、权限等扩展。
5. 不把 ROS 协议细节散落到页面组件里。

## 3. 推荐技术栈

建议第一版采用：

1. `React`
2. `TypeScript`
3. `Vite`
4. `pnpm`
5. `Ant Design` 或 `Arco Design`
6. `Zustand`
7. `React Router`
8. `Axios`
9. `WebSocket` 原生封装或轻量封装
10. `ECharts`

## 5. 各目录职责

### 5.1 `app`

放全局应用级能力：

1. 路由注册
2. store 初始化
3. 全局 provider
4. 类型定义
5. selector
6. 常量

### 5.2 `components`

放可复用组件，不直接承载完整业务页面。

建议拆分：

1. `common`：按钮、Tag、状态徽标、空态等
2. `map`：地图画布、地图工具栏、位姿标签等
3. `cards`：状态卡、健康卡、播报卡、日志卡等
4. `dialogs`：跳点弹窗、切图弹窗、点位编辑弹窗
5. `controls`：导航按钮栏、录包按钮栏

### 5.3 `features`

按业务域拆功能，不要所有逻辑都塞进 `pages/dashboard`。

例如：

1. `navigation` 放导航状态和动作逻辑
2. `route-task` 放路线序列和目标点逻辑
3. `map` 放地图视图和切图逻辑
4. `broadcast` 放播报等待状态
5. `obstacle` 放障碍与人工脱困状态

### 5.4 `pages`

放完整页面容器。

第一版至少有：

1. `dashboard`
2. `settings`

后续再扩展：

1. `map-management`
2. `waypoint-management`
3. `history`

### 5.5 `services`

这一层非常关键，用于隔离外部数据源。

建议拆成：

1. `api`：HTTP 请求
2. `ws`：WebSocket 管理
3. `adapters`：把 ROS/后端消息转换成前端状态模型
4. `mock`：本地 mock 数据加载器

页面组件不要直接处理 ROS 原始 JSON。

## 6. 页面分层建议

建议页面按三层组织：

1. `Page`
2. `Section`
3. `Widget/Card`

例如控制台主页：

1. `DashboardPage`
2. `TopStatusSection`
3. `TaskFlowSection`
4. `MapSection`
5. `RightPanelSection`
6. `BottomControlSection`

Section 负责组合布局，Card/Widget 负责具体渲染。

## 7. store 组织建议

建议使用 Zustand，并按 slice 拆 store：

```text
src/app/store/
  index.ts
  sessionSlice.ts
  connectionSlice.ts
  robotSlice.ts
  navigationSlice.ts
  routeTaskSlice.ts
  mapSlice.ts
  broadcastSlice.ts
  obstacleSlice.ts
  recordingSlice.ts
  logSlice.ts
  uiSlice.ts
```

这样以后接真实协议时，只需要主要改 slice 更新逻辑和 adapter，不需要大改组件。

## 8. 类型定义建议

建议统一放在：

```text
src/app/types/
  session.ts
  connection.ts
  robot.ts
  navigation.ts
  route-task.ts
  map.ts
  broadcast.ts
  obstacle.ts
  recording.ts
  logs.ts
  api.ts
  ws.ts
```

不要把类型散落在组件文件里。

## 9. 常量与枚举建议

建议单独维护：

```text
src/app/constants/
  navigation-state.ts
  reason-code.ts
  event-level.ts
  waypoint-role.ts
  walk-direction.ts
  map-mode.ts
```

好处：

1. 避免字符串硬编码
2. 便于后续统一映射中文文案
3. 便于 selector 与 adapter 复用

## 10. mock 方案

建议把 mock 当成正式能力建设，而不是临时凑合。

推荐做法：

1. 每个 mock 文件对应一整套完整状态树
2. 页面可通过顶部开发开关切换 mock 场景
3. 支持自动轮播 mock 状态，便于录屏和评审

建议提供：

1. `idle`
2. `running`
3. `broadcast_wait`
4. `obstacle_paused`
5. `manual_escape_wait_resume`
6. `localization_recovering`
7. `failed`
8. `map_switching`

## 11. WebSocket 封装建议

不要在页面里直接 `new WebSocket()`。

建议封装：

```text
src/services/ws/
  socketClient.ts
  socketEvents.ts
  socketMessageParser.ts
```

职责如下：

1. `socketClient.ts`：负责连接、重连、发送、订阅
2. `socketEvents.ts`：管理消息事件分发
3. `socketMessageParser.ts`：将消息分类并交给 adapter

## 12. Adapter 设计建议

Adapter 层负责把 ROS / 后端消息转成前端内部状态。

建议：

```text
src/services/adapters/
  navigationAdapter.ts
  routeTaskAdapter.ts
  mapAdapter.ts
  robotAdapter.ts
  obstacleAdapter.ts
  broadcastAdapter.ts
  logAdapter.ts
```

例如：

1. 后端推来 `navigation_status_changed`
2. `navigationAdapter` 把原始 JSON 转成 `NavigationState` 的更新片段
3. store 再统一落库

这样页面组件完全不用懂协议细节。

## 13. 样式管理建议

建议使用：

1. 全局 design token
2. CSS Modules 或 `scss module`
3. 局部组件样式封装

建议目录：

```text
src/assets/styles/
  tokens.css
  reset.css
  global.css
  layout.css
```

其中 `tokens.css` 至少维护：

1. 主色
2. 成功色
3. 警告色
4. 异常色
5. 边框色
6. 卡片背景
7. 阴影
8. 圆角

## 14. 环境变量建议

建议第一版区分：

`.env.development`

1. `VITE_API_BASE_URL`
2. `VITE_WS_URL`
3. `VITE_USE_MOCK`

`.env.production`

1. `VITE_API_BASE_URL`
2. `VITE_WS_URL`
3. `VITE_USE_MOCK=false`

## 15. ESLint / 格式化建议

第一版就建议加上：

1. `eslint`
2. `prettier`
3. `typescript-eslint`

避免后续多人协作时风格混乱。

## 16. 推荐落地顺序

建议按以下顺序开工：

1. 初始化脚手架
2. 建立目录结构
3. 建立类型定义
4. 建立 store
5. 接入 mock
6. 还原双状态主页面
7. 实现弹窗
8. 封装 services
9. 接真实接口

## 17. 第一版验收标准

这份脚手架落地后，至少应满足：

1. 前端项目结构清晰
2. 组件、业务、服务三层边界明确
3. mock 能支撑整页演示
4. 后续接 ROS 协议时，不需要推倒重来

## 18. 不建议的做法

尽量避免：

1. 所有组件都塞进 `pages/dashboard`
2. 页面组件直接处理 WebSocket 消息
3. 页面组件直接写协议字段名
4. 所有状态都塞进一个超大 store 文件
5. mock 数据零散写在组件里

这些做法前期看起来快，后面通常都会返工。
