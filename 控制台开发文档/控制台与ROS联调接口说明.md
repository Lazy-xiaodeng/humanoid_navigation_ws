# 控制台与ROS联调接口说明

## 1. 文档目的

本文档用于说明独立控制台项目在联调阶段如何与后端 / ROS 对接，重点回答：

1. 前端到底连谁，不直接连谁。
2. 前端发命令和收状态应该遵循什么规则。
3. 哪些消息属于命令 ACK，哪些属于真实业务状态。
4. 控制台页面需要哪些最小接口，才能支撑第一版 MVP。

说明：

本文档偏“联调边界说明”，不替代详细协议文档；如果后续需要，我还可以继续补成逐条 JSON 消息清单版。

## 2. 三层联调关系

建议联调关系固定为：

1. 前端控制台
2. 后端网关
3. ROS 机器人侧

前端不要直接连接 ROS 节点。

推荐链路：

1. 前端通过 HTTP 获取基础配置、地图列表、历史信息
2. 前端通过 WebSocket 订阅实时状态
3. 前端通过 HTTP 或 WebSocket 命令通道发起操作
4. 后端负责把命令转换后下发给 ROS
5. ROS 将状态回推给后端
6. 后端汇总后再推给前端

## 3. 联调原则

控制台联调必须遵守以下原则：

1. 命令发送成功，不等于机器人状态已经切换成功。
2. 页面主状态必须以 ROS 真实状态推送为准。
3. 前端不应依赖多个消息拼凑当前主状态，后端应尽量汇总后提供标准状态。
4. 所有失败都要有错误码和错误文案。
5. 切图、跳点、暂停恢复、播报等待等特殊状态必须可明确区分。

## 4. 建议接口分层

建议接口分为三类：

1. 查询类接口
2. 控制类接口
3. 实时推送类接口

## 5. 查询类接口

第一版建议至少具备以下查询能力：

### 5.1 查询当前机器人信息

用于页面初始化时获取：

1. 机器人名称
2. 机器人编号
3. 是否在线
4. 当前电量
5. 当前地图

### 5.2 查询地图列表

用于：

1. 地图切换弹窗
2. 顶部当前地图展示

### 5.3 查询当前路线任务快照

用于页面刷新后恢复：

1. 当前路线任务 ID
2. 当前目标点
3. 下一个目标点
4. 路线序列
5. 当前主状态

### 5.4 查询点位列表

用于：

1. 跳点弹窗候选列表
2. 点位编辑弹窗
3. 地图上的点位绘制

## 6. 控制类接口

第一版 MVP 至少应具备以下控制能力。

### 6.1 开始路线任务

用途：

1. 启动一条路线任务

前端需要提交的最小信息建议包括：

1. 机器人 ID
2. 地图 ID
3. 路线任务 ID
4. 点位 ID 列表或点位详情列表

### 6.2 暂停路线任务

用途：

1. 用户手动暂停

要求：

1. 后端要返回命令是否受理
2. 页面真实切到 `manual_paused` 必须等待 ROS 状态推送

### 6.3 继续路线任务

用途：

1. 从手动暂停恢复
2. 从人工脱困待继续恢复

### 6.4 终止路线任务

用途：

1. 主动终止当前路线任务

### 6.5 跳点

用途：

1. 在当前路线任务执行中，指定跳到某个任务点

要求：

1. 应明确回传受理结果
2. 真实路线重建结果以 ROS 后续状态推送为准

### 6.6 切换地图

用途：

1. 在无任务执行时切换地图

要求：

1. 后端必须能区分“命令已受理”和“地图已切换完成”
2. 页面需要显示切图中状态
3. 页面需要等待定位恢复完成后，才允许用户开始导航

### 6.7 开始录包

用途：

1. 启动 rosbag 录制

### 6.8 停止录包

用途：

1. 停止 rosbag 录制

## 7. 实时推送类消息

前端最关心的是实时推送，因为主页面几乎全部由它驱动。

建议后端对前端统一推送以下几类标准事件：

1. 连接状态变更
2. 机器人实时状态变更
3. 导航主状态变更
4. 路线任务进度变更
5. 地图状态变更
6. 播报状态变更
7. 障碍物 / 人工脱困状态变更
8. 录包状态变更
9. 事件日志新增

## 8. 命令 ACK 与状态推送的区别

这是联调里最容易搞混的地方。

### 8.1 命令 ACK

命令 ACK 表示：

1. 后端收到了命令
2. 命令格式合法
3. 当前阶段允许尝试执行

命令 ACK 不表示：

1. ROS 一定已执行完成
2. 页面业务状态一定应立即变化

例如：

1. 前端点击 `暂停`
2. 后端返回“暂停命令已受理”
3. 这时页面按钮可以结束 loading
4. 但页面主状态是否改成 `manual_paused`，要等 ROS 真正推送

### 8.2 状态推送

状态推送表示：

1. 机器人当前真实业务状态
2. 页面主状态应以此为准

## 9. 推荐的最小实时状态模型

后端推给前端的“主状态快照”至少建议覆盖这些字段：

1. 机器人在线状态
2. 电量
3. 实时速度
4. 当前位姿
5. 当前地图
6. 导航主状态
7. 导航原因码与原因文案
8. 当前路线任务 ID
9. 当前目标点
10. 下一个目标点
11. 跳点目标
12. 路线序列
13. 播报等待状态
14. 障碍物暂停状态
15. 定位质量
16. 系统健康状态
17. 录包状态

## 10. 页面与接口的映射关系

建议页面各区块按下面方式消费数据。

### 10.1 顶部全局栏

依赖：

1. 连接状态
2. 电量
3. 当前地图
4. 定位状态
5. 当前时间

### 10.2 左侧任务流程区

依赖：

1. 当前路线任务 ID
2. 当前目标点
3. 下一个目标点
4. 跳点目标
5. 当前主状态
6. 原因文案
7. 事件日志

### 10.3 地图区

依赖：

1. 当前地图底图
2. 机器人位姿
3. 路线序列
4. 当前目标点
5. 选中点位

### 10.4 右侧实时状态区

依赖：

1. 速度
2. 航向角
3. 电量
4. 网络延迟
5. 定位置信度
6. 当前行为模式

### 10.5 右侧健康 / 播报 / 路线 / 日志区

依赖：

1. 系统健康
2. 播报等待状态
3. 路线序列
4. 事件日志

### 10.6 底部控制区

依赖：

1. 导航主状态
2. 是否录包
3. 是否允许跳点

## 11. 第一版联调流程建议

建议前端、后端、ROS 按以下顺序联调，而不是一上来什么都一起接。

### 11.1 第一步：只接连接与状态快照

目标：

1. 页面能显示在线状态
2. 页面能显示电量、地图、位姿、导航状态

### 11.2 第二步：接开始 / 暂停 / 继续 / 终止

目标：

1. 五个主按钮先跑通最基本四个
2. 页面能根据真实推送切状态

### 11.3 第三步：接跳点与播报等待

目标：

1. 跳点弹窗可用
2. 播报等待能正确显示

### 11.4 第四步：接障碍物暂停与人工脱困

目标：

1. 异常暂停态页面能真实落地
2. 页面能显示暂停原因

### 11.5 第五步：接地图切换与录包

目标：

1. 地图切换弹窗可用
2. rosbag 录制可用

## 12. 联调阶段推荐 mock/真实双通道

建议前端保留：

1. mock 模式
2. 真实联调模式

这样好处是：

1. 联调出问题时，UI 开发不被阻断
2. 后端未准备好某类消息时，页面还能继续推进
3. 方便演示和录屏

## 13. 错误处理建议

联调阶段要重点收口以下错误：

1. 命令发送失败
2. ACK 成功但 ROS 状态未变化
3. WebSocket 断连
4. 地图切换失败
5. 跳点失败
6. 播报状态丢失
7. 障碍物暂停原因缺失

页面至少要做到：

1. 给出明确提示
2. 不错误切换主状态
3. 不让按钮进入不可恢复的 loading

## 14. 第一版最小接口清单

如果只为 MVP 服务，建议至少具备：

1. 查询当前机器人状态
2. 查询地图列表
3. 查询当前路线任务
4. 查询点位列表
5. 开始路线任务
6. 暂停路线任务
7. 继续路线任务
8. 终止路线任务
9. 跳点
10. 切换地图
11. 开始录包
12. 停止录包
13. WebSocket 实时状态订阅
