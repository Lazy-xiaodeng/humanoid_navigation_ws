# Win环境控制台开发准备清单

## 1. 文档目的

本文档用于给 Windows 开发同学快速说明：

1. 建议使用哪种 Codex 开发方式
2. 需要提前安装哪些软件
3. 推荐的前端开发技术栈是什么
4. 如何在不依赖 ROS 实机环境的情况下先把控制台做起来
5. 后续接 ROS 真机联调时要补什么环境

本文档对应当前这套“机器人导航控制台”项目，而不是直接在 ROS 工作区里开发业务前端。

## 2. 推荐开发方式

### 2.1 推荐结论

Windows 环境下，推荐：

1. **主力开发工具使用 `VS Code + Codex 插件`**
2. **Codex 桌面客户端用于方案讨论、文档梳理、评审和非工程化问答**

原因如下：

1. `VS Code + Codex 插件` 更适合真实开发
2. 可以直接读写前端项目源码
3. 可以直接运行终端命令、启动开发服务器、看报错、改代码、提交 Git
4. 更适合持续迭代 UI、联调接口、处理构建报错

Codex 桌面客户端更适合：

1. 聊方案
2. 读文档
3. 做需求拆解
4. 生成页面思路
5. 评审接口和业务流程

如果目标是**真正把控制台项目做出来并长期维护**，优先选 `VS Code + Codex 插件`。

## 3. 建议的软件安装清单

### 3.1 必装软件

1. `Visual Studio Code`
2. `Git for Windows`
3. `Node.js LTS`
4. `pnpm` 或 `npm`
5. `Google Chrome` 或 `Microsoft Edge`

### 3.2 推荐软件

1. `nvm-windows`
   作用：管理多个 Node 版本，避免后续升级冲突
2. `Postman` 或 `Apifox`
   作用：调试 HTTP / WebSocket 接口
3. `Figma`
   作用：查看 UI 设计稿、标注、间距、颜色
4. `Typora` 或 `Obsidian`
   作用：看我们这批 Markdown 开发文档

### 3.3 VS Code 推荐插件

1. `ESLint`
2. `Prettier`
3. `EditorConfig for VS Code`
4. `GitLens`
5. `Error Lens`
6. `Path Intellisense`
7. `Tailwind CSS IntelliSense`
8. `Codex` 插件

## 4. 建议版本

为了减少环境差异，建议统一：

1. `Node.js 20 LTS`
2. `pnpm 9.x`
3. `Git 2.4x+`
4. `VS Code` 使用稳定版

如果团队还没有统一版本，建议先定成这套。

## 5. 推荐技术栈

控制台项目建议使用：

1. `React`
2. `TypeScript`
3. `Vite`
4. `Zustand`
5. `React Router`
6. `Tailwind CSS`
7. `ECharts`
8. `WebSocket`

对应职责：

1. `React + TypeScript`
   负责前端页面与组件开发
2. `Vite`
   负责本地开发与构建
3. `Zustand`
   负责机器人状态、导航状态、地图状态、日志状态管理
4. `React Router`
   负责多页面或多视图切换
5. `Tailwind CSS`
   负责快速实现我们现在这套奶油白科技感 UI
6. `ECharts`
   负责状态图、统计图、趋势图、健康图表
7. `WebSocket`
   负责和后端网关做实时消息联动

## 6. 本地开发建议

### 6.1 不建议直接在 ROS 工作区里写前端

原因：

1. ROS 工作区主要用于导航源码、launch、配置和脚本
2. 前端项目依赖很多 `node_modules`
3. 混在一起会让目录臃肿
4. 也不利于前后端独立开发、打包和发布

建议单独新建一个前端项目仓库，或者至少单独新建一个前端工程目录，例如：

```text
robot-console/
```

### 6.2 前端项目推荐目录

```text
robot-console/
  src/
    api/
    assets/
    components/
    features/
    pages/
    store/
    styles/
    utils/
  public/
  mock/
  package.json
  vite.config.ts
  tsconfig.json
```

### 6.3 开发阶段的推荐顺序

建议不要一上来就连 ROS 真机，而是分三步做：

1. **第一步：纯前端静态页面**
   目标：先把界面做出来，包含地图区、状态区、路线区、日志区、控制按钮区
2. **第二步：前端接 Mock 数据**
   目标：先把开始、暂停、继续、异常暂停、播报等待、切图中等状态跑通
3. **第三步：接真实后端 / ROS 网关**
   目标：把 JSON 协议真正联调起来

这样开发效率最高，也最不容易被 ROS 环境卡住。

## 7. 与 Codex 配合的最佳实践

### 7.1 适合让 Codex 做的事情

1. 生成页面骨架
2. 补状态管理
3. 写 WebSocket 消息适配层
4. 补 TypeScript 类型定义
5. 根据文档生成 Mock 数据
6. 改页面布局和样式
7. 重构组件
8. 根据报错修复代码
9. 写接口说明和开发文档

### 7.2 每次给 Codex 的上下文建议

为了让它更容易一次做对，建议每次都给：

1. 当前项目目录结构
2. 本次要修改的页面或文件
3. 对应开发文档路径
4. 需要遵守的 UI 风格
5. 这次只改什么，不改什么

例如可以这样描述：

```text
这是一个 React + TypeScript + Vite 的机器人控制台项目。
请根据《控制台前端状态管理设计.md》和《控制台与ROS联调JSON消息清单.md》，
帮我实现导航控制区与状态栏，不要改地图组件，不要改全局主题。
```

### 7.3 推荐工作流

建议采用这个节奏：

1. 先让 Codex 读文档
2. 再让 Codex 看项目结构
3. 然后让它只做一个小模块
4. 本地运行看效果
5. 有问题再继续补

不要第一次就让它“一口气做完整个系统”，这样返工会更多。

## 8. 如果暂时没有 ROS 环境，能不能先开发

可以，而且建议先这样做。

即使没有 ROS、没有机器人、没有后端网关，也可以先完成：

1. 页面 UI
2. 页面交互
3. 状态切换
4. Mock 日志
5. Mock 地图信息
6. Mock 路线执行流程
7. Mock 异常暂停/人工脱困/播报等待/切图中状态

需要做的只是：

1. 按照我们现有 JSON 协议定义好 TypeScript 类型
2. 本地写一份 Mock 数据和 Mock WebSocket 事件流
3. 用定时器模拟 ROS 推送状态

这样等后端/ROS 接进来时，只需要替换数据源。

## 9. 真正联调前还需要准备什么

当前端页面和 Mock 跑起来后，联调前还需要：

1. 后端网关地址
2. WebSocket 路径
3. HTTP 查询接口地址
4. 登录鉴权方式
5. 设备选择方式
6. 机器人 ID / map_id / route_task_id 的真实规则
7. ROS 推送消息样例
8. 错误码枚举

如果这些还没完全定，可以先按我们现有文档里的协议占位开发。

## 10. 是否需要安装 ROS

### 10.1 前端同学

前端同学**通常不需要**在 Windows 本机安装 ROS。

前端主要依赖：

1. 页面
2. 状态管理
3. HTTP / WebSocket 联调
4. Mock 系统

### 10.2 什么时候才需要接触 ROS

只有在下面场景才需要：

1. 直接连机器人实机做联调
2. 本地同时承担网关开发
3. 需要看 ROS 原始消息字段

即便如此，也更建议：

1. ROS 继续放在 Ubuntu 机器上运行
2. Windows 前端通过局域网连后端/网关/ROS 桥接服务

这样整体更稳，也更接近最终部署形态。

## 11. 给开发同学的落地建议

如果现在就要开工，建议按下面顺序：

1. 安装 `VS Code`、`Git`、`Node.js 20 LTS`
2. 安装 `pnpm`
3. 安装 VS Code 插件：`ESLint`、`Prettier`、`GitLens`、`Codex`
4. 新建独立前端项目
5. 先把我们已经定下来的双状态页面做出来
6. 按文档接入 Mock 数据
7. 把开始/暂停/继续/终止/跳点/切图这些控制链路跑通
8. 再接后端网关
9. 最后再和 ROS 真机联调

## 12. 一句话结论

如果目标是**高效率、可维护、能持续迭代地把控制台做出来**，推荐方案就是：

**Windows 下使用 `VS Code + Codex 插件 + Node.js 前端工程` 开发；ROS 继续放在 Ubuntu 机器上跑；先 Mock，后联调。**
