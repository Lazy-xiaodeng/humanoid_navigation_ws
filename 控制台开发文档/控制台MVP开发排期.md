# 控制台MVP开发排期

## 1. 文档目的

本文档用于将“机器人导航控制台”MVP 开发任务拆分为可执行排期，覆盖：

1. 前端原型
2. 前端状态管理
3. mock 数据
4. 后端网关
5. ROS 联调
6. 实机验证

文档目标不是给一个很虚的工期，而是明确每一阶段做什么、谁做、做到什么程度算完成、有哪些依赖关系。

## 2. MVP 范围

本次 MVP 只覆盖主控制台的核心闭环，不追求一步做到全平台全权限全业务。

MVP 范围包含：

1. 主控制台页
2. 正常运行态 / 异常暂停态双状态页面
3. 五个主导航按钮：`开始 / 暂停 / 继续 / 终止 / 跳点`
4. 地图显示区
5. 左侧任务流程区
6. 右侧状态 / 健康 / 播报 / 路线 / 日志区
7. 跳点弹窗
8. 地图切换弹窗
9. rosbag 录制按钮
10. mock 场景切换
11. 对接当前 ROS 新导航系统协议

MVP 暂不强制包含：

1. 完整账号权限系统
2. 多租户
3. 复杂运维后台
4. 移动端原生封装
5. 历史报表

## 3. 角色分工建议

建议至少按以下角色分工：

1. 前端开发
2. 后端 / 网关开发
3. ROS 联调开发
4. 测试 / 实机验证

如果人数不足，也可以合并角色，但职责不能丢。

### 3.1 前端开发职责

1. 页面布局
2. 组件拆分
3. 状态管理
4. mock 数据接入
5. 按钮交互
6. 异常态页面
7. 地图 UI 展示

### 3.2 后端 / 网关职责

1. 控制台接口定义
2. WebSocket 会话管理
3. 命令转发
4. 状态汇聚
5. 统一错误码
6. 数据透传与适配

### 3.3 ROS 联调职责

1. 确认现有协议字段
2. 提供 mock 样例
3. 接入真实消息
4. 联调开始 / 暂停 / 继续 / 终止 / 跳点 / 切图 / 录包
5. 排查实机问题

## 4. 时间线建议

如果以“一个比较紧凑、但可落地”的节奏推进，建议按 4 周拆分。

## 5. 第 1 周：页面骨架与视觉定版

### 5.1 目标

完成控制台主页面静态骨架，做到“能看、能评审、能改样式”。

### 5.2 本周任务

前端：

1. 初始化独立项目脚手架
2. 搭建基础路由与页面布局
3. 完成顶部全局栏
4. 完成左侧任务流程区静态版
5. 完成中间地图区静态版
6. 完成右侧状态 / 健康 / 播报 / 路线 / 日志卡片静态版
7. 完成底部控制区静态版
8. 基于“双状态效果图”还原正常态和异常态样式

产品 / 业务确认：

1. 确认色彩、层级、布局
2. 确认按钮文案
3. 确认卡片标题
4. 确认哪些信息必须首屏展示

### 5.3 本周完成标准

1. 页面结构与效果图基本一致
2. 正常态与异常态都能切换预览
3. 所有主要区域都有占位数据

## 6. 第 2 周：状态管理与 mock 场景

### 6.1 目标

让页面从“静态展示”变成“可状态切换的前端原型”。

### 6.2 本周任务

前端：

1. 建立 TypeScript 状态类型
2. 建立 store
3. 建立 selector
4. 接入 6 到 8 组 mock 场景
5. 将正常运行态、播报等待态、障碍物暂停态、人工脱困待继续态、定位恢复中态、失败态全部跑通
6. 完成按钮可用规则
7. 完成跳点弹窗基础交互
8. 完成地图切换弹窗基础交互

后端：

1. 输出控制台接口草案
2. 确认与 ROS 的消息映射边界
3. 准备联调占位接口

ROS：

1. 提供真实协议样例
2. 提供常见状态样本
3. 提供关键事件示例

### 6.3 本周完成标准

1. 不接 ROS 也能完整演示主流程
2. 五个主按钮状态切换正确
3. 左中右三块数据能同步联动变化

## 7. 第 3 周：后端网关与协议联调

### 7.1 目标

让控制台从 mock 切换到真实消息链路。

### 7.2 本周任务

后端：

1. 建立 WebSocket 连接管理
2. 建立前端到 ROS 的命令转发
3. 建立 ROS 到前端的状态广播
4. 封装统一 ACK 结构
5. 封装统一错误码
6. 对接地图列表 / 当前地图 / 切图命令
7. 对接路线任务控制命令
8. 对接 rosbag 录制命令

前端：

1. 接真实 WebSocket
2. 增加命令发送 loading 态
3. 以真实状态推送更新页面
4. 增加断线重连提示
5. 增加命令失败提示

ROS：

1. 配合验证协议字段
2. 检查状态推送是否覆盖页面所需字段
3. 检查跳点、播报等待、障碍物暂停、切图状态是否能正确上屏

### 7.3 本周完成标准

1. 前端可看到真实连接状态
2. 前端能发真实命令
3. 页面能跟随 ROS 推送真实切状态
4. 已能完成基本联调演示

## 8. 第 4 周：实机闭环验证与收口

### 8.1 目标

完成真实机器人上的 MVP 闭环验证。

### 8.2 本周任务

联调 / 测试：

1. 验证开始导航
2. 验证手动暂停
3. 验证继续导航
4. 验证终止导航
5. 验证跳点
6. 验证障碍物自动暂停
7. 验证人工脱困后继续
8. 验证等待播报完成
9. 验证地图切换
10. 验证 rosbag 录制
11. 验证断线 / 重连场景

前端：

1. 修 UI 细节
2. 修异常态提示
3. 修按钮互斥逻辑
4. 修日志展示问题

后端 / ROS：

1. 修消息不一致问题
2. 修漏推状态问题
3. 修异常收口问题

### 8.3 本周完成标准

1. 一条完整路线任务能通过控制台稳定跑通
2. 双状态页面能真实反映正常与异常
3. 常用异常场景能被正确识别和展示
4. 有一轮基本可交付的演示版本

## 9. 里程碑定义

建议设 4 个里程碑。

### 9.1 M1：视觉稿落地

判定标准：

1. 双状态页面静态还原完成
2. 主要组件结构定版

### 9.2 M2：前端原型可演示

判定标准：

1. mock 场景驱动可切换
2. 五个主按钮逻辑跑通
3. 弹窗基本完成

### 9.3 M3：联调链路跑通

判定标准：

1. 前端能收真实状态
2. 前端能发真实命令
3. 控制台和 ROS 主链路打通

### 9.4 M4：实机 MVP 收口

判定标准：

1. 真实机器人跑通核心流程
2. 关键异常场景有展示和恢复路径
3. 可作为第一版内部演示或试用版

## 10. 每周产出物要求

为了避免“做了很多但没人知道做到哪”，建议每周都有明确产出物。

### 第 1 周产出物

1. 页面截图
2. 组件清单
3. 布局说明

### 第 2 周产出物

1. store 类型定义
2. mock 场景文件
3. 页面录屏

### 第 3 周产出物

1. 接口说明
2. 联调截图
3. 命令 / 状态日志样例

### 第 4 周产出物

1. 实机验证记录
2. 问题清单
3. MVP 演示版

## 11. 风险点

这类控制台项目常见风险主要有以下几类：

1. 页面做得很快，但状态模型很乱，后期返工
2. 前端直接绑定 ROS 细节，后端网关层缺失
3. 命令 ACK 和真实状态推送混淆
4. mock 阶段做得太粗，联调时发现页面结构不够用
5. 地图区前期只画了静态底图，联调时补实时位姿成本高
6. 异常态没有提前设计，后面只能在正常页硬塞告警

建议每周评审一次，不要等到联调周才第一次系统性看问题。

## 12. 如果人员更少，怎么压缩排期

如果只有 1 名前端 + 1 名后端 / ROS 复合开发，可以把节奏压成 3 周：

1. 第 1 周：页面骨架 + store + mock
2. 第 2 周：后端网关 + 前端联调
3. 第 3 周：实机验证 + 修问题

但压缩排期的代价是：

1. 页面打磨程度会下降
2. 异常态细节可能不够精致
3. 测试覆盖会更吃紧

## 13. 第一版验收建议

建议第一版验收时，不以“功能堆了多少”为核心，而以“主链路是否真实可用”为核心。

推荐验收项：

1. 能连接机器人
2. 能看见实时状态
3. 能开始一条路线任务
4. 能暂停 / 继续 / 终止
5. 能跳点
6. 能在异常暂停时给出明确提示
7. 能查看事件日志
8. 能切换地图
9. 能开始和停止录包

## 14. 后续迭代方向

MVP 完成后，建议第二阶段再做：

1. 登录与权限
2. 多机器人接入
3. 地图管理页
4. 点位管理页
5. 历史任务回放
6. 日志检索与导出
7. Electron / 平板端适配
