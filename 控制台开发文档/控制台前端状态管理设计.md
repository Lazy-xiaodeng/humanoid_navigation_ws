# 控制台前端状态管理设计

## 1. 文档目的

本文档用于指导“机器人导航控制台”前端状态管理设计，目标是让页面在以下场景下仍然保持清晰、稳定、可维护：

1. 正常运行
2. 手动暂停
3. 障碍物暂停
4. 人工脱困待继续
5. 等待播报完成
6. 定位恢复中
7. 导航失败
8. 地图切换中

本文档重点不是讲样式，而是讲“前端应该如何建状态、如何切换状态、哪些状态来自 ROS、哪些状态来自 UI 本地、如何避免页面逻辑混乱”。

## 2. 设计原则

前端状态管理必须遵守以下原则：

1. 页面状态必须由“明确的数据状态”驱动，不能靠按钮点击后手工改一堆布尔值。
2. 业务主状态必须只有一份单一事实来源，不能多个组件各自猜当前状态。
3. ROS 推送状态与前端临时 UI 状态必须分层管理，不能混在一起。
4. 导航状态、地图状态、播报状态、异常状态要拆开建模，但要能汇总成页面总状态。
5. 所有按钮是否可点，必须通过状态派生，而不是写死在组件里。

## 3. 状态分层总览

建议前端状态拆成 4 层：

1. 连接层状态
2. 设备业务状态
3. 页面衍生状态
4. 本地 UI 状态

### 3.1 连接层状态

连接层状态用于表示“前端是否还能和后端 / 机器人正常通信”，例如：

1. WebSocket 是否连接
2. 最近一次心跳时间
3. 后端接口是否可达
4. 当前机器人会话是否有效

### 3.2 设备业务状态

业务状态用于表示“机器人现在真实处于什么状态”，例如：

1. 是否有路线任务在执行
2. 当前导航主状态
3. 当前目标点 / 下一个目标点 / 跳点目标
4. 当前地图
5. 当前定位质量
6. 当前障碍物暂停原因
7. 当前播报等待状态

这一层主要来自 ROS 推送或后端汇总后的标准状态消息。

### 3.3 页面衍生状态

页面衍生状态是由业务状态计算出来的，不直接存原始事实，例如：

1. 当前页面顶部应该显示绿色还是红色
2. `暂停` 按钮是否可用
3. 当前是“正常运行态页面”还是“异常暂停态页面”
4. 左侧流程卡是否显示“等待播报”
5. 是否需要弹出“人工脱困提示”

### 3.4 本地 UI 状态

本地 UI 状态仅用于前端交互，不代表机器人真实状态，例如：

1. 跳点弹窗是否打开
2. 地图是否跟随机器人
3. 当前地图缩放等级
4. 当前显示 2D 还是 3D
5. 是否展开更多日志

## 4. 推荐状态树

建议第一版状态树至少包含以下顶级字段：

```ts
type RootState = {
  session: SessionState
  connection: ConnectionState
  robot: RobotState
  navigation: NavigationState
  routeTask: RouteTaskState
  map: MapState
  broadcast: BroadcastState
  obstacle: ObstacleState
  recording: RecordingState
  logs: EventLogState
  ui: UIState
}
```

## 5. 各状态模块设计

## 5.1 `session`

用于维护登录用户和当前控制对象信息。

建议字段：

```ts
type SessionState = {
  userId: string | null
  userName: string | null
  role: 'admin' | 'operator' | 'viewer' | null
  selectedRobotId: string | null
  selectedRobotName: string | null
}
```

用途：

1. 控制谁能下发导航命令
2. 控制谁只能看不能操作
3. 识别当前页面绑定的是哪台机器人

## 5.2 `connection`

用于维护控制台与后端 / ROS 的链路健康。

建议字段：

```ts
type ConnectionState = {
  wsConnected: boolean
  wsConnecting: boolean
  lastHeartbeatAt: number | null
  backendReachable: boolean
  robotOnline: boolean
  latencyMs: number | null
  lastError: string | null
}
```

页面用途：

1. 顶部“已连接 / 已断开”状态
2. 右侧网络延迟显示
3. 断链时禁用高风险控制按钮

## 5.3 `robot`

用于维护机器人本体实时状态。

建议字段：

```ts
type RobotState = {
  batteryPercent: number | null
  linearSpeed: number | null
  angularSpeed: number | null
  headingDeg: number | null
  pose: {
    x: number | null
    y: number | null
    yawDeg: number | null
  }
  health: {
    navModule: 'ok' | 'warn' | 'error' | 'unknown'
    localizationModule: 'ok' | 'warn' | 'error' | 'unknown'
    obstacleModule: 'ok' | 'warn' | 'error' | 'unknown'
    powerModule: 'ok' | 'warn' | 'error' | 'unknown'
    commModule: 'ok' | 'warn' | 'error' | 'unknown'
  }
}
```

页面用途：

1. 顶部电量显示
2. 实时状态卡
3. 系统健康卡
4. 地图中位姿标签

## 5.4 `navigation`

这是前端最核心的业务主状态模块。

建议字段：

```ts
type NavigationMainState =
  | 'idle'
  | 'starting'
  | 'running'
  | 'manual_paused'
  | 'obstacle_paused'
  | 'manual_escape_wait_resume'
  | 'broadcast_wait'
  | 'localization_recovering'
  | 'map_switching'
  | 'failed'
  | 'stopping'
  | 'completed'

type NavigationState = {
  mainState: NavigationMainState
  reasonCode: string | null
  reasonText: string | null
  startedAt: number | null
  pausedAt: number | null
  resumedAt: number | null
  finishedAt: number | null
  canStart: boolean
  canPause: boolean
  canResume: boolean
  canStop: boolean
  canJump: boolean
}
```

说明：

1. `mainState` 是导航页面的单一主状态来源。
2. `reasonCode` 用于表达暂停原因、失败原因、恢复原因。
3. `canStart/canPause/canResume/canStop/canJump` 建议由 selector 派生，不直接从 ROS 存入，但第一版也可先落在 store 中。

## 5.5 `routeTask`

用于表示路线任务执行上下文。

建议字段：

```ts
type RouteWaypointStatus =
  | 'pending'
  | 'running'
  | 'completed'
  | 'skipped'
  | 'blocked'

type RouteWaypoint = {
  waypointId: string
  waypointName: string
  role: 'task' | 'transit'
  walkDirection: 'forward' | 'backward'
  needBroadcast: boolean
  status: RouteWaypointStatus
}

type RouteTaskState = {
  routeTaskId: string | null
  routeName: string | null
  currentWaypointId: string | null
  nextWaypointId: string | null
  jumpTargetWaypointId: string | null
  currentWaypointName: string | null
  nextWaypointName: string | null
  jumpTargetWaypointName: string | null
  sequence: RouteWaypoint[]
  progressPercent: number | null
}
```

页面用途：

1. 左侧当前目标 / 下一个目标 / 跳点目标
2. 右侧路线序列卡
3. 地图路径高亮

## 5.6 `map`

用于表示地图相关状态。

建议字段：

```ts
type MapState = {
  currentMapId: string | null
  currentMapName: string | null
  availableMaps: Array<{
    mapId: string
    mapName: string
  }>
  switching: boolean
  switchTargetMapId: string | null
  switchTargetMapName: string | null
  mode: '2d' | '3d'
  followRobot: boolean
  zoomLevel: number
}
```

页面用途：

1. 顶部当前地图显示
2. 地图切换弹窗
3. 中间地图工具栏

## 5.7 `broadcast`

用于表示播报协同状态。

建议字段：

```ts
type BroadcastState = {
  waiting: boolean
  currentBroadcastId: string | null
  currentBroadcastText: string | null
  waitingSince: number | null
  lastFinishedAt: number | null
}
```

页面用途：

1. 右侧播报状态卡
2. 左侧流程中的“等待 APP 播报完成”
3. 顶部或中部的提示文案

## 5.8 `obstacle`

用于表示障碍物暂停和人工脱困相关状态。

建议字段：

```ts
type ObstacleState = {
  blocked: boolean
  blockedSince: number | null
  reason: 'dynamic_obstacle' | 'manual_escape' | null
  snapshotUrl: string | null
  guidanceText: string | null
}
```

页面用途：

1. 异常暂停态卡片
2. 人工脱困引导
3. 左侧暂停原因展示

## 5.9 `recording`

用于表示 rosbag 录制状态。

建议字段：

```ts
type RecordingState = {
  recording: boolean
  startedAt: number | null
  savePath: string | null
  fileName: string | null
  lastError: string | null
}
```

页面用途：

1. 底部录包按钮状态
2. 录包提示
3. 运维排障辅助

## 5.10 `logs`

用于表示事件日志。

建议字段：

```ts
type EventLogItem = {
  id: string
  timestamp: number
  level: 'info' | 'success' | 'warn' | 'error'
  category: 'system' | 'nav' | 'broadcast' | 'map' | 'obstacle' | 'user'
  title: string
  detail: string
}

type EventLogState = {
  items: EventLogItem[]
  maxSize: number
}
```

页面用途：

1. 右侧事件日志卡
2. 故障追踪
3. 用户操作回看

## 5.11 `ui`

用于维护纯前端本地状态。

建议字段：

```ts
type UIState = {
  jumpDialogOpen: boolean
  waypointEditorOpen: boolean
  mapSwitchDialogOpen: boolean
  selectedWaypointId: string | null
  routePanelExpanded: boolean
  logPanelExpanded: boolean
}
```

## 6. 主状态机设计

建议围绕 `navigation.mainState` 设计一个简化状态机。

### 6.1 状态列表

1. `idle`
2. `starting`
3. `running`
4. `manual_paused`
5. `obstacle_paused`
6. `manual_escape_wait_resume`
7. `broadcast_wait`
8. `localization_recovering`
9. `map_switching`
10. `failed`
11. `stopping`
12. `completed`

### 6.2 合法迁移

建议第一版只允许以下主要迁移：

1. `idle -> starting`
2. `starting -> running`
3. `running -> manual_paused`
4. `running -> obstacle_paused`
5. `running -> broadcast_wait`
6. `running -> failed`
7. `running -> stopping`
8. `manual_paused -> running`
9. `obstacle_paused -> running`
10. `obstacle_paused -> manual_escape_wait_resume`
11. `manual_escape_wait_resume -> running`
12. `broadcast_wait -> running`
13. `localization_recovering -> running`
14. `stopping -> idle`
15. `running -> completed`
16. `completed -> idle`

如果后续状态更多，必须继续在状态机层扩展，不建议到组件里临时加特判。

## 7. Selector 设计

前端不应在组件中直接判断一堆主状态字符串，建议封装 selector。

建议至少封装以下 selector：

1. `selectIsConnected`
2. `selectIsRunning`
3. `selectIsPaused`
4. `selectIsAbnormal`
5. `selectPauseReasonText`
6. `selectCanStart`
7. `selectCanPause`
8. `selectCanResume`
9. `selectCanStop`
10. `selectCanJump`
11. `selectCurrentWaypoint`
12. `selectNextWaypoint`
13. `selectJumpTarget`
14. `selectTopStatusTone`
15. `selectPageMode`

例如：

1. `selectPageMode` 返回 `normal` 或 `abnormal`
2. `selectTopStatusTone` 返回 `success / warning / error / neutral`

这样样式组件不需要理解复杂业务。

## 8. 命令发送与 ACK 处理建议

前端不能把“用户点了按钮”直接等同于“机器人已经进入那个状态”。

建议流程统一为：

1. 用户点击按钮
2. 前端发命令给后端
3. 前端进入 `pending` 或按钮 loading 态
4. 后端返回命令受理结果
5. ROS 再推送真实业务状态
6. 前端以“ROS 真实状态推送”为准更新主页面

例如“暂停”：

1. 用户点击 `暂停`
2. 前端发 `pause_route_task`
3. 前端只把按钮变成 loading，不直接写死为 `manual_paused`
4. 收到 ROS 推送 `navigation_paused + reason=manual_pause`
5. 再把主状态真正切换成 `manual_paused`

这条规则非常重要，否则 UI 会和真实机器人状态脱节。

## 9. 正常态与异常态页面映射

建议通过 selector 把业务状态映射成两种大页面模式。

### 9.1 正常态页面

满足以下任一状态时，页面走正常态布局：

1. `idle`
2. `starting`
3. `running`
4. `broadcast_wait`
5. `completed`

说明：

1. `broadcast_wait` 虽然不是纯运行，但它不是故障态。
2. `completed` 可以单独加一个成功提示，但整体仍可延用正常态布局。

### 9.2 异常态页面

满足以下任一状态时，页面走异常态布局：

1. `obstacle_paused`
2. `manual_escape_wait_resume`
3. `localization_recovering`
4. `failed`

说明：

1. `manual_paused` 是否归入异常态，可由产品决定。
2. 如果手动暂停只是人为控制，不一定需要红橙色异常视觉。

## 10. 前端建议使用的 store 方案

如果你们是中小型前端团队，推荐优先使用 `Zustand`。

原因：

1. 学习成本低
2. 状态切片容易拆
3. 比 Redux Toolkit 更轻
4. 更适合这种设备控制台类项目

推荐按 slice 拆分：

1. `sessionSlice`
2. `connectionSlice`
3. `robotSlice`
4. `navigationSlice`
5. `routeTaskSlice`
6. `mapSlice`
7. `broadcastSlice`
8. `obstacleSlice`
9. `recordingSlice`
10. `logSlice`
11. `uiSlice`

## 11. Mock 数据组织建议

建议在前端项目里单独维护 mock 场景目录：

```text
mock/
  idle.json
  running.json
  broadcast_wait.json
  obstacle_paused.json
  manual_escape_wait_resume.json
  localization_recovering.json
  failed.json
  map_switching.json
```

每个 mock 文件都应覆盖整棵状态树，这样最利于切页面和调样式。

## 12. 风险点

前端状态管理最容易踩的坑有以下几个：

1. 把命令点击当成真实状态变化
2. 把 ROS 状态和 UI 临时状态混在一起
3. 多个组件分别维护自己的“当前目标”
4. 手写太多 if/else，导致按钮规则不可维护
5. 日志、播报、障碍、导航都直接塞进一个大对象里

建议第一版就把状态边界划清，不然后面功能一多会非常难改。

## 13. 第一版落地建议

建议按以下顺序落地：

1. 先定义 TypeScript 类型
2. 再定义 store 与默认状态
3. 再补 selector
4. 再接 mock 数据
5. 最后才接组件与按钮逻辑

不要先写页面再回头补状态模型，那样通常会返工。

## 14. 交付结果定义

这份状态管理设计落地完成后，应至少达到以下效果：

1. 正常运行态与异常暂停态能用同一套状态树切换
2. 五个主按钮全部由 selector 控制可用性
3. 地图区、流程区、播报区、日志区全部能吃同一份 store 数据
4. 切 mock 场景时页面无需额外手调组件
5. 后续接 ROS 消息时只改数据适配层，不大改页面组件
